## 2. 재고 문서가 틀렸던 자리 둘

2차 재고 §3-3 은 남은 7건을 **"서로 독립된 네 경로, 전부 major 업그레이드가 필요"** 로 적었다.
그중 둘은 실행 불가능하거나 무효한 처방이었다.

### 2-1. "`@huggingface/transformers` 4.2.0 → 상위" — 올라갈 자리가 없다

**4.2.0 이 이미 최신이다.** `npm view @huggingface/transformers versions` 의 끝이 4.2.0 이다.
"상위 버전으로" 라는 처방은 대상이 존재하지 않았다.

실제 문제는 그 아래에 있었다.

```
. > @huggingface/transformers@4.2.0 > sharp@0.34.5                             (high)
. > @huggingface/transformers@4.2.0 > onnxruntime-node@1.24.3 > adm-zip@0.5.17  (high)
```

수정본(`sharp@0.35.4` · `adm-zip@0.6.0`)은 있지만 **부모가 선언한 범위 밖**이다 —
transformers 는 `sharp ^0.34.5`, onnxruntime-node 는 `adm-zip ^0.5.16` 을 선언하는데
**0.x 의 캐럿은 minor 를 넘지 않는다.**

### 2-2. "Prisma 6 → 7" — 7 로 올려도 안 빠진다

`@prisma/config@7` 도 여전히 `deepmerge-ts@7.1.5` 를 **정확한 버전으로 고정**한다.
major 를 올려도 취약본이 그대로 따라온다.

```bash
npm view @prisma/config@7 dependencies   # → "deepmerge-ts": "7.1.5"
```

**그래서 Prisma 7 은 이 취약점과 무관해졌다.** 공유 DB 를 건드리는 유일한 항목이라 미루고
있었는데, 애초에 그 경로가 답이 아니었다.

### 2-3. 셋 다 같은 유형이었다 — 범위 초과 override

| 경로 | 부모 선언 | 수정본 | 건 키 |
|---|---|---|---|
| `transformers > sharp` | `^0.34.5` | 0.35.4 | `sharp@0.34: ^0.35.0` |
| `transformers > onnxruntime-node > adm-zip` | `^0.5.16` | 0.6.0 | `adm-zip@0.5: ^0.6.0` |
| `@prisma/config > deepmerge-ts` | `7.1.5` 고정 | 8.0.2 | `deepmerge-ts@7: ^8.0.0` |

**교훈**: "major 업그레이드가 필요하다" 는 판정은 **부모의 최신 버전이 그 의존성을 어떻게
선언하는지**까지 확인해야 성립한다. 부모를 올려도 같은 핀이 따라오면 그 업그레이드는 헛수고다.
확인 명령은 한 줄이다 — `npm view <부모>@<목표major> dependencies`.

## 3. 이번에 세운 검증 방법

### 3-1. 범위를 넘기는 override 는 게이트가 검증해 주지 않는다

부모가 "이 버전은 안 된다" 고 선언한 조합을 강제로 만드는 것이라, `lint`/`test`/`build` 가
통과해도 그 부모의 실제 사용 경로가 깨져 있을 수 있다. **그 경로를 직접 굴려야 한다.**

**`sharp`(네이티브 모듈)** — 유닛 테스트가 임베더를 모킹해서 바이너리가 안 맞아도 초록불이
나온다. `LocalEmbedder` 를 그대로 호출해 변경 전후를 대조했다.

처음에는 문장 하나로 재고 이 결과를 "임베딩 공간이 같으니 재색인 불필요" 로 적었다.
**리뷰에서 그 일반화가 지적됐고 타당했다** — 표본 하나의 일치는 그 입력의 출력만 말해 준다.
그래서 표본을 축별로 늘리고, 값이 무엇으로 결정되는지를 코드·lock 으로 따로 확인했다.

**(1) 표본 20건 — 축을 갈라 세웠다.** 입력 10개 × `passage`/`query` 두 종류, 배치로 한 번에
넣어 배치 경로까지 태웠다. 축은 언어(한/영/혼합) · 길이(1글자 / 토큰 상한 초과 / 빈 문자열) ·
문자(특수기호 · 숫자 · 이모지 · 전각) · 규약(`passage:` 접두어 중복)이다.

비교 항목은 차원 · L2 노름(소수점 10자리) · 성분 합 · 앞 3개 · 뒤 3개다.
**20건 전부 완전 일치했다**(`diff` 무출력).

**(2) 값을 계산하는 것은 이 PR 에서 안 바뀌었다.** lock diff 를 전수로 보면 바뀐 것은
`@img/sharp-*` 플랫폼 바이너리와 `@emnapi/runtime`, 그리고 `adm-zip`·`deepmerge-ts` 뿐이다.
**추론 엔진 `onnxruntime-node` 는 1.24.3 그대로**이고 모델(`Xenova/multilingual-e5-small`)도
같은 id 의 같은 캐시다.

**(3) 다만 `sharp` 는 텍스트 경로에서도 적재된다 — 이건 내 예상과 달랐다.**
`process.report().sharedObjects` 로 확인하니 임베딩 한 번에
`sharp-darwin-arm64-0.35.4.node` 와 `libvips-cpp.8.18.6.dylib` 이 올라온다(transformers 가
모듈 로드 시점에 import 한다). 즉 **"이미지 전용이라 텍스트 경로엔 관여하지 않는다" 는 말은
틀렸다.** 관여하는 방식이 다를 뿐이다 — 값 계산에는 안 쓰이지만 로드는 되므로, 바이너리가
안 맞으면 **값이 조용히 달라지는 게 아니라 임베더가 통째로 죽는다.** 스모크 테스트가
막아 주는 것이 바로 그 경우다.

**증명되지 않은 것도 적어 둔다.** 위 셋으로도 "모든 입력에 대해 출력이 같다" 는 증명은 아니다.
표본 20건과 "엔진·모델 불변" 이라는 구조 근거를 합쳐 **재색인이 필요할 근거가 없다** 고
판단한 것이고, 전량 동일성을 확인한 것은 아니다. 값이 달라졌다면 episodic memory 를 통째로
다시 만들어야 했으므로, 이 판단의 잘못은 검색 품질 저하로 나타난다(즉시 실패가 아니다).

**`deepmerge-ts`(Prisma CLI 설정 병합)** — `prisma validate` 와 `prisma generate` 를 전후로
돌려 둘 다 정상인 것을 확인했다. `db push` 는 공유 DB 를 건드리므로 안 돌렸다.

**`puppeteer`** — `StudyDiagramRenderer.render()` 실호출(PNG 4949바이트, 위반 0건, 전후 동일)과
크롤러의 `--block-new-web-contents` launch + `goto`.

### 3-2. 죽은 override 를 세는 자동 검사에는 함정이 있다

override 를 지워도 되는지 보려고 "그 키의 범위에 해당하는 버전이 lock 에 있나" 를 셌더니
**`tmp@0.0` 이 죽은 것으로 나왔다.** 그 키는 0.0.x 를 0.2.7 로 **밀어내는** 것이라 0.0.x 가
없는 게 정상이다. 지웠으면 취약본 0.0.33 이 돌아왔다.

**자기 범위 안에서 올리는 override 와 범위를 넘기는 override 는 이 검사에서 다르게 읽힌다.**
믿을 수 있는 방법은 하나다 — **지우고 `pnpm install` 을 다시 돌려 lock 의 패키지 해석이
바뀌는지 본다.** #503 에서 네 개(`body-parser@1` · `brace-expansion@2` · `fflate@0.8` ·
`glob@10`)를 그렇게 확인하고 지웠다(바뀐 것은 overrides 헤더 4줄뿐이었다). #502 에서는
`basic-ftp@5` 하나를 같은 방법으로 지웠다.

### 3-3. 본문 파서 계약은 프레임워크를 올릴 때 가장 먼저 깨진다

웹훅 HMAC 은 본문이 **문자열 그대로** 컨트롤러에 닿아야 맞는다(`main.ts` 의
`express.text({ type: '*/*' })`). 이 계약은 본문 파서가 Nest 와 Express 사이에 있어서
둘 중 하나를 올릴 때 가장 먼저 깨지는데, **기존 유닛 테스트는 컨트롤러에 문자열을 직접 넘겨
그 사이를 건너뛴다.**

`test/webhook-rawbody.e2e-spec.ts` 를 새로 넣었다. `main.ts` 와 같은 순서로 조립한 앱에 실제
HTTP 요청을 보내, 서명이 맞는지(200)와 본문이 한 글자만 달라도 401 인지를 함께 단언한다.
두 번째가 없으면 첫 번째는 "서명 검증을 아예 안 한다" 로도 통과한다.
`express.text()` 한 줄을 빼고 돌려 두 단언이 실제로 깨지는 것을 확인했다.

**e2e 는 `AppModule` 전체가 아니라 컨트롤러만 띄운다** — 그래서 BullMQ 반복 작업을 건드리지
않는다. 앱 전체 부팅은 돌고 있는 서비스의 스케줄을 지우므로 검증 수단으로 쓸 수 없다.

### 3-4. 리뷰 봇의 diff 예산이 실제 코드 변경을 가린다

#503 에서 이대리 봇이 스스로 밝혔다 — **"diff 가 50,000바이트에서 잘려
`test/webhook-rawbody.e2e-spec.ts` 의 실제 구현과 lockfile 후반부는 미확인"**.
lockfile 이 1,258줄 바뀌면서 리뷰 예산을 먹었고, **정작 새로 넣은 테스트 파일이 리뷰에서
빠졌다.**

**의존성 업그레이드 PR 에서는 lock 이 코드 변경을 가린다.** 같은 PR 에 코드가 섞여 있으면
그 코드는 사실상 리뷰를 못 받는다고 보는 것이 맞다. 나눌 수 있으면 나누고, 못 나누면
그 코드는 스스로 더 강하게 검증해야 한다(위 3-3 처럼 가드를 빼서 깨지는 것까지 확인).

## 4. 이 라운드의 부수 변경

- **Node 하한 `>=22` → `>=22.12.0`** (#502). puppeteer 25 가 요구한다. 이 레포는 `.npmrc` 의
  `engine-strict=true` 때문에 이 선언이 **설치 실패로 강제**되므로, 안 올리면 22.0~22.11 에서
  "왜 막히는지 모를 실패" 가 된다. `.nvmrc` 의 `22` 는 최신 22.x 로 풀려 그대로 뒀다.
- **스택 사실 갱신** — `CLAUDE.md` §0 과 `README` 의 "NestJS 10" → 11, Node 22 → 22.12.
- **NestJS 11 은 Express 5 를 쓴다.** 파괴적 변경 둘(`req.query` 파서, 라우트 와일드카드)이
  이 레포엔 해당 없다 — 컨트롤러 5개 전수 확인, `@Query()`·`req.query` 사용 0건, 라우트가
  전부 리터럴 + `:param`. **HTTP 표면이 작아서 프레임워크 major 가 사건이 아니었다.**
- **`express` 직접 의존성도 ^5 로 함께 올렸다.** 안 올리면 4 와 5 가 같이 깔려 `main.ts` 는
  4 의 `text()` 를, Nest 는 5 의 라우터를 쓰는 상태가 된다.

## 5. 다음에 볼 것

- **override 는 부모가 자기 의존성을 올릴 때마다 다시 봐야 한다.** 특히 이번에 넣은 셋은
  부모 범위를 넘기는 것이라, 부모가 지원 범위를 넓히면 그때 걷어내는 것이 맞다. 방법은
  §3-2 — 지우고 `pnpm install` 후 lock 해석이 바뀌는지 본다.
- **Prisma 6 → 7 은 이제 보안 사유가 없다.** 올릴 이유가 생기면 별건으로 다룬다.
  공유 DB 때문에 세션이 하나일 때 해야 한다.
- 2차 재고 §3 의 나머지는 그대로다 — §3-2(이벤트↔집계 상태의 남은 절반),
  §3-4(콘솔 상태 바 여백), 죽은 `responseUrl` 컬럼 제거.

**표본 하나로 전역 결론을 쓰지 마라.** 이 문서의 §3-1 이 처음에 그랬다 — 문장 하나의 벡터가
같은 것을 근거로 "임베딩 공간이 같다" 를 적었다. 리뷰가 잡았고 타당했다. 고친 방법은 둘이다:
**표본을 축별로 늘리고**(언어·길이·문자·종류), **값을 결정하는 것이 안 바뀌었음을 따로
확인한다**(엔진 버전·모델 id). 그리고 **여전히 증명 안 된 것을 명시**한다. 그 과정에서
"sharp 는 텍스트 경로에 관여하지 않는다" 는 내 전제가 실제로 틀렸다는 것도 드러났다 —
근거를 보강하러 갔다가 전제 하나를 고친 셈이다.
