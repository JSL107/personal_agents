# 라우팅 기억 단축 — 설계와 사전 등록 평가 기준 (2026-11-02)

## 무엇을 하나

라우터 분류기는 분류 전에 `episodic_memory` 에서 비슷한 기록 3개를 찾아 예시로 붙인다. 그런데 저장된
내용은 워커의 **출력 JSON** 이고 검색어는 사용자의 **요청문**이라 형태가 맞지 않는다. 시점 정직 재생에서
정답 담당이 예시 3개 안에 든 경우는 9/43 이었고, UNKNOWN 이 정답인 발화 49건 중 44건에 엉뚱한 예시가
붙었다(2026-11-02 재현 확인). 저장분의 60.6% 가 CODE_REVIEWER 라 예시가 그쪽으로 쏠린다.

분류 정확도는 이미 약 97% 라 목표는 **속도**다. 분류 LLM 호출은 p50 8.9초, 임베딩+DB 검색은 p50 7.6ms 다.
거의 같은 과거 질문이 있으면 LLM 없이 바로 라우팅한다.

1. **저장** — 분류기를 탄 첫 턴 요청이 성공하면 `(정규화한 요청문, 최종 담당)` 을 `kind='routing_example'` 로 저장한다.
2. **검색** — few-shot 예시는 `routing_example` 에서만 찾는다. 기준선 미만은 버리고, 담당마다 1개만 넣는다.
3. **단축** — 직전 대화가 없고, 서로 다른 과거 문장 상위 k개가 모두 유사도 T 이상이며 같은 담당을 가리키면 LLM 을 생략한다.
   env `ROUTER_MEMORY_SHORTCUT_MODE=off|shadow|on`(기본 off). `shadow` 는 판정만 원장에 남기고 LLM 결과로 라우팅한다.

## 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 저장 시점 | 새 AgentRun 이 `SUCCEEDED` 로 끝난 직후. `RoutingContext.onRunSucceeded` 콜백을 `AgentRunService` 가 부르고, 저장 자격 판단은 라우터가 한다 | 비동기 BLOG 도 실제 완료 시점에 불린다. 라우팅 의미가 agent-run 모듈로 새지 않는다 |
| 저장 자격 | `routedVia='classifier'` · 직전 대화 없음 · `routedTo` 가 UNKNOWN 이 아님 · 실제 run 의 `agentType === routedTo` · 원문이 잘리지 않음 | handoff 자식은 이미 `routedVia='hint'` 이고, `/retry-run` 은 라우터를 거치지 않는다. `parentId` 는 대화 후속 턴에도 붙어서 판별 기준으로 쓸 수 없다 |
| handoff 를 넘긴 첫 워커 | 저장한다 | 첫 워커로 보낸 분류 자체는 맞았다. 다음 담당을 정한 건 워커다 |
| UNKNOWN | 저장하지 않는다(소유자 지시) | 오프라인 평가에서 "UNKNOWN 을 거부용 예시로 저장" 하는 변형도 LLM 없이 함께 계산해 보고만 한다 |
| 유사도 | 감쇠 없는 순수 cosine(`EpisodeSearchHit.similarity`). `routing_example` 정렬도 감쇠 없이 | 감쇠를 섞으면 같은 문장의 판정이 날짜에 따라 바뀐다 |
| 임베딩 접두어 | `routing_example` 은 저장과 검색 모두 `query:` | 기존 저장은 `passage:`, 검색은 `query:` 다. 같은 문장도 접두어가 다르면 cosine 이 0.94 안팎으로 떨어져 T 가 작동하지 않는다 |
| 검색 방식 | `routing_example` 은 정확 검색(HNSW 를 타지 않음) | HNSW 인덱스는 모든 kind 가 공유한다. 근사 후보를 먼저 뽑은 뒤 kind 로 거르면 소수 kind 는 결과가 비어 버린다 |
| 정규화 | `<@U…>` 멘션 제거 + 공백 축약 + trim. 저장·검색·백필이 같은 함수를 쓴다 | 원장 원문에 멘션 토큰이 섞여 있다 |
| 중복 | 저장 때는 막지 않는다. 판정 때 같은 문장을 하나로 접은 뒤 k 를 센다. 백필은 `agent_run_id` 로 멱등 | 같은 문장 3벌이 k=3 합의를 위조하는 것이 실제 위험이다. unique 인덱스는 스키마 변경이 필요해 쓰지 않는다 |
| 단축 반환값 | `confidence` 를 비운다. 유사도는 `reason` 과 로그에 남긴다. `routedVia='memory'` | cosine 은 확신도가 아니다. 원장의 `routedConfidence` 의미를 섞지 않는다 |
| 단축 결과의 저장 | 저장하지 않는다(`routedVia` 가 classifier 가 아니므로 자동 제외) | 틀린 단축이 다시 예시가 되는 순환을 막는다 |
| T·k·기준선 | 코드 상수(`routing-memory.policy.ts`). env 로 열지 않는다 | 바꾸면 재평가가 필요한 값이다 |
| knowledge-lint | 중복·모순 점검 쿼리에서 `routing_example` 을 뺀다 | 짧고 비슷한 문장이 본질이라 알림이 부풀고, 모순 판정 LLM 비용이 생긴다 |

## 사전 등록 평가 기준

**이 절은 최종 평가를 돌리기 전에 고정한다.** 이후 기준이나 T·k 를 바꾸면 평가 전체를 다시 한다.

데이터: `~/idaeri-eval/routing-memory-2026-11-02/` 의 발화 115건 중 정답 라벨 101건(`gold.py`, 맥락 의존 14건 제외).

재생: 시점 정직. 발화 i 는 시작 시각 이전에 성공한 run 으로 만든 예시만 본다. 예시 라벨은 정답이 아니라 **당시 시스템이
실제로 낸 담당**이다(정답 누수 방지). 현재 run 과 미래 정보만 뺀다. 같은 문장이 과거에 있었다면 그대로 쓴다. 이 기능의
목표가 바로 그 경우다. 임베딩은 저장소의 `LocalEmbedderAdapter` 로, 판정은 운영 코드의 정책 함수를 그대로 import 해서 한다.

| # | 기준 | 통과선 |
|---|---|---|
| E1 | few-shot 정답 포함률 (정답이 워커인 43건 중 예시에 정답 담당 포함) | ≥ 26/43 (60%). 현행 9/43 |
| E2 | 전체 정확도 (단축 구간 + 나머지 LLM), 반복 2회 각각 | ≥ 98/101 |
| E3 | 단축 처리 비율 | ≥ 9/101 (8% 이상) |
| E4 | 단축 구간 오분류 (UNKNOWN 정답 발화가 단축되면 오분류) | ≤ 1건 |

X 를 처음 제안한 15% 에서 8% 로 내렸다. 설계 검토 때 101건으로 탐색 스윕을 해 보니, 오분류 1건 이하를 지키면서 15% 에
닿는 칸이 없었다(k≥2 기준 최대 약 11%). **이 탐색에 같은 101건을 썼으므로 기준 설정은 이미 데이터를 본 상태다.** 결과
보고서에 이 한계를 그대로 적는다. 독립 검증은 운영 `shadow` 관측으로 한다.

T·k 선택 규칙: T ∈ {0.90, 0.91, …, 0.98}, k ∈ {2, 3}. 조건은 "같은 문장을 하나로 접은 뒤 상위 k개가 모두 T 이상이고
담당이 같다" 이다. E3·E4 를 함께 만족하는 칸 중 **T 가 가장 높은 칸**을 고른다(동률이면 k 가 큰 쪽). 만족하는 칸이 없으면
단축은 기본 off 로 두고 "미달" 로 보고한다. k=1 과 top1-only 조건은 비교용 표로만 낸다.

few-shot 기준선(floor) 선택 규칙: {0.80, 0.85, 0.88, 0.90} 중 E1 을 만족하는 가장 높은 값.

LLM 호출: 이전 조건은 기존 `ab_rep1/2.json`(같은 하네스 `ab.cjs`)을 정답 라벨로 다시 채점해 재현한다(0회). 이후 조건(새
few-shot, 단축되지 않은 발화)은 같은 하네스로 2회 → 최대 202회. 단축된 발화는 LLM 없이 판정 결과로 채점한다.

## 채택하지 않은 대안

- **parentId 로 handoff·후속 턴 거르기** — 대화 후속 턴에도 parentId 가 붙어 단독 발화를 잃는다.
- **handoff 여부까지 확인한 뒤 저장하는 조정자** — 첫 워커로 보낸 분류는 맞았으므로 저장해도 된다. 구조만 커진다.
- **UNKNOWN 을 거부용 예시로 저장** — 오프라인에서는 오분류를 줄이지만 소유자 지시와 충돌한다. 수치만 보고한다.
- **(문장, 담당) unique 인덱스** — 스키마와 수동 인덱스 관리가 늘어난다. 판정 때 접는 것으로 충분하다.
- **T 를 env 로 노출** — 바꿀 때마다 재평가가 필요하다.
- **k=1** — 비율은 크지만 UNKNOWN 정답 발화를 많이 잘못 단축한다.

## 평가 결과 (2026-11-02, 사전 등록 뒤 실행)

사전 등록 절은 17:46 KST 에 고정했다(sha256 `71a1b390…`). 아래는 그 뒤에 돌린 결과다.

| # | 기준 | 결과 | 판정 |
|---|---|---|---|
| E1 | few-shot 정답 포함 ≥ 26/43 | floor 0.80 에서 26/43 (현행 9/43) | 통과 |
| E2 | 정확도 ≥ 98/101, 2회 각각 | 98 · 98 (기준선: few-shot 없음 98·99, 현행 few-shot 98·98) | 통과 |
| E3 | 단축 ≥ 9/101 | 고정 규칙에서 기준을 만족하는 칸 없음 | **미달** |
| E4 | 단축 구간 오분류 ≤ 1 | (E3 와 함께 만족하는 칸 없음) | **미달** |

운영 풀(예시 33건, 직전 대화 없는 성공 실행만) 기준 "서로 다른 문장 상위 k개 모두 ≥ T" 규칙의 단축 건수/오분류:

| T | k=2 | k=3 |
|---|---|---|
| 0.90 | 9 / 2 | 6 / 1 |
| 0.91 | 5 / 1 | 4 / 1 |
| 0.92 | 5 / 1 | 2 / 1 |
| 0.93 | 2 / 0 | 0 / 0 |
| 0.94 | 2 / 0 | 0 / 0 |
| 0.95 이상 | 1 이하 / 0 | 0 / 0 |

오분류는 전부 정답이 UNKNOWN 인 발화(#73 · #114)다. 비교용으로 계산한 변형:

- **1위만 T 이상(top1) 규칙**: k=2·T=0.94 에서 6/0. parent 있는 행까지 넣으면 10/0.
- **UNKNOWN 을 거부용 예시로 저장**: k=2·T=0.91 에서 4/0.

이 변형들은 사전 등록 밖이라 채택 근거로 쓰지 않는다.

결론: few-shot 교체(E1·E2)는 기준을 통과했다. 단축은 기준에 미달해 기본 off 로 둔다. `MEMORY_SHORTCUT_RULE` 은 shadow
관측용 잠정값(T=0.93, k=2: 오분류 0인 칸 중 최다 2/101)이다. 예시가 쌓이면 단축 비율이 오른다. 재평가는 shadow 원장
(`routedMemoryHint` 와 실제 `routedTo` 대조)으로 한다.

LLM 호출: 새 few-shot 202회(응답 실패 0). 기준선은 기존 결과를 다시 채점해 재현했다(0회). p50 9.1~11.7초.
