### 1-1. 최소 창 상태 바 겹침 — 해소가 아니다. 처음엔 잘못 판정했다

**결론부터**: 이 항목은 **아직 남아 있다.** 처음에 "해소" 로 적었는데 그건 **백엔드가 꺼진 채로
굽어서 나온 거짓 음성**이었다. PR 리뷰에서 지적받아 다시 쟀다.

#### 처음에 무엇을 잘못했나

`swift run IdaeriConsole --render ... --size 640x560` 로 굽고 "겹치지 않는다" 고 적었다.
그런데 백엔드가 없으면 스냅샷이 비어서 상태 바가 **가장 짧은 문구**가 된다.

| 조건 | 상태 바 문구 | 결과 |
|---|---|---|
| 백엔드 없음(내가 굽은 것) | `진행 0 · 승인 0 · 쉬는 중 0` | 안 겹침 |
| 사람 24 · 세션 9 | `진행 0 · 승인 0 · 쉬는 중 24 · 내 세션 9(도는 중 5)` | **겹침** |

세션 구간(`· 내 세션 N(도는 중 M)`)은 `lastSyncedSessions` 가 비면 아예 안 붙는다
(`OfficeScene.swift:3372-3378`). 그 한 구간이 바 길이를 거의 두 배로 만든다. 1차 문서가 본
화면은 `쉬는 중 24` 였으니 백엔드가 살아 있었다 — **나는 다른 조건에서 재고, 안 나온 것을
없어졌다고 적었다.**

#### 원인도 틀리게 적었다

"창 최소 폭이 720 으로 바뀌어서" 라고 썼는데 **`windowMinWidth` 는 #229 부터 720 이었다.**
#492 가 바꾼 값이 아니다. 그리고 `--render` 경로는 그 최소 폭을 **적용하지 않는다** —
`renderOfficeScene` 이 `OfficeScene(size: size)` 를 직접 만들기 때문에
(`OfficeSceneRender.swift:29`) 640 을 넘기면 그대로 640 으로 그려진다.

#### 다시 잰 결과

스텁 서버로 사람 24명·세션 N개를 내려 주고 굽었다.

| 창 크기 | 세션 | 상태 바 오른쪽 끝 | 「나 (대표)」 이름표 왼쪽 | 판정 |
|---|---|---|---|---|
| 640×560 | 9 | ~306pt | ~302pt | **겹침** (왕관이 가려진다) |
| 720×560 (앱 최소) | 9 | ~305pt | ~325pt | 안 겹침, 여백 ~20pt |
| 720×560 | 19 | ~316pt | ~325pt | 안 겹침, **여백 ~9pt** |

**앱에서 실제로 겹치지는 않는다** — 앱은 720 밑으로 못 줄어들기 때문이다. 다만 **여백이 한 자릿수
포인트**라, 세션이 늘거나 숫자가 한 자리 길어지면 그대로 넘어간다. 막아 주는 장치가 없다.

`--render` 로 640 을 굽는 것은 앱에서 불가능한 폭이므로, 그 그림 하나로 "앱이 깨졌다" 고
판정해서도 안 된다. 1차 문서의 「회의실 문패를 덮는다」 는 재현되지 않았다 — 문패는 상태 바보다
한참 아래(y 기준 130px 남짓)에 있어 바가 아무리 길어져도 닿지 않는다.

### 1-2. `state.changed` 말풍선 — PR #496

`console.type.ts` 의 `state.changed` payload 에 `bubble` 을 추가하고, 문구 조립을
`bubbleForActiveRun()` 한 곳으로 모아 스냅샷 경로와 이벤트 경로가 같은 값을 내게 했다.

**시도했다가 되돌린 것이 하나 있다 — 이게 이 항목에서 가장 값진 기록이다.**

문구를 이벤트가 싣게 됐으니 화면 쪽 우회(상태 변경마다 스냅샷 재조회)를 지워도 될 것처럼
보였다. 실제로 완료·구버전만 남기고 좁혔는데, 외부 리뷰가 회귀 두 건을 지적했고 코드에서
확인하니 둘 다 맞았다.

1. **이벤트는 런 한 건, 화면은 그 사람 전체의 집계다.** `deriveAgentState` 는 열린 승인 >
   활성 런 > 마지막 종료 순으로 하나를 고른다. 승인이 열린 채 새 런이 시작되면 이벤트는
   `IN_PROGRESS`, 집계는 `AWAITING_APPROVAL` 이다. 재조회가 그 어긋남을 정정하고 있었고,
   좁히면 그 정정이 사라진다.

   **2초는 정정 시간이 아니라 최소 호출 간격이다.** `resyncAfterStateChange` 는 직전 재조회로부터
   2초가 안 지났으면 **요청을 버리고 재시도를 예약하지 않는다.** 그 창에 걸리면 정정은 다음 30초
   주기까지 안 온다 — 최악은 2초가 아니라 30초다. 승인 대기 회귀의 영향을 셀 때 이걸 2초로
   적으면 과소평가가 된다.
2. **`resyncSnapshot()` 끝에 `resyncBriefing()` 이 붙어 있다.** 재조회를 건너뛰면 대표
   브리핑의 실패 건수·할 일 갱신까지 함께 건너뛴다.

**교훈**: 우회를 걷어낼 때는 "그 우회가 무엇을 고쳐 주고 있었나" 를 전수로 세어야 한다.
주석에 적힌 이유(여기서는 말풍선)가 그 코드가 하는 일의 전부가 아니다. 특히 `resyncX()`
류처럼 **다른 갱신을 꼬리에 달고 있는 함수**는 이름만 보고 판단하면 안 된다.

**이벤트↔집계 불일치는 절반만 막았다.** PR 리뷰(codex · 이대리 봇 둘 다 같은 곳을 짚었다)를
받아 클라이언트 스토어에 가드를 넣었다 — 상태가 종료로 바뀌는데 그 사람에게 안 끝난 런이
남아 있으면 적용하지 않는다.

**승인이 열린 경우는 일부러 안 막았다. 이유가 대칭이 아니다.**

- 종료를 막으면 남은 런이 끝날 때 **또 다른 종료 이벤트가 와서** 저절로 회복된다.
- 승인이 열린 동안 온 `IN_PROGRESS` 를 막으면, 그 런은 이미 시작했으므로 **다시 보내 주는
  이벤트가 없다.** 승인이 닫혀도 상태가 안 돌아오고 30초 주기 스냅샷까지 기다려야 한다 —
  지금보다 나빠진다.

**교훈**: 이벤트를 드롭하는 가드는 "그 이벤트가 다시 올 기회가 있나" 를 먼저 봐야 한다.
재발행되는 이벤트(종료)는 막아도 되고, 한 번뿐인 이벤트(시작)는 막으면 그 자리에 구멍이 난다.

### 1-3. 취약점 — 운영 7건 그대로, 개발 21건 신규

21건 떠서 전체는 28건이 됐다. **1차 문서가 기준을 「권고 vs 경로」로만 갈랐는데, 실제로는

| 기준 | 1차(09-08 오전) | 2차(09-08 오후) | PR #497 이후 |
|---|---|---|---|
| 전체 · 경로 | 7 | **28** | **7** |
| 전체 · 권고 | 7 | **28** | **7** |
| 운영(`--prod`) · 경로 | 7 | 7 | 7 |

**인용할 때 축 두 개를 함께 적는다** — 「운영/전체」와 「권고/경로」. 셋 다 다른 값이 나올 수

### 1-4. 원격 브랜치 — 조사는 끝냈고, 삭제는 안 한다

**사용자 판단으로 원격 브랜치는 지우지 않기로 했다.** 조사 결과만 기록으로 남긴다.

원격 heads **266개**(main 포함). `git branch -r --merged origin/main` 은 82개만 잡는데,
**이 레포는 squash 머지라 머지된 브랜치도 조상 관계가 끊긴다** — 이 명령은 판정 근거로 못 쓴다.

브랜치마다 PR 상태를 조회해 이렇게 갈렸다.

| 분류 | 개수 |
|---|---|
| PR 머지 완료 + 머지 뒤 push 없음 | **248** |
| PR 머지 완료지만 **머지 뒤에 push 가 있음** | **9** |
| PR 이 아예 없음 | 2 |
| PR 이 닫혔고 미머지 | 3 |
| 진행 중(OPEN) | 3 |

**두 번째 줄이 이 조사의 핵심이다.** PR 상태만 보고 지우면 머지 뒤에 얹은 커밋이 함께
사라진다(이 레포에서 실제로 세 번 재발한 유형이다).

#### 판정 방법 — 커밋 시각으로 세면 틀린다

처음엔 **브랜치 tip 의 커밋 시각**과 PR `mergedAt` 을 비교해 8개를 골랐다. **이 방법은
새는 곳이 있다** — 머지 전에 만들어 둔 커밋을 머지 뒤에 push 하면 tip 의 커밋 시각이
`mergedAt` 보다 **앞**이라, "머지 뒤 push 없음" 쪽으로 잘못 들어간다. 커밋 시각은 만든
시각이지 올린 시각이 아니다.

**맞는 방법은 SHA 대조다.** `gh pr list --json headRefOid` 는 그 PR 이 머지될 당시의 head
SHA 를 준다. 지금 브랜치 tip 이 그 값과 다르면 머지 뒤에 무언가 올라간 것이다.

```bash
gh pr list --head "$b" --state all --json number,state,mergedAt,headRefOid
git rev-parse "origin/$b"
```

**이 방법으로 다시 세니 8개가 아니라 9개였다** — `refactor/slack-handler-port-phase-6` 이
시각 방식에서 새고 있었다. 목록은 이렇다.

`feat/autopilot-knowledge-lint` · `feat/episodic-memory` · `feat/office-visual-pass` ·
`feat/v3-router-manager-pattern` · `feat/vacation-calculator` ·
`fix/conversational-reply-di-and-drop-gemini` · `fix/episodic-docs-sync` ·
`fix/intent-classifier-bot-state-question` · `refactor/slack-handler-port-phase-6`

#### 여기서 막힌 것

그 9개의 머지 뒤 커밋이 실제로 main 에 반영됐는지는 **판정하지 못했다.** 시도한 방법과 왜
안 되는지:

- `git log main..branch` — squash 라 브랜치 커밋이 전부 "미반영" 으로 나온다. 무용.
- `git cherry` — squash 가 patch-id 를 바꾼다. 무용.
- `git diff main branch -- <해당 파일>` — main 이 그 뒤 3개월 치 움직여서, 차이가 나도
  그게 미반영 때문인지 이후 변경 때문인지 갈라지지 않는다(실제로 수천 줄 차이가 나왔다).

**다음에 판정하려면** `headRefOid..tip` 구간의 커밋을 하나씩 열어 그 내용이 지금 main 에
있는지 읽는 수밖에 없다(9개 × 1~4 커밋이라 감당 가능한 양이다).

**로컬 부산물 하나** — `refs/remotes/origin` 이라는 이름 없는 stale ref 가 하나 있다.
`git branch -r` 이 이것 때문에 원격보다 1개 많게 센다(267 vs 266). 원격에는 없는 로컬
찌꺼기라 지워도 원격에 영향이 없다.

## 3. 진짜 남은 것

### 3-1. 슬래시 블로그 발행 카드의 30분 만료 (1차 §3-2 에서 이관, 그대로)

슬래시로 만든 블로그 발행 카드는 `responseUrl` 을 들고 24시간 TTL 을 쓴다
(`publish-notion-draft.usecase.ts:88·241`). Slack `response_url` 은 30분 만료라, 30분이 지나
누르면 카드 상태는 DB 에 반영되지만 슬랙 메시지 갱신만 조용히 실패한다. 저녁 자동 경로처럼
채널 좌표(`channelId`/`messageTs`)를 함께 저장하면 해소된다.

### 3-2. 이벤트 상태와 집계 상태가 갈린다 — 절반 남음 (신규 · 잠복)

`state.changed` 는 런 한 건의 상태를, 스냅샷은 그 사람 전체의 집계(`deriveAgentState` —
열린 승인 > 활성 런 > 마지막 종료)를 낸다.

PR #496 이 **겹친 런** 쪽은 클라이언트 가드로 막았다. **승인이 열린 채 새 런이 시작되는 쪽은
그대로다** — 막으면 오히려 나빠져서 안 막았다(§1-2 의 교훈).

근본 해소는 발행 시점에 집계를 계산하는 것이고, 그러려면 `AgentRunService.execute` 가 매
발행마다 열린 승인과 그 agentType 의 다른 활성 런을 조회해야 한다. 런 하나의 라이프사이클만
아는 자리라 그 조회를 붙이는 것이 이 항목의 실제 비용이다.

### 3-4. 최소 창 상태 바가 대표 이름표에 닿을락 말락 한다 (1차 §3-1 계승)

측정값은 §1-1 에 있다. 앱 최소 창(720×560)에서 상태 바 오른쪽 끝과 「나 (대표)」 이름표
왼쪽 사이 여백이 **세션 9개일 때 ~20pt, 19개일 때 ~9pt** 다. 지금은 안 겹치지만 막아 주는
장치가 없어서, 세션이 더 늘거나 숫자가 한 자리 길어지면 그대로 넘어간다.

상태 바 문구는 `OfficeScene.updateCompanySummary`(`OfficeScene.swift:3365~`) 가 만들고,
세션 구간(`· 내 세션 N(도는 중 M)`)이 붙으면서 길이가 거의 두 배가 된다. 고칠 자리는 그
함수 하나다.

**이번에 안 고친 이유**: 다른 세션이 콘솔에서 작업 중이고, 특히 Swift 테스트 등록부
(`ConsoleCoreTests/main.swift`)를 함께 고치고 있어 충돌 지점이 겹친다.

## 4. 이 문서를 어떻게 쓰나

1차 문서 §5 를 그대로 잇는다. 덧붙일 것 셋:

- **재현 조건이 코드 상수면 먼저 읽어라.** 스냅샷에 적힌 창 크기·임계값이 그 사이 바뀌면
  같은 인자로 굽어도 같은 화면이 아니다(§1-1 의 720 vs 640).
- **우회를 걷어낼 때는 그 우회가 고쳐 주던 것을 전수로 세어라.** 주석에 적힌 이유가 전부가
  아니고, 꼬리에 다른 갱신을 달고 있는 함수가 있다(§1-2).
- **취약점 건수는 축이 셋이다** — 운영/전체 · 권고/경로. 셋 다 적어야 재현된다(§1-3).
- **없는 것을 확인할 때는 조건을 먼저 갖춰라.** 백엔드가 꺼진 채로 화면을 굽고 "안 겹친다" 고
  적었는데, 상태 바가 가장 짧은 문구였을 뿐이었다(§1-1). 거짓 음성은 결함보다 오래 산다 —
  다음 사람이 그 문장을 믿고 안 본다.
- **머지 여부는 시각이 아니라 SHA 로 대조하라.** 커밋 시각은 만든 시각이지 올린 시각이 아니라,
  머지 전에 만든 커밋을 머지 뒤에 push 하면 시각 방식이 그것을 못 잡는다. `headRefOid` 와
  현재 tip 을 비교하는 것이 정확하다(§1-4 — 이 차이로 8건이 9건이 됐다).
- **`resyncAfterStateChange` 의 2초는 정정 시간이 아니라 최소 호출 간격이다.** 그 창에 걸린
  요청은 버려지고 재시도되지 않아, 최악의 정정 시간은 30초다(§1-2).
- **이 문서를 새로 만들 때는 `git add -f` 가 필요하다.** `.gitignore:78` 에 `docs/` 가 있어서
  `docs/superpowers/plans/` 아래 새 파일은 `git add -A` 로 안 잡힌다. 기존 plan 파일들은 전부
  force-add 로 들어와 있다. `git status` 가 조용해서 커밋한 줄 알고 넘어가기 쉽다 — 실제로
  이 문서를 쓸 때 한 번 걸렸다.
