확장 → 화면·문서** 순서가 자연스럽다. 아래 4단계는 그 의존 관계를 반영한 것이다.

### 2️⃣ 망가진 모듈

**확인된 미해결 2건**

**(a) 단일 run 32분 지연 → 중복 실행 12~21회**

BullMQ 워커의 잠금 시간은 `worker-options.constant.ts:23`에서 계산된다.

```
lockDuration = MODEL_ROUTER_WORST_CASE_MS(360초) + 컨텍스트·발송 예산(90초) = 450초 (7.5분)
```

한 번의 실행이 32분 걸리면 이 7.5분을 크게 넘겨 잠금이 풀리고, BullMQ가 같은 작업을 "멈춘 것"으로
보고 재처리한다. 그래서 중복 실행이 발생한다. **32분이 왜 걸리는지가 아직 밝혀지지 않았고**, #182는
원인 추적을 위한 계측(파싱 실패 진단 + 모델 호출 소요시간 보존)만 넣은 상태다. 잠금 시간을 늘리는
대증요법은 의도적으로 보류했다 — 원인을 모른 채 늘리면 증상만 가린다.

**(b) 저녁 블로그 발행 승인 알림 유실**

승인 카드의 유효기간(TTL)은 24시간인데 Slack이 주는 응답 URL(`responseUrl`)은 30분이면 만료된다.
이 불일치 때문에 승인 알림이 사라진다. `fix/evening-blog-preview-ttl` 브랜치(7/6)가 관련 작업이나
방치 상태다.

**기본 OFF라 사실상 안 도는 기능 5종** (`.env.example` 기준)

`SUBCONSCIOUS_ENABLED` · `SESSION_DISPATCH_ENABLED` · `AUTOPILOT_PREFERENCE_LEARNING_ENABLED` ·
`PREFERENCE_PROFILE_INJECTION_ENABLED` · `STOCK_MONITOR_ENABLED`

> 실제 `.env`는 이 세션에서 읽기가 차단돼 현재 켜져 있는지 확인하지 못했다. 착수 시 먼저 확인해야 한다.

## 3. 의존 관계

```
0단계 재고 정리 ──┬─→ 1단계 고장 수리 ──┐
                  │                      ├─→ 3단계 화면·문서
                  └─→ 2단계 인터페이스 ──┘

5단계(컨벤션)는 각 단계의 완료 게이트로 흡수
7번(워크플로우)은 1~3단계를 굴리며 나온 마찰을 근거로 개선
```

**왜 이 순서인가**

- **0단계가 먼저인 이유** — 미머지 브랜치 22개와 worktree 4개가 살아 있어, 무엇을 하든 충돌 위험이
  있다. 판정 없이 새 작업을 얹으면 나중에 머지 지옥이 된다.
- **3단계가 마지막인 이유** — 1·2단계에서 기능이 바뀌면 화면과 문서도 다시 손봐야 한다. 먼저 하면
  두 번 일한다.
