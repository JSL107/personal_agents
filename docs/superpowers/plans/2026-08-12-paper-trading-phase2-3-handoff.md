## 3. 2단계 — 종목 마스터와 지표 스크리너

### 왜 필요한가

사용자 요구는 "종목 제한 없음"인데 **그대로는 구현 불가능하다.** 상장 종목 약 2,800개의 시세·지표를 프롬프트에 담을 수 없다. 그래서 LLM 앞단에 결정론적 압축 계층이 필수다.

```
2,800종목 → [지표 계산·정렬] → 상위 20~50종 → LLM 판단(3단계)
             ↑ 코드가 계산                    ↑ 여기서만 LLM
```

이 계층이 사용자가 요청한 "각종 지표 분석"의 실체이며, 스크리닝과 추천 근거 양쪽에 쓰인다.

### 선행 과제 (이것부터 정하지 않으면 즉석에서 아키텍처를 발명하게 된다)

**(1) `DailyPrice` 소유권 승격.** 현재 `DailyPrice`를 읽고 쓰는 곳은 `src/agent/stock/infrastructure/stock-monitor.repository.ts` 하나다. 스크리너는 2,800종목 × 200봉을 매번 재조회할 수 없어 반드시 이 표를 읽어야 하는데, 그러면 `paper-trading`이 주가 감시 모듈에 의존하게 된다 — 피어 기능 모듈 간 역의존이다. `Ticker`/`DailyPrice` 접근을 `src/market-data/infrastructure/` 아래 공유 repository로 올리고 `StockMonitorRepository`가 그것을 쓰게 바꾼다.

**(2) 장중 시세 구분 장치.** 1단계는 `DailyPrice`에 아무것도 쓰지 않는 것으로 문제를 회피했다. 2단계에서 스크리너가 쓰기 시작하면 그 회피가 무효가 된다.

문제의 실체: 휴장 판정이 달력이 아니라 **"저장된 마지막 시세 날짜 == 방금 받은 날짜"** 비교다(`src/agent/stock/domain/stock-anomaly.ts`의 `isMarketClosed`). `DailyPrice(tickerId, 오늘)` 행이 미리 생기면 그날 그 종목의 감시 판정이 통째로 건너뛰어지면서 원장에는 성공으로 남는다. **실제로 발생한 사고**이고 로드맵 §E에 기록돼 있다(2026-08-06 오전 11:30 수동 적재 → 그날 17:10 감시가 재판정 없이 저장된 알림 복구 경로로 빠졌다. 에러도 로그도 없다).

"이 시세가 장 마감 후 것인가"를 구분하는 장치를 2단계 선행으로 만들어야 한다.

**(3) `Ticker.market` 조달.** `Ticker`의 유니크 키는 `@@unique([market, code])`이고 `market`은 required다. 그런데 종목코드만으로는 KOSPI/KOSDAQ를 채울 수 없다. DART 고유번호 파일에 시장 구분이 있는지 **미확인**이다. 없으면 다른 소스를 정해야 한다.

여기에 1단계가 남긴 한계가 얽힌다 — 토스 경로는 `market='KR'`, Yahoo 경로는 `'KOSPI'|'KOSDAQ'`를 넣어서 **같은 종목이 두 행으로 존재할 수 있다**(`schema.prisma`의 `Ticker` 주석이 이 이원화를 명문화). 1단계는 `market='KR'` + `tossSymbol IS NOT NULL`만 쓰기로 정했고, 세부 시장(세율 계산용)은 저장하지 않는다. 2단계에서 전종목을 적재할 때 이 축을 어떻게 통일할지가 핵심 설계 판단이다. `PaperTrade`에 적용 시장을 기록하면 "이 거래의 세금이 왜 이 값인가"를 사후 재구성할 수 있다.

### 걸어 들어가는 벽 (실측 확인됨)

**200봉 조용한 절단.** `toss-market-data.client.ts`의 `count = Math.min(days, 200)` 후 `bars.slice(-days)` — `fetchDailyBars(symbol, 250)`은 **에러 없이 200봉**을 돌려준다. 52주(약 250거래일) 지표를 그대로 구현하면 **40주 고가를 52주 고가라 부르는 지표**가 조용히 만들어진다. MA120도 여유가 거의 없다.

**페이지네이션은 존재하는데 클라이언트가 안 쓴다.** `/candles`에 `before`(ISO 8601 상한)와 응답의 `nextBefore` 커서가 있다. 현재 클라이언트는 `symbol/interval/count/adjusted`만 보낸다. 250봉 이상은 클라이언트 확장이 전제다.

**`/prices` 배치를 안 쓴다.** 현재가는 `GET /api/v1/prices`에 `symbols`(복수)로 여러 종목을 한 번에 받을 수 있다(`lastPrice`). 전종목 스윕에서 종목당 1회 호출과 비용 차이가 크다.

**레이트 리미터가 단일 인스턴스 순차 가정이다.** 220ms 고정 간격이 인스턴스 필드(`lastRequestAt`)에 걸려 있고, 코드 주석이 직접 경고한다: "동시 호출은 경쟁할 수 있다 … 종목 수 증가나 병렬화 시 엔드포인트별 token bucket으로 교체한다." 2,800종목 스윕은 다른 시세 소비자와 겹치는 것이 확정적이다.

**DART 호출 한도 미확인.** 2,800종목 재무 수집이 한도를 넘으면 후보군에만 재무를 조회하도록 순서를 바꿔야 한다. 그리고 OpenDART는 **호출 IP를 등록해서 쓴다** — 발급 화면에 "IP 변경 신청은 담당자 승인(1~2영업일) 후 처리"라고 적혀 있다. 유동 IP면 막힐 수 있으니 실제로 붙일 때 등록 IP와 현재 IP를 먼저 확인해야 한다.

### 지표 후보

이동평균(5/20/60/120)과 배열, 거래량 급증 배수, 기간 수익률(1/3/6개월), 52주 고가 대비 위치, 변동성. 로드맵 §D가 같은 데이터를 요구하므로 **수집 기반을 공유하고 중복 구현하지 않는다**.

## 4. 3단계 — 추천과 자동 가상 매매

### 범위

스크리너 후보 + DART 공시·재무 + 뉴스를 근거로 **장투·단타를 분리 추천**하고, 전략별 계좌에 자동 체결한다. 체결은 §5-(2)의 "다음 거래일 시가" 규칙을 따른다(1단계에 `PaperOrder` 표가 이미 있다 — 판단 시각 `decidedAt`과 판단 데이터 날짜 `dataAsOf`를 기록해 사후 증명이 가능하다).

LLM을 쓰므로 에이전트 등록 체크리스트가 적용된다. 1단계에서 `AgentType.PAPER_TRADE`를 이미 추가했으니 추천 에이전트를 별도 타입으로 둘지 재사용할지 결정해야 한다.

### 반드시 지켜야 할 설계 판단

**추천 품질을 계좌 수익률로 재지 마라.** 계좌 수익률은 자본 투입률에 좌우된다 — 장투가 자금 100%를 넣어 +10%면 계좌 +10%, 단타가 10%만 넣어 +50%면 계좌 +5%다. 계좌 수익률은 장투 우위라고 말하지만 추천 자체의 수익성은 단타가 높다. 보유 기간이 다른 것도 같은 문제다(30일 +5% vs 3일 +3%).

두 층으로 측정한다.
- **추천 단위**: 고정된 진입·청산 규칙 아래 기간별 순수익률, 같은 기간 벤치마크 초과수익, 적중률, 최대 미실현 손실·이익
- **포트폴리오 단위**: 같은 초기자본·포지션 사이징 아래 시간가중수익률, 변동성, 최대 낙폭, 회전율과 순비용

**전략별 계좌를 분리하라.** 같은 종목을 두 전략이 사면 `PaperPosition.avgPrice`가 하나로 합쳐져 전략별 실현손익 귀속이 불가능해진다 — 장투 1주@100, 단타 1주@200 보유 상태에서 1주@150을 팔면 통합 평균가로는 손익 0이지만 실제로는 어느 전략 물량을 팔았느냐에 따라 +50 또는 -50이다. 스키마는 이미 계좌 다중화를 허용한다(`PaperAccount.name` unique).

**as-of 데이터를 보존하라.** 나중에 수집한 정정공시·수정 재무제표를 과거 판단 입력으로 쓰면 당시 알 수 없던 정보가 섞인다. 공시의 실제 공개 시각, 원본 버전, 수집 시각, 판단 입력 스냅샷을 보존하고, 사후 재계산 시 입력을 최신 데이터로 교체하지 않는다. 유니버스도 날짜별 상장 상태를 써야 한다 — 현재 상장 종목만으로 과거를 재평가하면 상장폐지 종목이 빠져 성적이 부풀려진다.

**전략별 horizon이 필요하다.** `DEFAULT_HORIZON_DAYS = 5`를 장투에 그대로 쓰면 장투가 구조적으로 불리해진다.

**프롬프트·지표 변경 시점을 기록하라.** 성적을 보며 규칙을 계속 손대면 지나간 구간에만 맞는 규칙으로 수렴한다. 성적 구간을 나눠 읽을 수 있어야 한다.

**분할·배당을 정식 처리하라.** 1단계는 감지 가드(정수비 근처 급변 → 스냅샷 미적재)만 두고 미뤘다. 2단계에서 DART 공시로 이벤트를 받아 `PaperCorporateAction`과 현금 원장으로 처리한다(분할 시 `quantity × ratio`, `avgPrice ÷ ratio`, 배당은 지급일 기준 세후 현금 적립). 입출금·배당이 생기면 `cashBalance = seedAmount + Σ거래` 불변식이 무효가 되므로 append-only 현금 원장이 필요하고, 수익률 기준도 시간가중수익률로 전환해야 한다.

## 5. 1단계에서 실측한 사실 (재조사하지 말 것)

| 항목 | 실측값 |
|---|---|
| 토스 `/candles` 응답 | `openPrice`·`highPrice`·`lowPrice`·`closePrice`·`volume` 전부 존재, 값은 문자열. `interval`은 `1m`·`1d`만 |
| 토스 `/prices` | `symbols`(복수) 파라미터, `lastPrice` 반환 |
| `Ticker.tossSymbol` (국내) | 6자리 KRX 종목코드와 동일 |
| 증권거래세 (2025-12-29 체결분부터) | KOSPI 0.20%(거래세 0.05% + 농특세 0.15%), KOSDAQ 0.20%(농특세 없음), KONEX 0.10%. **매도에만** |
| 그 이전 | KOSPI·KOSDAQ 0.15%, KONEX 0.10% |
| 유관기관 제비용 | 0.0036396%, **매수·매도 양쪽** |
| 토스 위탁수수료 | 0.015%로 두었으나 **공식 고지로 미확정**. `trade-cost.ts` 상수 한 곳에 모여 있다 |
| 실제 시세 (2026-08-11) | 삼성전자 239,000원, KODEX 인버스 1,126원 |
| **장 마감 후 종가 갱신** | 19:05에 239,500원이던 삼성전자가 19:12에 239,000원. 시간외 단일가 추정. **17:40 값이 최종인지 미확정** |

마지막 항목이 2·3단계에 갖는 의미: 성적의 기준 시점이 흔들린다. 17:40이 정규장 종가로 정확한 것인지, 아니면 아직 확정 전인지 판정해야 한다. 시간외 거래가 활발한 종목으로 17:40·18:30·19:30 세 시점을 비교하면 답이 나온다.

## 6. 함정 (이 세션에서 실제로 밟았거나 밟을 뻔한 것)

- **`docs/`는 gitignore다.** worktree를 만들면 스펙·계획이 따라오지 않는다. 새 worktree에서 작업하려면 문서를 복사해야 한다(이미 tracked인 파일은 따라오지만 새로 만든 것은 `git add -f`가 필요하다).
- **codex는 git write와 DB 접근을 못 한다.** 샌드박스가 worktree의 `index.lock`을 못 잡고 localhost:5434도 막는다. `db:push`·`prisma:generate`·커밋은 메인 세션이 대행한다.
- **codex에게 계획을 주면 모순을 잡아낸다 — 그걸 활용하라.** 이 세션에서 3번 멈추고 보고했고 3번 다 정확했다. "계획이 코드와 어긋나면 구현하지 말고 멈추고 보고해라"를 프롬프트에 명시하면 잘못된 구현을 미리 막는다.
- **`pnpm test -- <경로>` 필터가 안 먹는다.** jest를 2단계로 돌리기 때문이다. `pnpm exec jest src/paper-trading`을 쓴다.
- **포트·enum 확장은 다른 mock을 깨뜨린다.** 전체 `pnpm test`로만 잡힌다. `Record<AgentType, …>`는 누락 시 컴파일 실패, `agent-registry`/`agent-contract` spec은 enum과 양방향 집합 일치를 강제한다.
- **autopilot 그룹 맨 앞에 새 항목을 넣지 마라.** 스케줄러가 그룹 첫 항목 id로 env 키를 만들어, 기존 override가 조용히 무시되고 코드 기본값으로 되돌아간다. standalone이면 안전하다.
- **`AppModule`을 부팅하는 스크립트를 만들지 마라.** 스케줄러가 부팅 시 CRON을 재등록해 돌고 있는 서비스의 예약 작업을 건드린다. 필요한 모듈만 담은 전용 module로 `createApplicationContext`한다.
- **cron만으로 실행되는 기능은 실증 검증 입구가 없다.** 1단계는 `scripts/paper-trade.ts evaluate`를 추가해 해결했다 — autopilot task와 **같은 usecase**를 부르므로 검증 경로가 production 경로와 같다. 2·3단계 스크리너·추천도 같은 입구를 함께 만들어라.
- **`db:push`는 synchronize다.** 다른 worktree가 이후 구 스키마로 push하면 새 테이블이 사라진다. DB는 모든 worktree가 공유한다(PostgreSQL@5434).
- **`.env` 파일 읽기는 권한 차단돼 있다.** 값 확인이 필요하면 코드가 읽게 하거나 사용자에게 물어야 한다.
