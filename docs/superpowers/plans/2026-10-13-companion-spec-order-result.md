# [기존 테스트] 선택 순서 — 파일별 증감 줄 수로 (2026-10-13)

> 날짜 스냅샷이다. 이후 갱신하지 않는다. 앞선 기록: `2026-10-13-review-goal9-result.md` §4-4·§5 「선택 규칙의 한계」.

## 한 줄 결론

`[기존 테스트]` 블록의 선택 순서를 잘린 diff 에서 센 줄 수가 아니라 `pulls.listFiles` 의 파일별 증감으로 정하게 했다.
diff 가 상한에서 잘려도 순서가 경로순으로 무너지지 않는다. 다만 이 변경의 동기였던 #412 는 이것으로 풀리지 않고, 풀어야 할
오탐도 지금 main 에서는 재현되지 않는다. 함께 시험한 「문서를 diff 맨 뒤로」는 효과가 없고 정탐 1건을 잃어 넣지 않았다.

## 1. 변경

- `PullRequestDetail.changedLinesByFile`(필수): `getPullRequest` 가 이미 페이지네이션하는 `pulls.listFiles` 의
  `additions + deletions` 를 파일별로 담는다.
- `review-pull-request.usecase.ts`: 선택 가중치는 API 값을 우선하고, diff 로 센 값은 목록이 `CHANGED_FILES_MAX` 로
  잘린 파일의 보충으로만 쓴다. `selectCompanionSpecs` 자체는 바꾸지 않았다.
- 재생(`summarizeDiff`): 같은 필드를 diff 에서 센다. 재생은 카드 시점 head 를 쓰므로 현재 PR 의 API 값을 쓰면 그 뒤
  커밋이 섞인다. `--full-file-list` 면 잘리지 않은 diff 라 운영과 같다.

## 2. #412 — 이 변경으로 풀리지 않는 이유

블록만 다시 만든 결과(모델 호출 없음, 카드 571 의 head `fcc51400`, `--full-file-list` 와 같은 구성):

| | 실림 / 생략 | `backend-role.filter.spec.ts` |
|---|---|---|
| 변경 전 | 5 / 20 (경로순) | 빠짐 |
| 변경 후 | 6 / 19 (증감순) | 빠짐 |

- 변경 전 값은 앞선 기록 §4-4 와 같다.
- 이 PR 은 `job-feed` 모듈을 새로 만든 PR 이라 거의 모든 파일이 신규다. 후보 가중치(짝 소스와 spec 자신의 증감 중 큰 값)로
  세면 해당 spec 은 25개 중 10위이고, 예산 60KB 에는 6개가 들어간다. 이 파일만 끌어올릴 규칙은 #412 에 맞춘 과최적화다.
- 더 근본적인 사실: 지금 main(120KB, 테스트를 뒤로)에서도 #412 의 모델 입력은 `.env.example`·`README.md`·
  `docs/env-catalog.md`·계획 문서 앞부분뿐이고 소스 코드는 한 줄도 없다. 짝 테스트를 실어도 그 테스트가 다루는 코드를 모델이 못 본다.

## 3. 카드 571 이 나온 경로

카드 생성 시점(2026-08-28)의 상한은 50KB, 파일은 경로순이었다(재배열과 120KB 는 #737, 10-07). 그때 입력도 문서뿐이었고,
180KB 계획 문서 `docs/superpowers/plans/2026-08-27-job-feed.md` 안의 spec 초안(diff 기준 30,043~37,057 바이트)이 상한
안에 들어 있었다. 초안에는 중복 태그 케이스가 없고, 실제 spec 146행에는 있다. 모델은 계획 속 초안을 실물로 읽고 실제 spec
경로에 "검증되지 않는다"를 단 것이다. "spec 이 잘려 본문을 못 봤다"는 앞선 설명보다 이쪽이 정확하다.

## 4. 문서를 diff 맨 뒤로 — 시험하고 넣지 않음

넘친 diff 를 동작 코드 → 테스트 → 문서(`.md`·`.mdx`) 순으로 자르는 안이다.

### 4-1. 오프라인 집계 (카드 줄이 상한 안에 드는가)

라벨 카드(FIXED·REJECTED) 그룹 177개 중 120KB 를 넘는 19개, 카드 25장. 두 번 독립으로 세어 같은 값을 얻었다.

| 문서를 뒤로 보내면 | 카드 |
|---|---|
| 새로 보이는 소스 | 3장, 모두 REJECTED (133 · 570 · 572) |
| 밀려나는 문서 | 4장 — FIXED 2장(1301 · 1351, spinoff `INTEGRATION.md`), REJECTED 2장(1314 · 1449) |

### 4-2. 재생 (같은 25장, `--trials 2`, `--full-file-list`, 모델 호출 76회)

기준선은 이 브랜치의 순서 수정을 포함한 현행 절단이고, 후보는 거기에 문서 뒤로만 더했다.

| | 현행 | 문서 뒤로 |
|---|---|---|
| 오탐 재발 | 3/28 (10.7%) | 4/28 (14.3%) |
| 정탐 유지 | 9/22 (40.9%) | 8/22 (36.4%) |
| 응답 시간 중앙값 | 83초 | 101초 |

- 두 지표 모두 회차 범위가 겹쳐 효과는 측정되지 않았다.
- #412 의 오탐 3장(570 · 571 · 572)은 양쪽 모두 0/2 다.
- 1301(`INTEGRATION.md` 정탐)은 2/2 → 0/2 로, 문서가 잘려 나가며 실제로 잃었다.
- 그 밖의 오르내림은 잡음으로 본다. 문서가 0바이트라 두 실행의 입력이 같은 #3093 의 1306 도 1 → 2 로 움직였다.

## 5. 남는 것

- #412 유형(계획 문서 속 코드 초안을 실물로 읽는 오탐)은 지금 main 에서 재현되지 않는다. 다시 보이면 문서 순서가 아니라
  "문서 안의 코드 블록은 실제 파일이 아니다"를 다루는 쪽을 먼저 본다.
