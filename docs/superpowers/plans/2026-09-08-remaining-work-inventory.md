## 3. 진짜 남은 것 — 고쳐야 하는 것

### 3-1. 최소 창에서 상태 바가 상단 밴드 문패를 덮는다 (신규)

`--render --size 640x560` 에서 좌상단 상태 바(`진행 0 · 승인 0 · 쉬는 중 24 …`)가
**회의실 문패와 대표 이름표 위에 겹쳐** 그려진다. 960×820 에서는 상태 바가 검은 여백에
있어 겹치지 않는다 — 도면이 커져 위로 올라오는 최소 창 구간에서만 나온다.

**이번에 고치지 않았다.** 다른 세션이 `fix/office-scale-small-window` 브랜치에서 콘솔
배율·창 크기를 작업 중이고(`OfficeViewMetrics.swift`·`main.swift`·`OfficeScene.swift` 등
8개 파일 수정 중), 같은 파일을 건드리면 충돌한다. 그 작업과 함께 보는 편이 맞다.

### 3-2. `state.changed` 이벤트가 말풍선 문구를 싣지 않는다 (그대로)

`console.type.ts:129-132` 의 payload 는 아직 `agentType` 과 `state` 뿐이다. 앞 문서 이후
15일 동안 바뀌지 않았다. 화면이 상태 변경 직후 스냅샷을 한 번 더 당겨오는 우회가 그대로다.

**이번에 고치지 않은 이유는 §3-1 과 같다** — 근본 수정은 백엔드 이벤트 계약과 콘솔 파서를
함께 바꾸는 일인데, 콘솔 쪽이 다른 세션과 겹친다.

여기에 앞 문서 §2-2 에서 이관된 것이 붙는다: **슬래시로 만든 블로그 발행 카드는
`responseUrl` 을 들고 24시간 TTL 을 쓴다**(`publish-notion-draft.usecase.ts:88·241`).
Slack `response_url` 은 30분 만료라, 30분이 지나 누르면 카드 상태는 DB 에 반영되지만
슬랙 메시지 갱신만 조용히 실패한다. 저녁 자동 경로처럼 채널 좌표를 함께 저장하면 해소된다.

### 3-3. 의존성 취약점 — 55건 → **7건** (이번에 처리)

앞 문서는 prod 46건이었고 이번 실측 시작값은 55건(high 23 · moderate 27 · low 5)이었다
— **요약(경로) 기준이다.**
**`pnpm.overrides` 로 취약본만 끌어올려 7건(high 4 · moderate 3)까지 줄였다.**

부모 패키지의 major 는 하나도 올리지 않았고, 5중 게이트(`lint:check` · `build` · `test` ·
`docs:check` · Swift 테스트)로 회귀가 없음을 확인했다.

**다만 "같은 major 안" 이라는 말은 두 가지 뜻으로 갈린다 — 처음에 그걸 혼동해 사고가 났다.**
아래 §3-4 에 따로 적었다.

**아래 표는 「권고(advisory) 기준」이다.** `pnpm audit` 은 두 가지로 센다 — `advisories` 는
권고 객체 수, 요약 줄(`N vulnerabilities found`)은 **경로(findings) 수**다. 같은 권고가 여러
의존 경로에 걸리면 요약이 더 크다. 이번 값은 이렇다.

| 기준 | 변경 전 → 후 | 감소 |
|---|---|---|
| 요약(경로) | 55 → 7 | **48** |
| 권고(advisory) | 51 → 7 | **44** |

**아래 표의 합계 44 는 권고 기준이라 요약 기준 48 과 다르다.** 어느 쪽도 틀린 값이 아니지만
섞어 쓰면 재현이 안 되므로, 인용할 때 기준을 함께 적는다.

| 강제한 키 | 빠진 건수(권고 기준) |
|---|---|
| `undici@7` ^7.28.0 | 12 |
| `fast-uri@3` ^3.1.4 | 7 |
| `ip-address@10` ^10.3.1 | 4 |
| `hono@4` ^4.12.34 · `@hono/node-server@1` ^1.19.15 | 5 |

**키는 전부 `패키지@major` 형태다** — 이유는 §3-4.

**세 가지가 실측으로만 드러났다.**

- `ip-address` 는 처음에 `^10.1.1` 로 걸었더니 10.2.0 이 뽑혔는데, **그 버전을 겨냥한 별도
  권고가 3건 더 있었다.** 권고 하나의 `patched_versions` 만 보고 정하면 같은 패키지의 다른
  권고를 놓친다 — 강제한 뒤 다시 `audit` 을 돌려 확인해야 한다.
- `body-parser` 는 **1.x 와 2.x 두 라인이 동시에 설치돼 있다.** 한쪽만 강제하면 다른 쪽
  부모가 깨지므로 pnpm 의 범위별 키(`body-parser@1` / `body-parser@2`)로 각 라인의 수정본을
  따로 걸어야 한다.
- **키를 대상 major 로 한정하지 않으면 다른 major 를 쓰던 소비자까지 덮는다.** `js-yaml` 을
  `"js-yaml": "^4.2.0"` 로 전역에 걸었더니, `js-yaml ^3.13.1` 을 선언한
  `@istanbuljs/load-nyc-config@1.1.0` 의 해석이 **3.14.2 → 4.3.2** 로 바뀌었다. audit 대상은
  4.1.1 하나뿐이었으므로 3.x 를 덮을 이유가 없었는데, 전역 키라 자동으로 따라온 것이다.
  `"js-yaml@4"` 로 한정하니 3.x 는 3.15.2(부모 범위 안)로 남고 감축 효과는 그대로였다.
  **이 사고는 게이트가 못 잡는다** — 그 소비자가 jest coverage 경로라 테스트는 전부 초록이었고,
  `codex` 리뷰가 lock 파일을 읽고 찾아냈다.

**남은 7건은 전부 major 업그레이드가 필요하다 — 그래서 이번 범위 밖이다.**

| 남은 것 | 현재 → 수정 | 무엇을 올려야 하나 |
|---|---|---|
| `file-type` ×2 (moderate) | 20.4.1 → ≥21.3.2 | major. NestJS 계열이 물고 있다 |
| `@nestjs/core` (moderate) | 10.4.22 → ≥11.1.18 | **NestJS 10 → 11.** `CLAUDE.md` §0 이 "NestJS 10" 을 스택 사실로 박아 둔 값이다 |

해소에 필요한 하한은 11.1.18 이다 — 최신값을 목표로 삼으면 필요 없는 major 를 한 단계 더
건너뛰게 된다.

넷 다 이 레포의 스택 정의를 바꾸는 일이라(특히 `CLAUDE.md` §0 이 못 박은 NestJS 10 ·
Prisma 6) 경로별로 나눠 별도 계획으로 다뤄야 한다.

### 3-4. override 의 「같은 major」 는 두 가지 뜻이다

`pnpm.overrides` 로 취약 패키지를 끌어올릴 때 "같은 major 안이라 안전하다" 는 말은 두 축을
섞고 있다. 둘을 갈라 봐야 한다.

1. **대상 패키지의 major** — 7.24.7 → 7.28.0 처럼 자기 major 안에서 올라가는가. 이건 지켰다.
2. **소비자 전체의 major** — 그 패키지를 **다른 major 로 쓰던 소비자**가 함께 덮이는가.
   전역 키는 여기서 샌다(위 `js-yaml` 사례).

**그래서 키에 대상 major 를 붙였다**(`undici@7` · `qs@6` · `js-yaml@4` …). 부수 효과가 하나 더
있다 — 나중에 부모가 자기 의존성의 major 를 올리면 전역 override 가 그것을 계속 옛 major 로
붙잡는데, 한정 키는 그 major 에만 걸리므로 자동으로 비켜난다.

**그리고 override 는 부모가 선언한 범위를 넘긴다 — 이건 피할 수 없다.** Express 4.22.1 이
`qs ~6.14.0` 을 선언했는데 실제로는 6.16.0 이 붙는다. 취약본을 밀어내려면 당연한 결과지만,
"부모가 허용한 범위 안" 이라고 설명할 수는 없다. 실제로 붙은 버전은 아래와 같다.

| 패키지 | 변경 전 → 후 |
|---|---|
| `undici` | 7.24.7 → 7.29.1 |
| `qs` | 6.14.2 · 6.15.1 → 6.16.0 |
| `ip-address` | 10.1.0 · 10.2.0 → 10.7.0 |
| `hono` | 4.12.31 → 4.13.7 |
| `basic-ftp` | 5.2.1 → 5.3.1 |
| `js-yaml` | 4.1.1 → 4.3.2 (3.x 는 3.15.2 로 유지) |
| `multer` | 2.1.1 → 2.3.0 |
| `body-parser` | 1.20.4 → 1.20.6 · 2.2.2 → 2.3.0 |
| `fast-uri` | 3.1.0 → 3.1.7 |
| `@hono/node-server` | 1.19.14 → 1.19.17 |
| `protobufjs` | 7.6.4 → 7.6.6 |
| `uuid` | 11.1.0 → 11.1.1 |
| `fflate` | 0.8.2 → 0.8.3 |

lock 부수 변경은 `content-type@2.1.0`·`type-is@2.1.0` 추가(body-parser 2.3 을 따라감),
`side-channel` 1.1.1 상승(qs 를 따라감)이다. 무관한 패키지 변경이나 다운그레이드는 없다.

**부모가 자기 의존성을 올릴 때마다 override 의 필요 여부를 다시 봐야 한다.** 취약본이 이미
빠졌는데 override 가 남아 있으면, 그때부터는 보안 조치가 아니라 버전 고정 장치가 된다.

## 5. 이 문서를 어떻게 쓰나

앞 문서 §6 을 그대로 잇는다. 덧붙일 것 하나:

- **`pnpm audit` 을 근거로 쓸 때는 강제한 뒤 다시 돌려라.** 권고 하나의 `patched_versions` 로
  버전을 정하면 같은 패키지의 다른 권고가 남는다(§3-3 의 `ip-address` 사례). "몇 건 줄었나" 는
  반드시 재측정값으로 적는다.
- **건수를 인용할 때 「권고 기준」인지 「경로 기준」인지 함께 적어라.** 두 값이 다르다
  (이번엔 51 vs 55). 기준을 안 밝히면 표의 합계와 총계가 어긋나 보여 검증이 막힌다.
