# 매일 오는 Slack 메시지 — 무엇을 보여 줄지 방향

작성 2026-10-08. 설계서 `docs/superpowers/specs/2026-09-18-slack-message-readability-design.md` §7-1
("매일 오는 메시지에서 실제로 알고 싶은 것")에 대한 답을 받아 방향을 정한 문서다. 구현은 하지 않았다.
같은 날 코드·데이터 대조로 초안을 한 번 고쳤다 — 무엇이 바뀌었는지는 §7.

> **한 줄 요약.** 하루 평균 16통(중위)을 **아침 한 통 + 저녁 한 통 + 승인 카드 + 사건 알림**으로 줄인다.
> 아침은 맨 윗줄에 "할 일 N — 종류별 개수"를 띄우고, 그 아래에 투자·회사·공부를 한 줄씩 둔다.
> 저녁은 "한 일 나열"을 버리고 결과 한 줄과 내일로 넘어가는 것만 남긴다.

---

## 1. 무엇이 문제였나 — 사용자 답

설계서 §1은 "슬랙 메시지를 안 읽게 된다"를 길이 문제로 보고 출발했다. 이번에 직접 물어보니 순서가 달랐다.

| 질문 | 답 |
|---|---|
| 언제·어디서 보나 | 출근길 아침 폰, 업무 중 PC, 퇴근 후 폰. 세 시간대 모두 본다 |
| 무엇을 열어 보나 | 비서실·PO 검토, 저녁 묶음·카드, 모의투자·주식, 공고·공부. **종류별로 건너뛰는 것은 없다** |
| 안 읽히는 느낌 (순위) | ① 너무 많아 대충 넘긴다 → ② 봐도 남는 게 없다 → ③ 뭘 해야 할지 모른다 → ④ 길어서 끝까지 못 읽는다 |

종류마다 열어 보기는 한다. 문제는 **양**이고, 그다음이 **내용**(매일 비슷함)과 **행동 연결**이다.
길이는 맨 뒤다. 설계서가 보류해 둔 3-1·3-2(길이 줄이기)가 우선순위가 낮았다는 것과도 맞는다.

같은 날 발송 길이 분석(`2026-10-08-slack-send-analysis.md`)도 같은 방향을 가리킨다. 채널 본문 중위는 168자로
짧다. PR 리뷰 스윕과 콘솔 경로 task 를 뺀 채널 발송(`push`·`card`)은 9-19 ~ 10-07 KST 기준
**하루 중위 16통, 범위 8~21통**이다(`logs/slack-send.jsonl`, 19일).

10-07 하루(17통)를 성격별로 나누면 이렇다.

| 성격 | 통 | 예 |
|---|---:|---|
| 내가 눌러야 진행됨 | 3 | 블로그 후보·경력 후보·GitHub 발행 카드 |
| 문제 생김 | 2 | 포트폴리오 응답 없음, 발행 실패 |
| 판단 재료 | 2 | 비서실, PO 검토 |
| 결과 보고 | 7 | 모의투자 4, 주식 모니터링 2("새 경보 없음"), 저녁 묶음 |
| 읽을거리 | 3 | 오늘의 공부 2, 공고("조건에 맞는 공고가 없습니다") |

꼭 손대야 하는 것은 3통이고, "아무 일 없음"을 알리는 메시지도 섞여 있다.

## 2. "할 일"의 정의

사용자가 고른 범위는 셋이다.

- **승인 카드** — 블로그·경력·GitHub 발행처럼 눌러야 진행되는 것
- **고쳐야 할 장애** — 발행 실패, 연속 응답 없음
- **내가 정할 것** — 새 공고에 지원할지 등

**회사 PR 대응은 넣지 않는다.** 비서실·PO 검토의 "먼저 볼 PR"은 할 일이 아니라 참고 한 줄로 내려간다.

## 3. 결정한 것

### 3-1. 아침 08:30 — 할 일 맨 위 + 나머지 한 줄씩

목업 세 개 중 ①을 골랐다. 스레드로 숨기는 ②는 스레드가 잘 열리지 않는다는 분석 결과(긴 글자의 60%가
스레드에 있다) 때문에 뺐다.

**첫 줄에는 개수와 함께 종류를 적는다.** 승인 대기·장애·신규 공고가 모두 없던 날은 19일 중 하루(10-02)뿐이라,
"손댈 것 없음"은 거의 뜨지 않는다. 매일 "할 일 N"만 보이면 그 숫자가 곧 배경이 되므로, 3초 판단의 근거는
숫자가 아니라 종류여야 한다.

```
☀️ 10/8(목) 아침 — 할 일 5 · 승인 3 · 장애 1 · 공고 1

✋ 할 일
• 승인 대기 3장 — 블로그 후보(95점) · 경력 반영 13건 · GitHub 발행  [보기]
• 🔴 장애  포트폴리오 사이트 응답 없음 · 2일째 (429)  [로그]
• 공고 1건 — 하마랩 Back-End 경력, 지원할지?  [공고]

어제 · 오늘
• 투자  장기 -0.06% · 오늘 시가 매수 1 · 매도 3 예정
• 회사  먼저 이것부터 — PR #3668 비속어 필터 규칙과 검증 근거 기록
• 공부  Agent Middleware Lifecycle Hooks · 15분  [읽기]
```

할 일이 없는 날은 첫 줄이 `☀️ 10/9(금) 아침 — 손댈 것 없음` 이 되고 나머지 세 줄만 남는다.

이 한 통이 **비서실·아침 브리핑·PO 검토(13시)·새 공고·공고 갭 분석·오늘의 공부**와 **전날 23시 포트폴리오 발행 보고**를 대신한다. 포트폴리오 발행 결과는 "어제" 아래 한 줄(예: `• 포트폴리오  발행 완료 · 이력서 감사 약함 2건`)로 들어간다. 단 두 가지는
지켜야 한다.

- **PO 검토의 판정 버튼을 살린다.** PO 검토를 콘솔 경로로 보내면 `po_first_action` 판정 버튼이 조용히
  사라진다 — 콘솔 항목 타입에 `runVerdicts` 가 없다(`autopilot.orchestrator.ts:211-217`, `:255-262`).
  그래서 PO 검토는 콘솔이 아니라 **아침 묶음의 일원**으로 옮기고, 버튼은 아침 메시지의 스레드 첫 댓글로
  붙인다(저녁 회고 판정과 같은 방식, `:510-535`).
- **아침 묶음에 `morning-briefing` task 를 남긴다.** 저녁 `pm_plan` 판정 버튼은 오늘 아침 발송 원장에
  `itemKinds` 로 `morning-briefing` 이 있어야 붙는다(`evening-retro-publish.autopilot-task.ts:427-433`).
  없으면 에러 없이 버튼만 빠진다.

### 3-2. 저녁 — 결과 한 줄 + 넘어가는 것

목업 세 개 중 (가)를 골랐다. 저녁 카드는 대부분 다음 날 아침에 눌리지만(분석 §3-③: 19시 카드 중
다음 날 8~10시 처리 19건, 당일 7건), 퇴근 후에도 폰으로 보므로 하루를 닫는 신호는 남긴다.

```
🌙 10/7(수) 마감 — 내일 아침 할 일 3
• 오늘    PR 17건 머지 (+8,770 / -853) · 핵심: 자연어 오실행 방지  [worklog]
• 투자    장기 -0.06% · 손절 1 · 내일 시가 매수 1 · 매도 3 예정
• 넘어감  승인 카드 3장 · 포트폴리오 장애 (2일째)
```

그 아래로 승인 카드는 지금처럼 따로 온다. 카드(`previews`)와 저녁 회고 판정 버튼(`runVerdicts`)은 요약
문구와 별개 필드로 발송되므로, 요약을 한 줄로 줄여도 같이 사라지지 않는다(`autopilot.orchestrator.ts:283-287`).
Work Reviewer 4조각 묶음의 나머지(오늘 한 일 나열 · 정량 근거 · PO 평가 · 발행 후보 전체)는 원장에 남고
`worklog` 링크로 연다.

### 3-3. 따로 보내는 것은 셋뿐

| 따로 보냄 | 조건 | 지금 빈도 (9-18 ~ 10-08) |
|---|---|---|
| 승인 카드 | 지금처럼. 아침 메시지에도 "승인 대기 N장"으로 다시 모인다 | 하루 평균 2.1장(카드 있는 날 기준 2.5장) |
| 투자 사건 | 손절 체결, 새 경보가 **있을 때만**. "새 경보 없음"·"0건 청산"은 보내지 않는다 | 손절 메시지 4통(청산 있던 날 2일), 경보 있던 날 3일 / 14거래일 |
| 장애 | **처음 한 번만** 따로. 그다음부터는 아침 할 일 줄에 `N일째`로만 남는다 | 포트폴리오 장애 메시지 6통 / 3주 |

장애는 지금도 하루 1통 수준이라 이 규칙으로 줄어드는 건수는 크지 않다. 효과는 건수보다 "할 일 줄에
몇 일째인지가 보인다"는 쪽에 있다.

### 3-4. 빼는 것

- 비서실의 "① 완료 243건 · CODE_REVIEWER …" 같은 처리 건수 나열과 "판단 근거" 스레드
- Work Reviewer의 "오늘 한 일" 나열, 정량 근거·PO 평가·발행 후보 전체 스레드
- 주식 모니터링 "새 경보 없음", 장중 손절 "0건 청산", 공고 "조건에 맞는 공고가 없습니다"

빠진 것은 지워지지 않는다. 발송 관문(#742·#748)이 만든 대로 `slack_delivery` 원장에 전문이 남고,
콘솔(`src/console/interface/console.controller.ts` 의 `GET /deliveries` 등)에서 볼 수 있다.

## 4. 성공 기준 — 2주 뒤(2026-10-22께) 확인

1. **하루 채널 메시지 6통 이하** — 아침 1(전날 23시 포트폴리오 발행 결과 포함) + 저녁 1 + 카드 평균 2~3 + 사건 0~1. 지금은 중위 16통이다.
   포트폴리오 발행 보고(21일 중 13일 발송)를 아침에 흡수하지 않으면 같은 집계 기준으로 7통이 된다.
   `logs/slack-send.jsonl` 의 `push`·`card` 를 날짜별로 센다(스윕·콘솔 경로 제외 기준 동일하게).
2. **승인 카드의 다음 날 정오(KST) 전 처리 비율 90% 이상 유지** — 지금 91.4%(32/35, 9-18 이후,
   응답 시간 중위 13.6시간). 할 일 목록으로 옮긴 뒤 카드를 놓치기 시작하면 실패다. `preview_action` 으로 잰다.
3. **사용자 확인 한 문장** — "아침 첫 줄만 보고 열지 말지 정할 수 있나?" 2주 뒤 직접 묻는다.

반응·답글 수(`slack_delivery`, #751)는 기준에서 뺐다. 이틀치 기준선이 25통 중 1건이고, 합쳐진 메시지의
반응은 그 안의 모든 task 에 똑같이 더해지는 구조라(`slack-delivery-summary.ts:14-17`) 묶음이 커질수록
"무엇이 읽혔나"를 가를 수 없다.

실패로 볼 신호: 아침 메시지의 "할 일" 아래가 다섯 줄을 넘는다, 판정 버튼(`pm_plan`·`po_first_action`)이
안 나간 날이 생긴다, "손댈 것 없음"인 날에 장애가 묻혀 있었다.

## 5. 구현 범위 추정

다파일 변경이다. 사용자가 꼽은 1순위가 "양"이므로 건수를 줄이는 것부터 한다. 다만 정보가 콘솔에만 남는
공백을 피하려고 **건수 줄이기와 아침 한 통을 한 PR 로** 묶는다.

| 순서 | 내용 | 주요 지점 | 비고 |
|---|---|---|---|
| PR 1 | 아침 한 통 + 아침 쪽 건수 줄이기 | `secretariat` · `morning-briefing` · `po-shadow`(morning 그룹으로), `secretariat.digest.ts`, `secretariat.formatter.ts` | 할 일 조회: 승인 대기는 `FindAllOpenPreviewsUsecase`, 신규 공고는 `ListNotifiablePostingsUsecase` — 둘 다 기존 함수. 투자·공고·공부·포트폴리오 줄은 아침 task 가 데이터를 직접 읽어 만들고, 원래 task(job-feed·job-feed-gap·study-*·portfolio-publish)는 Slack 요약을 내지 않는다 |
| PR 2 | 저녁 마감 + 저녁 쪽 건수 줄이기 | evening 그룹 4개 task, stock-monitor·paper-score·paper-recommend·paper-intraday-stop | 사건 없는 회차는 #748 방식(`skip: true` + `emptyReason` → `SUPPRESSED/EMPTY`)으로 원장에만 남긴다. **경로 표를 회차별로 바꾸는 새 장치는 필요 없다** |
| PR 3 | 시각 조정 | `autopilot.playbook-defaults.ts`, `study-brief-cron.type.ts` | 아래 표 |
| (선택) PR 4 | 장애 "N일째" | `portfolio-warmup.autopilot-task.ts`, 열린 장애 조회 신설 | 지금도 하루 1통 수준이라 우선순위 낮음 |

**투자·공고 task 를 아침·저녁 묶음에 task 째로 넣지 않는다.** 같은 `digestGroup` 안의 cron 항목은 실행 시각이
같아야 하고, 다르면 부팅 검사에서 막힌다(`autopilot.playbook.ts:575-610`). 체결 09:30 · 장마감 17:40 ·
추천 19:30 을 한 시각에 맞출 수 없으므로, 묶음 task 가 그 결과를 원장에서 읽어 한 줄로 만드는 쪽이 맞다.

메시지 문구를 고정한 formatter spec 이 11개 파일 있다(`secretariat`·`po-shadow`·`job-feed`·`stock-monitor`·
`paper-*` 등). PR 1·2 에서 같이 고쳐야 한다.

| 모의투자 내일 추천 | 19:30 | 저녁 묶음(19:00)보다 늦어 "내일 예정"을 넣을 수 없다 | 추천을 18:30 으로 앞당긴다. 추천은 계좌 현금을 즉시 읽으므로 장마감 평가(17:40)의 손절 반영 뒤여야 한다 — 50분 간격을 두고, 완료 확인 가드는 두지 않는다 |

  모두 데이터의 종류로 코드가 판정할 수 있다. 분석 보고 §4·§5 가 적은 "(가) 내가 눌러야 할 것만이면 3-2 재검토"는
