## 한 줄 요약

사람이 이대리에게 직접 물었을 때 답이 빗나가는 원인은 네 갈래다. 워커가 질문을 고정 메뉴로 뭉개고, 담당을 못 고른 질문은 이대리가 무엇을 할 수 있는지 모르는 잡담 응답으로 가고, 후속 턴이 직전 턴의 대상(PR 링크)을 잇지 못하고, 실행 결과를 시스템이 아니라 모델이 서술한다. 가정형 문장이 쓰기로 실행되는 경로를 먼저 막고, 실 LLM 질문 eval 로 기준선을 잰 뒤, 네 원인을 차례로 고친다.

### 1-2. 08-27 PR 게시 — 점검 문서 판정 정정

점검 문서는 "게시 미확인으로 모두 막힘"이라 적었으나 1차 출처로 보면 다르다.

| 회차 | 원장 | GitHub 실측 |
|---|---|---|
| 1520 (16:27) | finding 3건 `SUPPRESSED` | 코멘트 없음 |
| 1521 (16:33) | finding 3건 `SUPPRESSED` | 코멘트 없음 |
| 1523 (16:38) | finding 2건 `ACKED` | 07:38:42~47 UTC 이대리 코멘트 5건 게시됨 |

- 자연어 경로는 "게시"라는 말이 없어도 `publish: input.publish ?? true` 다(`code-reviewer.dispatcher.ts:56`). 막은 것은 허용 레포 목록(`PR_REVIEW_INLINE_REPOS`, `publish-policy.ts:24`)이고, 미등재 레포는 조용히 `SUPPRESSED` 로 끝난다. 1523 직전에 목록이 바뀐 것으로 보이나 당시 값은 복원할 수 없다(미확인).
- 응답 본문의 "게시 미확인", "404", "사용자 취소" 는 네트워크가 차단된 리뷰 모델(`codex-cli.provider.ts:246`)이 지어낸 문장이다. 게시 결과(`PublishOutcome`)는 `review-pull-request.usecase.ts:198` 에서 받자마자 버려지고, 사용자에게 가지 않는다.
- 따라서 고칠 것은 둘이다: 링크 없는 후속 지시가 직전 PR 을 잇게 하는 것, 게시 결과를 코드가 결정론으로 알리는 것.

## 2. 목표와 성공 기준

| 기준 | 합격선 |
|---|---|
| 가정·조건 표지가 있는 자연어 원문에서 게이트 없는 쓰기(휴가 등록·취소, 지원 추가·상태 변경, 일정 등록) 실행 | 0건. 코드 가드 + 단위 테스트로 고정 |
| eval holdout(점검 문서 실패 원문) 충족률 | 기준선 대비 개선을 보고하고, 문항별 3회 중 2회 이상 합격을 "충족"으로 센다. 목표 80% 이상 |
| eval 응답에 범용 챗봇 표현("고객사", "타인의 금융정보", 슬래시 명령 안내) | 0건 |
| facts 답의 숫자 | 지어낸 숫자는 코드가 막고 facts 결정론 요약으로 폴백, 사유가 원장에 남는다. 계산의 정답 여부는 eval 로 판정한다 |
| PR 후속 지시 ("게시까지 진행해줘." 류) | 직전 코드 리뷰 턴의 PR 이 하나면 그 PR 로 실행, 둘 이상이면 어느 PR 인지 되묻는다. 응답 끝에 코드가 만든 게시 결과 줄이 붙는다 |
| 3중 green | `pnpm lint:check && pnpm test && pnpm build` |

과최적화 방지: 프롬프트는 튜닝 문항만 보고 고치고, holdout 은 고친 뒤 한 번씩만 돌려 따로 보고한다. holdout 성적을 보고 다시 고쳤다면 그 사실을 보고에 적는다.

## 3. 설계

### 원칙

- 메뉴에 맞지 않는 질문은 워커가 기존 `UNKNOWN` 으로 정직하게 내린다. 새 액션 값은 만들지 않는다.
- 그 질문은 워커가 조회한 사실(facts)과 함께 사실 기반 답변으로 넘긴다. 답에 나온 숫자가 지어낸 것인지는 코드가 검사한다.
- 담당을 못 고른 질문의 대화 답변은 이대리의 기능 목록을 안다.
- 실행 결과(게시 여부 등)는 모델이 아니라 코드가 말한다.

### 답변이 만들어지는 두 경로

| 경로 | 지금 | 바꾼 뒤 |
|---|---|---|
| 분류기가 UNKNOWN | 라우터가 예외 → `router-message.handler.ts:320`·`handle-conversation-turn.usecase.ts:110` 이 `ConversationalReply` 호출 | 호출부는 그대로. `ConversationalReply` 가 기능 목록을 프롬프트에 싣는다 |
| 워커가 UNKNOWN | 워커 고정 안내문, `agentRunId: 0` | 워커가 자기 AgentRun 을 열고 그 안에서 facts 를 조회해 공용 `FactAnswerUsecase` 로 답을 만든다. 답은 그대로 `formattedText` 가 된다 |

워커 UNKNOWN 을 라우터에서 처리하지 않고 워커 안에서 처리하는 이유: 라우팅 근거는 dispatch 스코프에서 **처음 열린 AgentRun** 이 가져가고(`routing-context.ts`), 열린 행이 없으면 dispatch 직후 `routing_no_run` 에 남는다(`idaeri-router.usecase.ts:200-205`). 라우터가 dispatch 뒤에 답을 만들고 AgentRun 을 따로 열면 근거가 `routing_no_run` 과 새 행에 이중으로 갈리거나 빠진다. 워커가 dispatch 안에서 AgentRun 을 열면 기존 규칙대로 그 행이 근거를 한 번만 가져간다. `DispatchOutcome`·`DispatchResult`·라우터·진입점은 바꾸지 않는다.

`FactAnswerUsecase` 는 라우터가 아닌 독립 모듈(`src/fact-answer/`, 의존은 `ModelRouterModule` 뿐)에 둔다. `RouterModule` 이 워커 모듈들을 import 하므로 워커가 라우터 쪽을 참조하면 순환 의존이 된다.

### 기능 목록의 단일 소스

분류기 프롬프트의 `## 분류 후보` 줄(`intent-classifier-system.prompt.ts`)이 지금 유일한 워커 설명이다. 이것을 `워커 → 설명` 상수로 옮기고 분류기 프롬프트는 그 상수로 조립한다. 옮기는 커밋에서는 **조립 결과가 기존 문자열과 바이트 단위로 같은지 단위 테스트로 고정**한다 — 리팩터링 검증용이다. 이후 설명을 바꾸는 변경(예: 3단계의 SCHEDULE 조회)은 별도 커밋에서 바뀐 줄을 명시하고 분류 테스트와 eval 로 검증한다.

`ConversationalReply` 는 같은 상수에서 등록된 dispatcher 의 항목만 싣는다. 설명 문구는 "그 워커가 받는 요청"이고 실제 지원 액션의 보증은 아니므로, 상수에 워커별 "자연어로 할 수 있는 일" 예시를 함께 두고 이것을 대화 답변에 쓴다. 분류기 프롬프트에는 기존 설명만 쓴다.

## 4. 단계별 계획

각 단계는 독립 PR 로 낼 수 있게 자른다.

### 0단계 — 가정형 문장의 쓰기 오실행 가드 (가장 먼저)

- [ ] 가정·질문 표지 상수 하나를 두고 테스트와 공유한다. 넓은 조건 어미(`하면`, `쓰면` 단독)는 평서 등록("면접 보면 상태 바꿔줘")까지 막으므로 넣지 않고, 질문·가정으로 좁힌 표지만 쓴다: `가정`, `라면`, `이라면`, `만약`, `기준이면`, `면 몇`, `면 며칠`, `남아\?`, `맞아\?`, 끝의 `?`. 목록은 대조군 테스트로 범위를 고정한다.
- [ ] 가드는 자연어 dispatcher 에만 둔다. 같은 쓰기 usecase 를 쓰는 슬래시 명령·콘솔 버튼은 명시 입력이라 대상이 아니다.
- [ ] VACATION: 파서 결과가 REGISTER·CANCEL 인데 원문에 표지가 있으면 UNKNOWN 으로 내린다.
- [ ] JOB_APPLICATION: ADD·UPDATE_STATUS 에 같은 가드.
- [ ] SCHEDULE: 직전 턴과 **합친 뒤의** 명령이 REGISTER 이고 이번 원문에 표지가 있으면 등록하지 않는다. 직전 턴 합치기로 가정형 질문이 등록되는 경로를 함께 막는다.
- [ ] 막은 경우의 응답: "질문으로 보여 기록하지 않았다. 기록하려면 '등록해줘'로 말해 달라." 답은 3단계에서 붙인다. 막은 사유(걸린 표지)는 경고 로그와 `DispatchOutcome.output.heldWrite` 에 남긴다. 이 회차는 AgentRun 을 열지 않으므로 원장에는 `routing_no_run` 의 원문만 남고, 사유가 원장에 실리는 것은 3단계(UNKNOWN AgentRun)부터다.
- [ ] 단위 테스트: 워커별 가정형 문장 10개 이상이 쓰기로 실행되지 않음 + 평서형 등록 문장 10개 이상은 그대로 실행됨(대조군).

### 1단계 — 질문 eval 과 기준선

- [ ] `scripts/nl-answer-eval.ts`: Nest 테스트 모듈로 앱을 조립하되 **쓰기 usecase 를 기록만 하는 가짜로 교체**한다(`overrideProvider` — 휴가 등록·취소, 지원 추가·상태 변경, 일정 등록, 블로그 발행, PR 게시 경로). 쓰기 차단은 "DB 를 읽기 전용으로 쓴다"는 약속이 아니라 이 교체로 보장하고, 가짜가 호출된 것을 결과에 기록한다. 분류기·워커 파서·대화 답변은 실 LLM 을 부르고, 조회는 실제 DB 를 읽는다.
- [ ] 결과에는 문항별로 분류 결과, **가드 이전의 파서 원판단**(액션), 가드 이후 실행된 쓰기(가짜 호출), 최종 응답을 남긴다. 파서 원판단을 따로 남기므로 0단계 이후에 재도 "가드가 없었다면 쓰기가 실행됐을 비율"을 기준선으로 복원할 수 있다.
- [ ] 문항 32개 이상, 각 문항은 `{ text, priorTurns?, expect }`. `expect` 는 코드로 채점한다: 기대 워커 집합, 금지 쓰기, 응답에 있어야 할 정규식(예: `4\s*일`), 없어야 할 정규식(`고객사|금융정보|/[a-z-]+ `).
  - 튜닝용 20개: 직접 작성. 5개 메뉴형 워커의 평서 조회·가정형·확인형·비교형·가정형 쓰기·평서 쓰기(대조군), 기능 질문("너 뭐 할 수 있어?").
  - holdout 12개 이상: 점검 문서 실패 원문 그대로. 휴가 3건(10-07 두 턴, 09-15), 자유 서식 정정(09-08), 모의투자 2건("지금은 계좌에대해서 조사할수있어?", "페이퍼 드레이딩 관련해서"), "프롬프트 Rag"(앞 두 턴 포함), PR 후속 2건("게시까지 진행해줘.", "리뷰를 게시하라고", 직전 턴에 PR 링크), "왤캐느려", `#공부` 2건(직전 봇 메시지 포함).
- [ ] 문항당 3회. 수동 실행이며 `pnpm test` 게이트가 아니다. 결과는 문항별 합격 횟수와 실패 원문을 JSON 으로 남긴다.
- [ ] 이후 단계마다 같은 문항으로 다시 잰다.
- 비용: 문항당 LLM 2~3회 × 3회 × 32문항 ≈ 200~300회 호출, 회차당 10~40초. 동시 실행 수를 제한해 한 번에 1시간 안팎으로 본다.

### 2단계 — 대화 답변이 이대리를 알게 한다

- [ ] 기능 목록 상수 추출 + 분류기 프롬프트를 그 상수로 조립(바이트 동일 테스트).
- [ ] `ConversationalReply` 시스템 프롬프트에 등록된 워커의 "자연어로 할 수 있는 일"을 싣는다. 규칙을 바꾼다(덧붙이지 않고 해당 줄을 치환): 사용자가 묻는 것이 목록에 있는 일이면 되묻지 말고 "할 수 있다 + 이렇게 말하면 바로 한다"를 자연어 예시로 답한다(슬래시 안내 금지는 유지). 목록에 없는 일이면 없다고 말한다. 이 봇은 1인 사용자의 개인 봇이며 "고객사"·"타인" 은 없다는 사실을 넣는다.
- [ ] 낡은 자기소개(Node 20 · NestJS 10)를 고친다.
- [ ] 기존 `unresolvedStreak` 방향 전환 분기는 유지한다.

### 3단계 — 워커 UNKNOWN 을 facts 답으로

- [ ] `src/fact-answer/` 모듈에 `FactAnswerUsecase.answer({ text, priorTurns, facts })`. 시스템 프롬프트: facts 와 원문의 숫자만 근거로, 계산은 단계를 보이고, 모르는 값은 지어내지 않는다.
- [ ] facts 는 워커가 **이름 붙은 필드**로 만든다(예: `granted`, `used`, `remaining`, `usages[].days`). 계산이 정해진 값(잔여·사용 합계)은 도메인 계산 결과를 facts 에 넣는다.
- [ ] 숫자 검사(코드)는 지어낸 숫자를 막는 장치로 한정한다: 답의 수치 토큰이 facts 값·원문 숫자·그 둘의 합·차 중 하나인지 본다. 날짜(`YYYY-MM-DD`, `M월 D일`)와 id 는 먼저 떼어 내 날짜·id 끼리만 대조한다. 검사를 통과해도 계산이 맞다는 보증은 아니며, 정답 여부는 eval 로 판정한다. 실패하면 facts 의 결정론 요약(사용법 안내가 아니라 잔여·내역 표)으로 폴백한다.
- [ ] 각 워커의 UNKNOWN 분기는 `agentRunService.execute` 로 자기 AgentRun 을 연다(action `UNKNOWN`, `inputSnapshot.parsedIntent`). 그 안에서 facts 조회 → 답변 → 숫자 검사를 하고 `output = { facts, reply, numberCheck }` 로 정상 종료한다. 답변 생성이 실패하면 facts 결정론 요약으로 답하고 `output.answerError` 를 남긴 채 정상 종료한다(사용자에게는 답이 나갔다). facts 조회 자체가 실패하면 실패로 끝낸다. UNKNOWN 분기는 `preview`·`slackBlocks`·`followUp` 을 채우지 않는다.
- [ ] 단위 테스트: 라우팅 근거가 UNKNOWN AgentRun 에 한 번만 실리고 `routing_no_run` 에 남지 않음, 답변 실패 시 폴백, 숫자 검사(날짜·반차 0.5·여러 건 합계 포함).
- [ ] 워커별 facts 와 파서 수정 (파서는 UNKNOWN 정의 줄을 치환해 가정·확인·비교·정정 요청을 UNKNOWN 으로 명시하고, `priorTurns` 를 싣는다):
  - VACATION: 현재·직전 회기 부여·사용·잔여, 사용 내역. 기존 BALANCE AgentRun 을 열지 않도록 repository + 잔여 계산을 직접 쓴다. 기존 BALANCE·REGISTER·CANCEL 경로의 `inputSnapshot` 에도 `parsedIntent` 를 남긴다.
  - JOB_APPLICATION: 지원 현황 목록.
  - CAREER_MATE: 최신 프로필 요약(없으면 없음).
  - SCHEDULE: `ListSchedulesUsecase` 를 dispatcher 에 연결해 0단계에서 막은 질문과 조회 질문("이번주 일정 뭐 있어?")에 다가오는 일정 facts 로 답한다. 분류기의 SCHEDULE 설명에서 "조회 요청은 보내지 않는다"를 바꾸는 것은 별도 커밋으로, 바뀐 줄과 분류 테스트·eval 결과를 함께 남긴다.
  - BLOG_PUBLISH: 원문이 발행 요청이 아니면(질문 표지) 발행 usecase 를 부르지 않고 UNKNOWN 으로 내린다. facts 는 초안 목록 — 발행 usecase 안의 목록 조회를 꺼내 쓸 수 있을 때만. 꺼내는 비용이 크면 facts 없이 기능 목록 답으로 둔다.

### 4단계 — PR 후속 지시와 게시 결과

- [ ] 코드 리뷰 dispatcher: 원문에서 PR 참조를 못 찾으면 `input.priorTurns` 중 **`agentType === CODE_REVIEWER` 인 턴**에서만 PR 참조를 모은다(대화 메모리는 본문을 자르지 않고 저장하고, 실패한 턴의 사용자 원문도 남긴다 — `router-message.handler.ts:279·303·362`). 서로 다른 PR 이 하나면 그 PR 로 실행하고, 둘 이상이면 어느 PR 인지 되묻는다. 하나도 없으면 실패하되 안내문은 슬래시 사용법 대신 "어느 PR 인지 링크를 같이 보내 달라"로 바꾼다. 다른 워커 턴의 링크는 쓰지 않는다 — `publish` 기본값이 true 라 잘못 고르면 다른 PR 에 코멘트가 달린다.
- [ ] 게시 결과: `ReviewPullRequestUsecase` 가 `publishFindingsService.publish` 의 반환값(`PublishOutcome`)을 버리지 않고 결과에 싣는다. 허용 목록 판정은 이미 있는 순수 함수 `isRepoAllowed` 로 같은 자리에서 구해 함께 싣는다(새 조회 없음). 게시 예외는 지금처럼 리뷰를 유지하되 "게시 실패"로 싣는다.
- [ ] dispatcher 가 결정론 한 줄을 붙인다: 게시 N건 / 허용 목록 밖이라 게시하지 않음(설정 `PR_REVIEW_INLINE_REPOS`) / 이미 게시된 지적과 중복 / 게시 실패 / 지적 없음. "지적 없음"은 게시 성공과 구분해 쓴다.
- [ ] 리뷰 시스템 프롬프트에 "게시 여부는 시스템이 따로 알린다, 서술하지 않는다"를 넣는다.
- [ ] 단위 테스트: CODE_REVIEWER 턴의 PR 승계, 원문 참조 우선, 복수 PR 되묻기, 다른 워커 턴 링크 무시, 게시 결과 갈래별 문구. 콘솔 진입(`handle-conversation-turn.usecase.ts`)도 같은 `priorTurns` 를 넘기는지 확인한다.

## 5. 리스크와 미해결

- **표본 부족**: 사용자는 1명이고 자연어 진입은 하루 몇 건이다. 효과 판정은 eval 로 하고, 운영 원장은 실패 원문을 holdout 에 보태는 용도로 쓴다.
- **파서 판단 의존**: 읽기 쪽 뭉갬(가정 질문 → 잔여 표)은 eval 로만 확인된다. 쓰기 쪽은 0단계 코드 가드가 받친다.
- **가드의 한계**: 표지는 좁혀 두었으므로 표지 없는 가정 표현("다음주 3일 쓰는 걸로 치고")은 통과할 수 있다. 이 경로는 파서가 UNKNOWN 으로 내리는지 eval 로 본다. 반대로 끝이 `?` 인 평서 등록("내일 휴가 등록해줄래?")은 막힌다. 막힌 경우 "등록해줘로 말해 달라"를 알리므로 손실은 재요청 한 번이다.
- **형태 강제와 폴백**: 파서에 `outputSchema` 를 걸면 claude 폴백이 막힌다(`model-router.usecase.ts`). 지금처럼 코드 파서로 검증한다.
- **숫자 검사의 범위**: 지어낸 숫자만 막는다. 원문 숫자를 그대로 되풀이한 틀린 답은 통과한다. 계산 정확도는 eval 이 잰다. 합·차만 허용하므로 곱셈·나눗셈 답은 폴백된다 — 반복되면 그 질문 형태만 결정론 계산으로 승격한다.
- **분류기 프롬프트 리팩터링**: 바이트 동일 테스트가 깨지면 분류 기준선(2026-09-22, 30/30)이 무효가 된다.
- **원문 무시형 워커(PAPER_TRADE 등)**: 모의투자 질문은 분류가 맞으면 고정 리포트가 나간다(`paper-trade.dispatcher.ts:34` 는 원문을 받지 않는다). "잔고 얼마야"에는 리포트가 답이 되므로 이번 범위에서는 고치지 않고 eval 로 지켜본다.
