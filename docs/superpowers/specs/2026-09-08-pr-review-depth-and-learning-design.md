## 2. 진짜 천장 세 가지

### 2-1. 깊이 — diff 밖을 못 본다

리뷰는 PR 메타 + diff(50KB 상한)를 한 번에 넣고 JSON 하나를 받는 원샷이다(`review-pull-request.usecase.ts:126`). 모델이 레포의 다른 파일을 볼 수 없다.

기각된 TEST 지적 8건을 전수로 열어 오탐 유형을 갈랐다. **"파일이 있는지 몰라서"가 아니라 "파일 안을 못 봐서"가 실제 원인이다.**

| 유형 | 사례 | 무엇이 있어야 풀리나 |
|---|---|---|
| 기존 spec이 이미 그 케이스를 덮고 있음 | #412 — owner가 `backend-role.filter.spec.ts:145`를 인용해 기각 | **대응 spec 파일의 본문** |
| 지적 대상 코드를 잘못 읽음 | #268 — 조건이 `end <= door + 1`이 아니라 `+ 1e-9`(부동소수 여유) | **그 소스 파일의 본문** (spec으로는 안 풀린다) |
| 레포에 그 실행 경로가 아예 없음 | #493 js-yaml·multer — 의존성만 올렸고 직접 쓰는 코드가 0건 | 레포 전역 검색 (부분적으로만 풀린다) |
| 코드로 알 수 없음 | sbe-api-v5#1067 — 운영 DB 실측이 근거 | 해결 불가 |

첫 유형은 spec 본문으로, 둘째 유형은 소스 본문으로 풀린다. **둘은 다른 자료를 요구하므로 설계에서 갈라야 한다.**

호출부 추적도 안 된다 — "이 함수 시그니처를 바꾸면 다른 호출부가 깨진다" 류의 근본 원인 지적을 못 한다. 기각 40건 중 최다가 CORRECTNESS 15건이다.

### 2-2. 학습 — 재료가 오염됐고, 자기 레포 + 억제 방향만

학습 규약은 `isSelfRepo` 게이트로 `JSL107/personal_agents`에만 실린다(`learning-repo.ts`). 회사 레포 4개(228건)에는 하나도 안 간다. 데이터가 없어서가 아니다 — `sbe-api-v5`는 기각 8건 중 6건이 규약화 가능 길이(40자 이상)다.

방향도 한쪽뿐이다. "기각당한 지적을 억제한다"만 있고, FIXED 115건은 어디에도 되먹여지지 않는다. STALE 65건(8%)은 PR이 결론 없이 닫혀 판정을 못 한 카드로, 그만큼 표본이 샌다.

**가장 급한 것은 재료 자체의 오염이다.** 기각 카드 40건의 이유를 훑어 명백한 역적재를 찾았고, 원인까지 규명했다.

**카드 id 57** (`sbe-api-v5-puppeteer#103`, 코멘트 3708876108):

| 시각 | 사건 |
|---|---|
| 02:03:13 | owner 답글 — "타당합니다. `8e0d19ad`에 (테스트를) 추가했습니다" |
| 02:03:47 | owner 👎 리액션 (답글 34초 뒤) |
| 02:05:01 | 수확 → REJECTED 확정 |

**수용하고 실제로 고친 지적에 👎가 잘못 눌렸고, 리액션이 답글보다 우선이라 "타당합니다"는 판정에 쓰이지 않았다**(`harvest-signal.ts`의 리액션 우선 판정). 답글은 `rejectReason`으로 저장만 됐다. 이 문장이 규약이 되면 "in-flight 경합 테스트는 지적하지 마라"를 가르친다 — 정확히 반대 방향이다.

카드 687·693·694(`sbe-api-v5#1066·#1067`)는 기각 이유가 `@gemini-code-assist 검토 감사합니다`로 시작한다. 다른 봇 앞으로 쓴 답변이 규약 재료가 됐다. 내용은 유효하지만 인사말과 타 봇 멘션이 섞인다.

**재료를 안 씻고 학습을 넓히면 오염이 증폭된다.** 그리고 오염은 매일 쌓인다 — 카드가 하루 20~33건 생성된다.

### 2-3. 대상 — PR 밖은 사각지대

열린 PR만 본다. 커밋 전 로컬 변경, 이슈·설계 문서는 리뷰 대상이 아니다.

## 3. 설계 제약 (이 셋이 해법을 좁힌다)

### 제약 A — 파일 접근은 우리가 중개해야 한다

두 가지 이유이고, 보안은 둘째다.

1. **대상 레포가 로컬에 없다.** 리뷰 대상이 7개 레포에 걸쳐 있고(회사 4개, 커뮤니티 2개, 자기 1개), 이대리 프로세스는 그중 어느 것의 체크아웃도 갖고 있지 않다. 파일을 보려면 GitHub API로 가져오는 수밖에 없다.
2. **상한을 우리가 걸 수 있다.** 중개하면 무엇을 몇 개까지 열지 코드가 정한다. 모델에게 파일시스템을 열어주면 그 통제가 사라진다.

보안 측면은 정확히 적어 둔다. codex 자식 프로세스는 `--sandbox read-only`로 실행되고(`codex-cli.provider.ts:227`), cwd·HOME은 일회용 임시 경로로 바뀐다(`cli-process.util.ts`). 그러나 **환경변수를 바꾸는 것은 읽기 권한을 막는 것이 아니다** — read-only 샌드박스는 쓰기를 막을 뿐 절대경로 읽기까지 봉하지는 않는다. "빈 폴더만 본다"는 표현은 과장이고, 실제로 얻는 것은 "경로 추론이 어려워지고 쓰기가 막힌다"까지다. 따라서 이 제약은 보안 방어선이라기보다 **운영 현실(체크아웃 부재) + 통제 가능성**의 문제로 다룬다.

### 제약 B — 시간 창: 머지까지 10~20분

2026-09-08 실측. PR은 하루 27개 열리고 대부분 10~20분 만에 머지된다. 리뷰는 생성 후 3.5~8분에 도착한다.

| PR | 생성 | 리뷰 도착 | 머지 | 마진 |
|---|---|---|---|---|
| #505 | 03:00 | 03:04 | 03:10 | 6분 |
| #507 | 04:21 | 04:26 | 04:30 | 4분 |
| #496 | 01:03 | 01:12 | 01:15 | 3분 |
| #515 | 06:16 | 06:25 | 06:35 | 10분 |

**깊이를 소요 시간으로 사면 리뷰가 머지 뒤에 도착한다.** 원칙: 시간을 늘리는 수단은 그 시간이 필요한 PR에서만 발동한다.

### 제약 C — 학습 경계: 레포마다 규약이 다르다

세대가 다른 레포에 틀린 규약을 실으면 오탐이 아니라 정탐을 지운다. 학습 규약은 레포별로 분리 저장·주입해야 하고, 효과를 재는 채택률 집계도 같은 경계를 봐야 한다.

### 제약 D — 파서가 "빈 findings"를 신뢰하지 않는다

`pr-review.parser.ts:41-50`은 정제된 `findings`가 비면 legacy 3배열(`mustFix`/`niceToHave`/`missingTests`)에서 복원한다. 모델이 새 필드를 안 채우는 사고를 막으려고 일부러 넣은 방어다.

이 방어는 **철회를 표현할 수단이 없다는 뜻이기도 하다.** 2패스가 "전건 철회"를 findings 빈 배열로 표현하면 legacy 배열에서 부활한다. 부분 철회에서도 Slack 포맷터는 legacy 배열을, GitHub 게시는 findings를 보므로 두 무대가 갈린다. 3단계 설계는 이 제약을 정면으로 다뤄야 한다.

## 4. 단계별 설계

순서는 "매일 손해가 쌓이는 것 → 싼 것 → 시간을 쓰는 것"이다. 단계 간 강한 의존은 4단계가 1단계에 기대는 것 하나뿐이다.

### 0단계 — 안전한 재현 경로 (다른 모든 단계의 전제)

**문제**: 검증하려면 과거 PR을 재리뷰해야 하는데, **지금은 안전하게 재리뷰할 방법이 없다.** 슬래시·멘션·콘솔은 전부 `publish: true`이고, 게시 호출은 `dryRun: false`를 하드코딩한다(`review-pull-request.usecase.ts:155`). `PR_REVIEW_INLINE_DRYRUN`은 스윕 경로에서만 읽힌다(`sweep-pr-reviews.usecase.ts:420`). 즉 검증 재리뷰가 **머지된 PR에 실제 코멘트를 단다.**

**설계**: 게시하지 않고 리뷰만 돌리는 실행 경로를 만든다. 가장 작은 형태는 `ReviewPullRequestUsecase.execute`가 이미 받는 `dryRun` 인자를 게시 호출에 연결하는 것이다 — 지금 `dryRun: false` 리터럴 자리에 넘기면 된다. 여기에 CLI 스크립트(`scripts/`) 하나를 붙여 "PR 번호를 주면 리뷰 결과를 파일로 떨군다"까지 만든다.

이게 0단계인 이유: 이후 모든 단계의 검증이 이 경로 위에서 돈다.

### 1단계 — 학습 재료 위생

**겨냥하는 것**: 카드 57 유형 — 수용한 지적이 리액션 오조작으로 기각 적재되는 역학습.

**가드 삽입 위치**: `harvest-review-signals.usecase.ts`의 `case 'REJECTED'` 분기, `markDecisionAndResolve` **호출 전**. 리플라이 판정기(`judgeReplies()`) 안에 넣으면 이 경로는 그 함수를 지나지 않아 가드가 무력해진다.

**가드 내용**: 👎 리액션 + owner 답글이 함께 있으면, 그 답글을 기존 리플라이 판정기(`REVIEW_REPLY_JUDGE`)에 넘긴다. 판정기가 "수용"이라고 하면 리액션과 모순이므로 **REJECTED로 확정하지 않고 보류**하고 Slack으로 한 건 알린다. 기각 카드는 전체의 5%(40/801)라 LLM 호출량이 미미하다.

**함께 다뤄야 할 두 가지 (검토에서 드러남)**:

- **종결 후에는 재검사되지 않는다.** 👎가 답글보다 먼저 도착해 REJECTED로 종결되면, 카드가 OPEN 전용 조회(`pr-review-finding.prisma.repository.ts:79`)에서 빠져 나중에 달린 수용 답글을 영영 못 본다. 최근 REJECTED를 짧은 기간(예: 24시간) 재조회 대상에 포함하거나, 답글이 없는 상태의 👎는 한 사이클 유예한다. **어느 쪽을 택할지는 구현 계획에서 정한다.**
- **답글·리액션 페이지 잘림.** 스레드 조회는 답글·리액션을 각 20개까지만 가져온다(`octokit-github.client.ts:66`). 봇 댓글과 👎가 첫 페이지에 있고 수용 답글이 그 밖에 있으면 모순을 못 본다. 대상 스레드의 완전성 플래그를 확인하고, 잘렸으면 보류로 떨어뜨린다(잘못 확정하느니 사람에게 넘긴다).

**규약 렌더링 정규화**: 기각 이유에서 선행 멘션(`@gemini-code-assist`, `@JSL107`)과 인사말을 걷어내고 싣는다.

**기존 오염 정리**: 카드 57을 `pnpm review:unlearn 57 --apply`로 ACKED로 되돌린다(`scripts/unlearn-review-card.ts`에 이미 있다). GitHub의 👎는 손으로 지운다.

### 2단계 — 동반 컨텍스트: 대응 spec 본문 (시간 비용 낮음)

**겨냥하는 것**: 2-1절 표의 **첫 유형 하나만** — "기존 spec이 이미 그 케이스를 덮고 있음". 둘째 유형(소스를 잘못 읽음)은 이 단계로 안 풀린다. 지적의 40%가 TEST 카테고리라 첫 유형만으로도 대상이 넓다.

**설계**: 변경된 소스 파일의 대응 spec 파일을 본문째 붙인다. 존재 여부만으로는 부족하다 — #412는 spec이 있고 그 안에 해당 케이스가 있는데도 "검증 안 됨"으로 지적했다.

```
[변경 파일의 기존 테스트 — 레포에서 그대로 읽어 옴]
### src/job-feed/domain/backend-role.filter.spec.ts (전체 4,050 bytes)
<파일 본문>
```

- **diff에 포함된 spec도 제외하지 않는다.** diff는 unified diff라 변경된 hunk만 보인다 — 테스트 100개 중 하나를 고쳤으면 나머지 99개는 여전히 안 보인다. 이 단계의 목적이 "이미 덮고 있는지 확인"이므로 전체 본문이 필요하다.
- 짝 판정에 레포 트리 조회 1회를 쓴다(새 포트 메서드 `listTree({ repo, ref })`, octokit `git.getTree({ recursive: 'true' })` — 이 파라미터는 문자열 타입이다). 트리 전문은 프롬프트에 넣지 않고 판정에만 쓴다.
- **트리 `truncated` 처리**: 재귀 트리는 100,000항목·7MB에서 잘린다. 잘린 트리에 없는 경로를 "spec 없음"으로 단정하면 안 된다. `truncated`가 참이면 그 사실을 블록에 명시하고, 짝 후보 경로를 개별 조회로 확인한다.
- **`changedFilesTruncated`는 별개다** — 그건 PR 변경 파일 목록의 잘림이다. 참이면 "일부만 확인함"을 블록 머리에 적어, 모델이 목록 밖 파일을 "테스트 없음"으로 읽지 않게 한다.
- **크기 예산**: 검토 중 실측으로 이 레포 spec 486개의 중앙값이 4,050바이트, 40KB 초과가 7개였다. 중앙값 크기 15개면 이미 60KB다. 따라서 단순 상한이 아니라 **선택 규칙**을 둔다 — MUST_FIX 후보가 걸린 파일 우선, 그다음 변경 라인 수가 큰 파일 순으로, 합계 예산까지 채우고 나머지는 "N개 생략"으로 표기한다. 예산 초깃값은 60KB로 두되 **첫 실측 후 조정한다.**
- 트리 조회·파일 읽기 실패는 best-effort로 무시하고 블록 없이 진행한다(현행 동작으로 열화).
- **시간 비용은 0이 아니다.** GitHub API 1 + N회이고 변경 파일은 최대 500개까지 온다. 조회 동시성과 총 조회 시간 상한(초안 10초)을 두고, 초과하면 모은 데까지만 싣는다. 입력이 커지는 것 자체의 시간 영향은 작다고 보지만(2026-07-31 실측: 입력 76KB PR 28초 vs 71KB PR 156초 — 소요를 가른 것은 출력량) **표본 2건의 관찰이라 근거로 약하다.** 배포 후 실입력 바이트와 소요를 함께 기록해 확인한다.

### 3단계 — 조건부 2패스 열람 (시간 비용을 필요한 PR에만)

**겨냥하는 것**: 2단계로 안 풀리는 나머지 — 소스를 잘못 읽어 생기는 오탐(#268 유형)과 호출부 추적.

**발동 조건 (검토 반영해 수정)**: 처음 설계는 "MUST_FIX 후보가 있을 때만"이었는데, 이건 순환이다 — 현재 프롬프트가 "확인 못 한 것은 지적하지 말라"고 지시하므로, **맥락이 없어 아직 MUST_FIX라고 못 박지 못한 후보가 정확히 배제된다.** 근본 원인 발견이 목표인데 그 후보를 거르는 조건이다. 고친 조건:

1. `needContext`가 비어 있지 않다 — **이것 자체가 신호다.** 모델이 "이걸 봐야 판단할 수 있다"고 말한 것 자체가 확인할 가치의 표현이다.
2. 요청 파일을 실제로 하나 이상 읽는 데 성공했다.
3. 스윕 사이클당 2패스 발동 상한(초안 1건) — 시간 창을 지키는 장치를 조건이 아니라 예산으로 옮긴다.

**needContext 계약**: 경로만 받으면 어느 지적을 위한 것인지 알 수 없다. 후보와 연결한다.

```jsonc
"needContext": [
  { "findingIndex": 0, "path": "src/...", "reason": "이 함수의 다른 호출부 확인 필요" }
]  // 최대 5개
```

부분 조회 성공을 전체 후보의 검증 성공으로 취급하지 않는다 — 파일을 못 읽은 후보는 1패스 상태 그대로 둔다.

**2패스 입력 (검토 반영)**: 1패스 findings만 주면 근거가 없다. codex는 `--ephemeral`이라 1패스 문맥이 이어지지 않고(`codex-cli.provider.ts:229`), 시스템 프롬프트는 "diff에서 인용 가능한 사실만"을 요구한다. 따라서 2패스에는 **후보별 관련 diff hunk + 읽은 파일 본문 + 적용 규약**을 함께 싣는다. diff 전문은 안 싣되, 후보가 가리키는 hunk는 반드시 싣는다(`diff-hunk.parser.ts`가 이미 hunk를 파싱한다).

**2패스 출력 (제약 D 대응)**: "새로 보이는 것 추가"는 **이번 범위에서 뺀다** — 변경과의 관련성을 검증할 계약이 없으면 2패스가 오탐 생성기가 된다. 2패스는 **후보별 판정만** 낸다.

```jsonc
{ "verdicts": [ { "findingIndex": 0, "verdict": "KEEP" | "WITHDRAW", "reason": "..." } ] }
```

전체 findings를 다시 받지 않으므로 파서의 legacy 복원 경로를 건드리지 않는다. 철회는 1패스 findings 배열에서 해당 항목을 **우리 코드가** 제거해 확정한다. Slack 포맷터가 legacy 3배열을 보므로(`pull-request-review.formatter.ts:28`), 철회 시 legacy 배열에서도 같은 항목을 지워 두 무대가 갈리지 않게 한다.

**시간 예산 (제약 B 대응)**:

- `CompletionRequest`에 `timeoutMs?`를 추가한다. provider에 `completeOnce(request, timeoutMs)`가 이미 있어(`codex-cli.provider.ts:315`) 배선만 하면 된다.
- **2패스는 단일 시도로 제한한다.** 재시도를 남기면 120초 상한이 attempt당이 되어 총 242초 + 부대비용이 된다.
- 2패스가 타임아웃·실패하면 1패스 결과를 그대로 게시한다(열화 폴백).
- `worker-options.constant.ts`의 lockDuration은 작업 타임아웃이 아니라 갱신되는 lease다. 2패스로 총 실행이 길어지면 lock 갱신 실패·stalled 복구를 별도로 확인한다 — 길이만 늘려서 될 문제로 다루지 않는다.

**스냅샷 일관성**: `getFileFromBranch`의 `ref`에 커밋 sha를 넣을 수 있는 것은 확인했다(`octokit-github.client.ts:754`가 그대로 `ref`로 전달). 다만 detail과 diff는 PR 번호로 각각 조회되므로 "리뷰 시점 스냅샷이 정확히 일치"하지는 않는다 — 스윕 경로도 '옛 headSha + 새 diff' 경쟁을 이미 알고 있다(`sweep-pr-reviews.usecase.ts:247`). 2패스 파일 읽기는 **1패스가 본 detail의 headSha**로 고정하고, 그 사이 head가 바뀌었으면 2패스를 건너뛴다.

**측정**: 2패스 발동률, 발동 시 추가 소요, KEEP/WITHDRAW 비율, 발동 PR의 기각률. 발동률이 낮거나 기각률이 안 줄면 철회한다.

### 4단계 — 학습 확장

1단계로 재료를 씻은 뒤에 연다. 셋은 **효과를 구분해야 하므로 따로 배포한다.**

**ⓐ 레포 게이트 개방.** `isSelfRepo` 하드코딩을 걷어내고 레포별로 규약을 쌓는다. 안전한 이유: 규약 재료가 되는 `rejectReason`은 이미 owner가 쓴 답글만 저장한다(`harvest-review-signals.usecase.ts`). 조회도 레포별이라 섞이지 않는다. 제약 C를 지키려면 채택률 집계 경계도 같이 옮겨야 한다(`adoption-rate.ts`, 스윕 요약 포맷터).

**ⓑ 정탐 학습 — 표본 검증이 선행 조건.** FIXED는 사람 확인이 아니라 **LLM 해소 판정**이다(`harvest-review-signals.usecase.ts`가 `judge-finding-resolution`을 호출해 `verdict === 'FIXED'`로 저장). 이걸 그대로 "검증된 정탐"으로 학습시키면 LLM 오판이 되먹여진다. 먼저 FIXED 카드 표본(20건)을 손으로 검증해 정확도를 재고, 충분할 때만 진행한다. 진행하더라도 30일 채택률로 유지·철회를 판정한다.

**ⓒ STALE 회수.** PR 머지 시점에 미판정 카드를 Slack 스레드 하나로 묶어 일괄 판정을 받는다. PR이 닫히면 GitHub 스레드에 리액션을 안 달게 되므로 무대를 옮기는 것이다. Preview Gate 인프라를 재사용한다. **주의**: 이걸 켜면 채택률 분모가 달라진다(`adoption-rate.ts`는 STALE을 제외한다). ⓐ·ⓑ의 효과 측정 기간과 겹치면 원인을 못 가른다 — 배포 시점을 분리한다.

### 5단계 — 대상 확장

**커밋 전 로컬 변경 리뷰.** 이대리는 로컬 파일에 접근할 수 없다(제약 A). 세션 쪽에서 diff를 실어 보내는 형태가 되고, 이미 있는 `idaeri-delegate` 스킬이 그 통로다. CODE_REVIEWER 입력에 "PR 참조 대신 diff 본문"을 받는 형태를 추가한다. 게시 대상이 없으므로 결과는 Slack·스킬 응답으로만 돌려준다.

**이슈·설계 문서 리뷰.** 성격이 코드 리뷰와 다르다. 실제 수요가 확인되기 전에는 만들지 않는다.

## 5. 안 하는 것

- **레포 체크아웃 기반 agentic 리뷰.** clone 인프라·프라이빗 레포 인증·디스크 정리가 붙고, 제약 B를 정면으로 위반한다. 2·3단계로 부족하다고 판명되면 올라갈 사다리로 남긴다.
- **2패스에서의 신규 지적 생성.** 관련성 검증 계약이 없으면 오탐 생성기가 된다.
- **이슈·설계 문서 리뷰 워커.** 수요 미확인.
- **allowlist 밖 레포 게시 개방.** SUPPRESSED 34건은 `PR_REVIEW_INLINE_REPOS`에 없는 레포에서 나온다. 코드가 아니라 운영 결정이라 env 항목으로 남긴다.
- **전역 실행 상한(watchdog).** 정상 PM 실행이 최대 33.6분 걸려 단일 상한은 정상 워커를 죽인다.

## 6. 검증

공통으로 `pnpm lint:check && pnpm test && pnpm build` 3중 green.

**계측을 먼저 만든다.** 지금 실행 기록에는 패스별 소요·컨텍스트 바이트·폴백 여부를 구별하는 필드가 없다(`review-pull-request.usecase.ts`의 `inputSnapshot`). 2·3단계 실험 전에 아래를 남기도록 한다: 첨부한 spec 개수와 바이트, 트리/파일 조회 소요, 2패스 발동 여부와 소요, 폴백 사유.

**대조군 없는 측정을 하지 않는다.** "과거 오탐이 사라졌다"만 보면 아무 지적도 안 하는 모델이 만점을 받는다. 각 실험은 **유지돼야 할 정탐 표본**을 함께 돌려 그것이 살아남는지 확인한다.

- **0단계**: 게시 없이 리뷰가 도는지, 그리고 게시 경로가 여전히 정상인지 양쪽 다 확인한다.
- **1단계**: 👎 + 수용 답글이 함께 달린 카드 픽스처가 보류로 떨어지는지. 가드를 빼면 실패하는지도 확인한다 — 통과만 보면 그 테스트가 가드를 지키는지 알 수 없다. 답글 페이지가 잘린 경우도 픽스처에 넣는다.
- **2단계**: 기각 TEST 8건 중 #412(기존 spec이 덮고 있던 건)가 사라지는지 + 정탐 대조군이 유지되는지. 첨부 바이트와 소요를 함께 기록한다.
- **3단계**: 기각 CORRECTNESS 15건 중 몇 건이 WITHDRAW로 걸리는지 + 정탐 대조군 유지. 발동률과 추가 소요가 제약 B 안인지.
- **4단계 ⓐ**: 레포별 기각률을 주입 전후로 비교(합산 금지).
- **4단계 ⓑ**: FIXED 표본 20건 손 검증이 선행. 그 뒤 30일 채택률.
- **4단계 ⓒ**: STALE 신규 발생 감소. 분모 변화를 감안해 ⓐ·ⓑ와 배포 시점을 분리한다.
