# 멀티 AI 오케스트레이션 파이프라인 v2 — 설계

작성일: 2026-07-30
범위: 개인 글로벌 작업 방식 (`~/.claude/CLAUDE.md` + `~/.claude/commands/`), 모든 레포에 적용

---

## 1. 문제 (Why)

현재 작업 방식은 Claude가 설계하고 `codex exec`(CLI)로 구현을 위임한 뒤 결과를 검증하는 구조다. 여기서 세 가지 문제가 반복된다.

- **호출 계층의 반복 실패.** `codex exec`를 백그라운드로 돌리면 stdin 대기로 무한 hang(`< /dev/null` 필수), 한글 경로에서 exit 2, exit 코드 파싱 취약 등 CLI 전송 방식 자체에서 오는 실패가 잦다.
- **지연.** codex 왕복이 10~40초이고 검증이 순차적이라 대기가 길다.
- **자율성 부족.** 단계마다 사람 관문이 있어 "한 번 맡기면 PR까지 알아서 가는" 흐름이 안 된다.

## 2. 목표 (What)

작업을 한 번 킥오프하면 **설계 → 구현 → 검증 → 수정 → PR 생성 → PR 봇 대응**까지 자율로 진행하고, 사람은 **완성된 PR을 최종 검토**하는 것을 기본 관문으로 삼는다. 성공 기준:

- codex 호출이 CLI hang·경로·파싱 실패 없이 안정적으로 왕복한다(MCP 도구화).
- 검증이 병렬로 돌아 대기가 줄어든다.
- 명확한 작업은 사람 개입 없이 draft PR까지 도달한다. 모호·고위험 작업만 시작 시 1회 확인한다.
- PR에 붙는 리뷰 봇(레포마다 상이)을 런타임에 탐지해 각각 대응한다.

## 3. 확정 결정 (전제)

| 항목 | 결정 |
|---|---|
| 독립 AI 구독 | Claude(오케스트레이터) · Codex(구현/외부 리뷰) · Gemini(PR 봇 전용). omc·superpowers는 별도 AI가 아니라 Claude Code 확장 |
| codex 호출 | `codex mcp-server`를 MCP 도구로 승격. 기존 `codex exec` CLI는 폴백으로 보존 |
| Gemini 위치 | 로컬 파이프라인 제외. GitHub PR 봇(`@gemini-code-assist`)로만 |
| 시작 관문 | 적응형 1회 — 모호·고위험만 설계 확인, 명확하면 통과 |
| 최종 관문 | PR = 보장된 사람 게이트. 사람은 draft PR을 보고 머지 |
| 오케스트레이션 엔진 | Claude 오케스트레이션(A)이 기본, 검증 fan-out만 Workflow(B)로 위임 가능 |
| 산출물 | `~/.claude/CLAUDE.md` 규칙 개정 + `/codex-flow` v2 재작성 + codex MCP 등록 |

### MCP 도구화의 경계 (중요)

MCP 승격은 **호출 계층의 실패**(stdin hang, 백그라운드 대기, exit 파싱, 스트리밍)를 없앤다. 그러나 codex의 `--sandbox workspace-write` **정책 제약**(localhost DB 접속 차단으로 인한 `P1001`, 레포 밖 worktree의 git `index.lock` 접근 불가)은 전송 방식이 아니라 샌드박스 정책이므로 **그대로 남는다**. 따라서 DB·설치·레포 밖 git 커밋은 메인(Claude)이 선/후처리하는 기존 분업을 유지한다.

## 4. 파이프라인 (How)

```
/codex-flow <task>   또는  자연어 위임
   │
   ├─① 설계 (Claude)          → .ai/design.md (구현 계약)
   ├─② 적응형 게이트           → 모호·고위험만 1줄 확인 / 명확하면 통과
   ├─③ 구현 (Codex = MCP 도구) → 설계 계약대로. 샌드박스 제약분은 메인이 선처리
   ├─④ 검증 (2층)             → Layer 0 결정론 게이트 + Layer 1 리스크 기반 LLM 리뷰(병렬)
   │      └→ 발견 취합 → codex 수정 위임 → 재검증 (수렴 루프, 최대 2회)
   ├─⑤ PR 생성 (Claude)       → draft PR. 맨 위 「이번 변경 한눈에」 산문 + 글로벌 PR 규칙 ★outward
   ├─⑥ PR 봇 루프 (레포 적응형) → 붙은 봇 동적 탐지 후 각 스레드 대응
   └─⑦ 사람 최종 게이트        → draft PR 검토 후 머지
```

### 4.1 검증 2층 구조 (④)

**Layer 0 — 결정론 게이트 (항상).** 레포 자체 검증 명령(예: `pnpm lint:check && pnpm test && pnpm build` 3중 green)을 먼저 통과시킨다. green이 아니면 Layer 1로 넘어가지 않고 바로 수정 루프. 가장 저렴하고 확실한 방어선.

**Layer 1 — LLM 리뷰 (리스크 기반 선택 발사, 병렬).** diff 성격을 판정해 필요한 리뷰어만 병렬 발사한다.

| 변경 성격 | 발사 리뷰어 |
|---|---|
| 순수 문서·주석·사소 설정 | 생략 (Layer 0만) |
| 일반 로직 변경 | `codex review`(외부 시각) + `omc:code-reviewer` |
| 보안·인증·외부입력·시크릿·env 경로 | + `omc:security-reviewer` (Opus 고정) |
| 큰 리팩토링·다파일 구조 변경 | + `omc:critic` (다관점) |

`codex review`는 로컬에서 유일한 외부 가문 시각이다. 나머지 리뷰어는 Claude 가문(omc 서브에이전트)이라는 비대칭을 인지하고, 외부 시각은 codex에 의존한다. 보안 리뷰는 Opus 서브에이전트로 고정한다(Fable 안전 분류기가 정상 보안 작업을 거부하는 사례 회피).

**적대적 검증 (맹종·맹반 금지).** 리뷰어(및 이후 PR 봇)의 지적을 그대로 반영하지 않는다. 각 발견을 파일:라인으로 재확인해 (A) 타당·범위 내 → 수정, (B) 타당·범위 밖 → 후속 기록, (C) 오탐 → 반증 근거와 함께 기각으로 분류한다.

**수렴 루프.** 발견 → codex(MCP) 수정 위임 → Layer 0 재실행 + 해당 리뷰어 재확인. 최대 2회, 미수렴이면 자율 진행을 멈추고 요약과 남은 발견을 사람에게 넘긴다.

### 4.2 PR 봇 루프 (⑥)

PR에 붙는 리뷰 봇은 레포마다 다르고 최대 두 종류다: `@gemini-code-assist`, `chatgpt-codex-connector`(Codex cloud 리뷰어). 하드코딩하지 않고 **런타임에 실제 코멘트를 단 봇을 탐지**해 대응한다(0~2개 모두 처리). codex cloud 리뷰가 레포에 연결돼 있으면 `@codex review`로 트리거할 수 있다.

대응 절차는 기존 글로벌 "PR 봇 리뷰 대응" 규칙을 계승한다: 수집(대화/인라인 스레드) → 코드로 평가(맹종·맹반 금지) → triage 3갈래(수정+답변 / 답변만 / 반박) → 각 인라인 스레드에 reply(봇 핸들 멘션 포함) + 필요 시 수정 push. dev/master 이중 PR 정합성 규칙도 그대로.

### 4.3 PR 본문의 사람용 설명 (⑤)

draft PR 본문 맨 위에는 리뷰어용 구조(문제/목표/변경/리스크/검증/후속)보다 앞서 **「이번 변경 한눈에」** 산문 설명을 둔다. 코드를 안 본 사람도 읽을 수 있게 **무엇을 바꿨나 · 왜 바꿨나 · 어떻게 설계했나**(핵심 판단과 검토한 대안 포함)를 자연스러운 한국어 3~6문장으로 쓴다. doc-tidy·humanize 정신을 따르되(약어·개조식 나열 최소화, 사실·수치·고유명사 불변) AI 제작 과정 메타(에이전트명·파이프라인·"N차 리뷰" 등)는 넣지 않는다. 자율 파이프라인은 산출물의 근거를 사람이 되짚을 수 있어야 머지 가능하다는 원칙의 실현 장치다.

## 5. 정책 결정 (하드룰 조정)

**commit 자동화 — 자율 모드 한정 완화.** 자율 파이프라인이 PR까지 도달하려면 커밋이 자동이어야 한다. 격리 브랜치/worktree 안에서는 자동 atomic commit을 허용한다. 단 ①main·공유 브랜치 직접 커밋 금지, ②force push 절대 금지, ③커밋 메시지 규약 유지, ④일반 대화형 세션은 기존 하드룰("사용자 명시 요청 후에만")을 그대로 둔다. 격리 브랜치라 브랜치 삭제·reset으로 되돌리기 쉽다.

**PR 봇 답변 게시 — 기본 draft-first, 옵트인 자동.** 봇 답변·수정 push는 되돌리기 어려운 outward 액션이라 기본값은 "초안 보고 → 승인 후 게시"(기존 글로벌 룰 유지). 킥오프에서 `--auto-reply`를 명시하거나 "봇 답변까지 자동"이라고 지시하면 자동 게시로 전환한다. PR이 뜨는 순간 이미 사람이 루프에 들어오므로, 봇 대응에 가벼운 관문을 두는 것은 "PR = 게이트" 모델과 모순되지 않는다.

**draft PR 생성 — 자율 허용.** 브랜치 push와 draft PR 생성은 사용자가 이미 "PR까지 자율, PR이 게이트"로 승인한 범위이므로 파이프라인의 정상 단계로 둔다.

## 6. 산출물

1. `~/.claude/CLAUDE.md` — "Claude-design / Codex-implementation 기본 작업방식" 섹션을 v2로 개정(MCP 우선·폴백 CLI, 적응형 게이트, 2층 검증, 수렴 루프, PR 봇 루프). commit "자율 예외" 명문화.
2. `~/.claude/commands/codex-flow.md` — v2 재작성. `codex-implement.md`·`codex-finalize.md`도 정합 갱신.
3. codex MCP 등록 — `claude mcp add codex -- codex mcp-server` 절차와 스모크 확인.
4. 본 설계 문서.

## 7. 동작 변화 / 리스크

- codex 호출 경로가 CLI → MCP 도구로 바뀐다. MCP 서버가 안 뜨면 CLI 폴백으로 자동 강등(둘 다 보존).
- 자율 모드에서 격리 브랜치에 자동 커밋이 생긴다. main 직접 커밋·force push는 여전히 차단.
- codex config에 죽은 MCP(예: figma)가 재주입되면 codex mcp-server 기동이 느려질 수 있다 → 최소 MCP 유지.
- 샌드박스 정책 제약(localhost, 레포 밖 git)은 MCP로 해소되지 않는다 → 메인 선/후처리 유지.

## 8. 검증 방법 (어떻게 "됐다"를 판정하나)

- codex MCP 등록 후 간단한 구현 작업 1건을 MCP 도구 경로로 왕복시켜 hang·경로 실패 없이 완료되는지 실증.
- 문서 변경 1건으로 Layer 1이 생략되는지, 로직 변경 1건으로 code-reviewer가 병렬 발사되는지 확인.
- 봇이 붙은 실제 PR 1건에서 런타임 탐지 → 스레드별 인라인 reply(멘션 포함)가 되는지 확인.
- MCP 서버를 일부러 꺼서 CLI 폴백이 동작하는지 확인.

## 9. 범위 밖 / 후속

- Gemini의 로컬 파이프라인 투입(headless CLI 교차검증)은 이번 범위 밖. 필요 시 후속.
- 완전 이벤트드리븐 데몬(장기 상주 프로세스)은 범위 밖. "한 번 킥오프하면 관문 없이 PR까지" 수준까지만.
- 통합 관측 대시보드(왕복·산출물·상태 단일 뷰)는 이번 목표에서 제외됨.
