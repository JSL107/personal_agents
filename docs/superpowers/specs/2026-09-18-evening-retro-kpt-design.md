# 저녁 회고 KPT 전환 — 설계

작성일 2026-09-18 · 상태: 구현 완료(머지 전)

저녁 회고를 「오늘 뭘 했나」 나열에서 KPT(Keep·Problem·Try) 판단으로 바꾼다. 핵심 제약은
**각 칸을 비울 수 있어야 한다**는 것이다. 모델은 빈 칸을 싫어해 근거가 없어도 무언가를 적는데,
지어낸 문제는 지어낸 개선안을 낳고 그것이 다음 날 일정을 밀어낸다.

---

## 1. 무엇을 바꾸나

`retrospective` 가 2~4문장 평문이었다. 이것을 네 칸짜리 객체로 바꾼다.

```ts
export interface EveningRetroReflection {
  keep?: string;       // 유지할 것
  problem?: string;    // 아쉬웠던 것
  tryNext?: string;    // 다음엔 이렇게 (행동 교정)
  carryOver?: string;  // 오늘 못 끝낸 것 + 이유
  malformed?: boolean; // 모델이 형식을 어긴 회차 표식
}
```

**키 이름 `retrospective` 는 유지한다.** `agent-contract.ts:377` 의 `deliverableFields` 를
건드리지 않아도 되고, 원장(`agent_run.output`)에 쌓인 과거 실행과 키가 같아 조회가 끊기지 않는다.
네 칸이 모두 비어 `{}` 가 되어도 계약 위반으로 잡히지 않는다 — `contract-inspector.ts` 의
`isEmptyValue()` 가 문자열·null·undefined 만 비었다고 보고 객체는 제외한다.

`tryNext` 는 KPT 의 Try 다. 예약어 `try` 를 속성명으로 쓰는 것 자체는 합법이지만 `reflection.try`
가 읽기 나쁘다.

### 칸을 넷으로 나눈 이유

`carryOver`(못 끝낸 것)를 `tryNext` 에 합치지 않았다. 둘은 성격이 다르다 — Try 는 행동 교정이고
carryOver 는 미완 작업이다. 합치면 못 끝낸 일이 있는 날마다 Try 칸이 차고, 그것이 모델에게
"이 회고는 칸을 채우는 양식"이라는 신호가 된다. 지어낸 문제를 막자면서 옆 칸에 채움 압력을
심는 셈이다.

---

## 2. 빈 칸을 어떻게 지키나

세 겹으로 나눠 걸었다. **결정론 게이트는 만들지 않았다.**

### 2-1. 프롬프트 — 키를 빼라고 명시

> 근거가 없는 칸은 키를 아예 빼라. 네 칸이 모두 빠져 retrospective 가 `{}` 가 되어도 된다.
> 입력에 없는 문제를 지어내지 말 것 — 없는 문제에서 나온 개선안이 다음 날 일정을 밀어낸다.
> "없음" "특이사항 없음" 같은 문자열로 칸을 채우지 말고 키 자체를 빼라.

덧붙이지 않고 기존 `retrospective` 지시 두 줄을 **교체**했다. 같은 주제의 지시가 두 벌이면
어느 쪽이 유효한지 알 수 없다.

### 2-2. 칸마다 근거 참조를 요구하지 않는다

핸드오프가 후보로 든 수단이지만 채택하지 않았다. `2026-09-17-blog-evidence-gate-design.md` §2-7 이
같은 구조로 무너졌다 — 모델이 아무 `#번호`나 붙이면 게이트가 꺼지고 우회 비용이 한 줄이다.
근거가 주장을 받치는지는 세는 것이 아니라 읽는 것이다.

### 2-3. 정규화는 공백 제거까지만

`없음` · `특이사항 없음` 같은 문자열 목록을 파서에 박지 않았다. 모델이 그 자리에 실제로 무엇을
쓰는지 관측한 적이 없어, 지금 만드는 목록은 실측이 아니라 창작이다. 같은 문서 §2-5 가 지적한
**"구현이 결정론인 것과 정의가 결정론인 것은 다르다"** 가 이 경우다.

렌더가 빈 칸을 「없음」으로 찍으므로, 모델이 "없음"이라 써도 화면 결과는 같다. 관측된 표현이
쌓이면 그때 `normalizeReflectionColumn()` 에 추가한다.

## 3. 억지 채움을 어떻게 감시하나 — 종료 조건 포함

### 3-1. 네 칸을 항상 찍는다

빈 칸을 숨기면 *"오늘 문제가 없었다"* 와 *"그런 칸이 원래 없다"* 가 화면에서 같아진다. 그러면
모델이 지어내기 시작해도 사람이 알아챌 표면이 사라진다.

```
🌙 *오늘의 회고 — 2026-09-18 19:00*

*유지* 가드를 깨뜨려 검증한 뒤 통과 대조군까지 봤다.
*문제* 없음
*개선* 없음
*미완* #605 리베이스 — 로컬 DB 를 worktree 가 공유해 막혔다.
```

### 3-2. 판정은 사람이 한다 — 자동 지표를 만들지 않는다

**"Problem 칸이 매일 차면 지어내는 것"은 판정 기준이 될 수 없다.** 해석이 둘이고(모델이
지어냈거나, 실제로 매일 아쉬운 점이 있거나) 후자가 더 흔하다. 개발한 날 아쉬운 점이 하나도
없는 쪽이 오히려 드물다. 실제로 2026-09-17 회고의 마지막 문장("확인하지 않은 채 결론을 쓴
패턴이 하루에 두 번 나왔다")은 지어낸 것이 아니라 사실이었다.

그래서 세는 장치를 만들지 않고 종료 조건을 사람 판정으로 박는다.

| 항목 | 값 |
|---|---|
| 관측 기간 | 도입 후 **7 영업일** |
| 관측 대상 | 저녁 메시지의 `*문제*` 칸 |
| 판정 | 사용자가 각 날짜를 「실제로 아쉬웠던 것」 / 「지어낸 것」으로 가른다 |
| 실패 기준 | 지어냄 **3건 이상** |
| 실패 시 조치 | `problem` 칸을 걷어내고 Keep·Try·carryOver 로 간다 |

관측만 하고 아무 일도 일어나지 않는 지표를 만들지 않기 위해, 실패 시 무엇을 되돌릴지를 함께
적는다. 이 저장소에는 관측 전용 지표가 무시된 전례가 있다.

### 3-3. 파서 실패를 화면에 드러낸다

회고를 못 읽어도 **던지지 않는다** — 회고 한 칸 때문에 그날 `candidates`·`prNotes`(블로그 후보와
이력서 재료)가 통째로 사라지는 쪽이 손해가 크다. 대신 `malformed` 를 세우고 메시지에 밝힌다.

```
_⚠️ 회고를 읽지 못했습니다(모델이 형식을 어겼습니다). 아래 후보는 정상입니다._
```

로그로는 부족하다. 사용자가 매일 읽는 표면만이 무시되지 않는다.

## 4. carryOver 의 근거 — 열린 PR

「오늘 못 끝낸 것」을 말하려면 근거가 필요한데, 기존 입력 셋(머지된 PR·worklog·daily-eval)에
그것이 없었다. 머지된 PR 은 정의상 끝난 것이다. 근거 없이 칸만 만들면 모델은 지어내는 수밖에 없다.

`listAuthorOpenPullRequests()` 로 **오늘 업데이트된 열려 있는 내 PR** 을 조회해 프롬프트에
별도 섹션으로 넣는다.

```
## 아직 열려 있는 내 PR (오늘 업데이트)
```

**본문은 싣지 않는다 — 제목과 링크만 넣는다.** 이 입력이 하는 일은 "무엇이 아직 안 끝났나"를
알리는 것뿐이다. 머지 PR 과 같은 형식(본문 500자)으로 실으면 각 최대 20건이라 프롬프트가 두 배가
된다. 반대로 `listOpenPullRequestRefs()`(상세 조회를 생략하는 가벼운 API)는 제목을 주지 않아
쓸 수 없다 — 제목이 없으면 모델이 "#611 이 미완"이라고만 쓰고 그게 무엇인지 말하지 못한다.

조회가 깨져도 회고는 계속 돈다. 저녁 보고가 부가 입력 하나 때문에 통째로 막히는 쪽이 더 나쁘다.
`inputSnapshot.openPrCount` 를 남겨, carryOver 가 매일 비면 *"정말 다 끝낸 날"* 인지
*"조회가 0건인지"* 를 가를 수 있게 한다.

### 노션을 쓰지 않은 이유

노션 작업 DB 를 근거원 후보로 검토했고 **실측으로 기각**했다. `NOTION_TOKEN` 과
`NOTION_TASK_DB_IDS` 는 설정돼 있으나, 그 DB 는 항목이 2건뿐이고 마지막 편집이 **2026-04-27**
이다. 둘 다 상태가 「시작 전」로 5개월째 박혀 있다. 입력에 넣어도 얻는 것이 없고, 유령 항목이
carryOver 의 가짜 근거가 된다.

> 별건: 아침 PM(`/today`)이 같은 DB 를 매일 프롬프트에 넣고 있다. 이 작업의 범위 밖이지만
> 확인이 필요하다.

## 5. 소비처

핸드오프는 6곳으로 적었으나 실제 코드 참조는 4곳이다. 나머지 둘은 주석에만 등장한다.

| 파일 | 변경 |
|---|---|
| `evening-retro.prompt.ts` | 타입·파서·프롬프트·`formatRetroContext` |
| `evening-retro-publish.autopilot-task.ts` | 열린 PR 조회, KPT 렌더, payload 조립 |
| `humanize-report.adapter.ts` | 채워진 칸만 윤문, 복귀 시 재정규화 |
| `agent-contract.ts` | **변경 없음** — 키 이름을 유지했다 |
| `evening-blog-publish.applier.ts` | **변경 없음** — 주석에만 등장 |
| `agent-run.service.ts` | **변경 없음** — 주석에만 등장 |

### 블로그 발행 경로가 안 깨지는 이유

`EveningBlogPayload.retroContext` 는 `string` 을 유지한다. 이 값은 승인 카드가 눌릴 때까지 DB 에
머물기 때문에, 객체로 바꾸면 **이미 발송된 미승인 카드가 깨진다**. `formatRetroContext()` 가
채워진 칸만 이어 붙인 평문을 만든다.

### 윤문

채워진 칸만 `retrospective.keep` 식으로 평탄화한다. 빈 칸을 빈 문자열로 넣으면 윤문기가 무언가를
채워 돌려줄 수 있고, 그러면 모델이 비워 둔 칸이 윤문 단계에서 되살아난다. 돌아온 값에는 같은
정규화를 다시 건다. 필드 상한은 240개라 +3 은 여유가 있다.

## 6. 검증

- `pnpm lint:check` — 0 errors (경고 38건은 기존)
- `pnpm test` — 504 suite / 5502 tests + code-graph 5 suite / 40 tests 전부 통과
- `pnpm build` — exit 0
- **실제 렌더 실증** — 네 경로(네 칸 전부 / 일부만 / 전부 빔 / 형식 어김)의 Slack 메시지
  문자열을 실제 task 로 찍어 확인했다. DB `output` 이 최종 메시지가 아니므로 그것만으로는
  검증이 되지 않는다.

**아직 검증하지 못한 것**: 실모델(codex)이 이 프롬프트로 어떤 형태를 내는지는 확인하지 않았다.
네 칸을 실제로 비우는지, "없음" 류 문자열을 쓰는지는 §3-2 의 7 영업일 관측에서 드러난다.

## 7. 범위 밖

- **아침 `/today` 연결.** PM 은 직전 PM 실행과 직전 Work Reviewer 실행만 읽고 저녁 회고를 보지
  않는다(`generate-daily-plan.usecase.ts:373-382`). 전달 경로를 새로 만들어야 하므로 별도 PR 로
  나눈다. 이번 변경이 `tryNext`·`carryOver` 를 원장에 쌓아 두면 다음 PR 은 읽는 쪽만 만들면 된다.
- **저녁 회고가 내일 일정을 짜는 것.** 아침 PM 의 일이다.
- **실행 조건(`skip`) 변경.** 열린 PR 만 있고 머지·worklog·daily-eval 이 없는 날은 지금도
  건너뛴다. 조건을 바꾸면 회고가 도는 날짜 자체가 달라지므로 이번 변경에 섞지 않았다.
- **아침 PM 의 죽은 노션 DB 참조** (§4).
