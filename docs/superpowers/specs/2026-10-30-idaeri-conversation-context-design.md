# 이대리 대화 답변 — 맥락·사진·조회·이어서 등록 설계

작성일: 2026-10-30
범위 밖: 답변 가독성(Markdown → Slack 변환)은 `fix/slack-markdown-bold` 브랜치에서 별도로 처리한다.

## 1. 왜 하는가

Slack DM 실사례(2026-10-30). 아침신문(Hermes cron 이 이대리 봇 토큰으로 같은 DM 에 보낸 글) 바로 아래에서
사용자가 "왜 스킬 아직도 한개야"라고 묻자, 이대리는 "어느 화면인지 알려 달라"고 되물었다. 스크린샷을 보내자
"지금 주신 정보만으로 확인할 수 없어요"라고 답한 뒤 할 수 있는 일 목록을 늘어놓았다.

사용자가 바라는 흐름은 다음과 같다.

> 이거 왜 안 돼? → (위 글·사진·기록을 보고) 이런 게 의심돼요 → 원인과 함께 일정에 등록해 줄래? → 등록했어요

코드로 확인한 원인은 다섯 가지다.

| 증상 | 원인 | 근거 |
|---|---|---|
| 위에 온 글을 모름 | 대화 원본이 Redis 대화 기억(이대리가 직접 주고받은 글)뿐이다. DM 최상위 메시지는 스레드 부모 보충도 타지 않는다 | `router-message.handler.ts` `getPriorTurnsWithChannelFallback`, `fetchThreadRootText` 의 `threadTs === messageTs` 조기 반환 |
| 사진을 못 봄 | DM 핸들러가 `subtype` 이 있는 메시지(`file_share`)를 버리고, 두 진입점 모두 `event.text` 만 읽는다 | `router-message.handler.ts:229`, `:184`, `:237` |
| "확인할 수 없어요"만 반복 | 대화 답변은 조회 수단이 없는 순수 생성이고, 프롬프트에 사고마다 덧붙인 금지 문장이 쌓여 있다 | `conversational-reply.usecase.ts` `buildSystemPrompt` |
| 분석을 다음 행동에 못 실음 | 일정 등록은 지금 문장만 읽는 규칙 기반 파서라 "원인과 함께"가 가리키는 내용을 모른다. 날짜가 없으면 되묻는다 | `schedule.dispatcher.ts` `parseScheduleCommand`, `modelUsed: 'deterministic'` |
| 회귀 감시 없음 | 위 대화가 eval 문항에 없다 | `src/router/eval/nl-answer-eval.cases.ts` |

이미 갖춰진 것도 있다. 이미지는 video-watch 가 `imagePaths` → codex `--image` 로 넘기고 있고, 지정 폴더만 읽게 하는
codex 읽기 잠금(`readableRoots`)은 PR 리뷰의 레포 사본 읽기(#915·#919)에서 도입됐다. `ScheduleItem.memo` 칸과
`RegisterScheduleUsecase` 의 `memo` 입력도 이미 있다.

## 2. 목표 / 비목표 / 반목표

**목표**
1. 답하기 전에 그 DM·스레드의 최근 메시지를 Slack 에서 읽어 맥락으로 쓴다. 이대리 자신의 답, 자동 발송 글(아침신문·알림), 사용자 글을 구분한다.
2. 사용자가 보낸 사진을 대화 답변이 본다.
3. 대화 답변이 이대리 원장·발송 기록·레포·Hermes 실행 기록을 읽기 전용으로 확인하고, 본 것을 근거로 답한다.
4. "원인과 함께 일정에 등록해 줘"처럼 직전 대화를 가리키는 등록 요청을, 그 내용을 memo 로 실어 바로 등록한다.
5. 대화 답변 프롬프트를 소수의 원칙으로 줄이되 기존 eval 성적은 지킨다.
6. 위 실사례를 eval 문항으로 남긴다.

**비목표 (이번에 안 함)**
- Redis 대화 기억 제거. 역할만 바꾼다(§3-1).
- channel 키 되짚기 보정 코드(`getPriorTurnsWithChannelFallback` 의 옮겨 담기) 삭제. Slack 원본이 운영에서 안정된 뒤 후속으로 뺀다.
- 일정 외 쓰기 워커(휴가·할 일·블로그 등)의 "이어서 등록".
- 채널 최상위 멘션의 채널 기록 읽기. 남의 잡담이 섞이므로 DM 과 스레드만 읽는다.
- 아침신문 「오늘의 도구」가 1건만 나간 원인 조사(별건).

**반목표 (기술적으로 돌아가도 실패로 본다)**
- 보지 못한 사진·기록을 본 것처럼 답한다.
- 아침신문 본문 같은 외부 글을 이대리 자신의 발화나 지시로 받아들인다.
- 읽기 허용 범위가 아래 §3-3 에 적은 폴더 밖으로 넓어진다(특히 `~/.hermes/auth.json`·`config.yaml`, 이대리 `.env`).
- 사진·조회를 붙였다는 이유로 codex 가 실패했을 때 답이 아예 나가지 않는다.

## 3. 설계

### 3-1. 대화 원본을 Slack 으로 (Redis 는 부가 정보로)

**읽는 범위**
- 스레드 안 메시지: `conversations.replies` 로 그 스레드 전체(부모 글 포함). 긴 스레드는 최근 30개로 자른다.
- DM 최상위 메시지: `conversations.history` 로 그 DM 의 최근 15개, 24시간 이내. 스레드만 보면 시작점 사례(DM 최상위 아침신문 아래의 최상위 질문)가 잡히지 않는다.
- 채널 최상위 멘션: 읽지 않는다(현재 동작 유지).
- 메시지당 1500자에서 자른다(기존 `PRIOR_TURN_TEXT_CAP` 재사용).
- 현재 메시지 자신은 제외한다(지금처럼 `[현재 사용자 메시지]` 로 따로 싣는다).

**누가 쓴 글인지 구분** — Slack 메시지 `metadata` 꼬리표를 쓴다.
- 이대리가 대화 답(라우터 답장, 대화 답변, 비동기 BLOG 완료 답장)을 보낼 때 `metadata: { event_type: 'idaeri_reply', event_payload: {} }` 를 붙인다. 발송 지점은 `router-message.handler.ts` 의 `say` 호출들과 `agent/blog/infrastructure/slack-web.notifier.ts` 다.
- 읽을 때 `include_all_metadata: true` 로 받아 다음처럼 나눈다.

| 글 | 판정 | 대화 턴으로 바꾼 모양 |
|---|---|---|
| 사용자(현재 발화자) | `user` 필드가 발화자 | `role: 'user'` |
| 이대리 대화 답 | 봇 글 + `idaeri_reply` 꼬리표 | `role: 'assistant'` |
| 아침신문·autopilot 알림·기타 봇 글 | 봇 글인데 꼬리표 없음 | `role: 'user'`, 본문 앞에 `[자동 발송 글]` 표식, 외부 입력 경계(`wrapUntrustedInput`)로 감쌈 |

autopilot 알림처럼 이대리가 스스로 보낸 알림도 꼬리표를 붙이지 않는다. 사용자가 그 알림에 "이거 왜 이래?"라고 물으면
이대리는 그 글을 자기 대화 답이 아니라 참고할 대상으로 읽어야 하기 때문이다.

꼬리표가 기록 조회에서 돌아오지 않는 것으로 실측되면(§5), 대안으로 이대리가 대화 답을 보낸 뒤 받은 메시지 `ts` 를
기록해 두고 그 `ts` 로 판정한다. 이 경우 저장 위치(Redis 대화 기억 또는 `mention_receipt`)는 계획 단계에서 정한다.

`[자동 발송 글]` 을 user 역할로 두는 이유는 기존 스레드 원문 처리(`THREAD_ROOT_LABEL`)와 같다. assistant 로 두면
분류기와 대화 답변 둘 다 그 글을 "내가 한 말"로 읽는다.

**Redis 기억과의 관계**
- 프롬프트에 싣는 **대화 본문**은 Slack 에서 읽은 것을 쓴다(분류기 `priorTurns`, 대화 답변, 워커에 넘기는 `priorTurns` 모두).
- **부가 정보**는 지금처럼 Redis 에서 읽는다. 실행 id·담당 에이전트(작업 상태 조회, `priorAgentRunId`), 되묻기 연속 횟수, 승인(응/아니)·목표 답변·갭 주제 선택 가로채기가 여기에 해당한다.
- Redis 쓰기는 지금과 같게 유지한다.
- Slack 조회가 실패하면(scope 부족, rate limit, 네트워크) 경고 로그를 남기고 지금처럼 Redis 턴을 대화 본문으로 쓴다. 맥락 보강 때문에 답을 막지 않는다.

**구현 위치**: `slack/infrastructure` 에 대화 기록 리더를 두고, `Slack 메시지 → ConversationTurn[]` 변환과 판정 규칙은
순수 함수로 domain 에 둔다(단위 테스트 대상). 이렇게 하면 하류(분류기·대화 답변·워커)는 `ConversationTurn[]` 를 그대로 받으므로 바뀌지 않는다.

### 3-2. 첨부 사진

- **수신**: DM 핸들러가 `subtype === 'file_share'` 는 통과시킨다(다른 subtype 은 지금처럼 버린다). 두 진입점 모두 `event.files` 를 읽는다.
- **대상**: §3-1 로 읽어 온 대화 범위 안의 이미지(`mimetype` 이 `image/png|jpeg|gif|webp`). 스레드 부모와 이어지는 글에 모두 사진이 있으면 둘 다 본다.
  - 상한: 합계 4장, 장당 5MB.
  - 우선순위: ① 현재 메시지 → ② 사용자가 올린 사진(최신순) → ③ 자동 발송 글의 사진(최신순, 예: 아침신문 그림 카드).
  - 상한·크기 때문에 못 본 사진이 있으면 "사진 N장은 보지 못했다"를 프롬프트에 적는다.
  - 프롬프트의 대화 기록에는 각 메시지 옆에 `[사진 k번 첨부]` 를 달아, 모델이 어느 사진이 어느 글에 붙었는지 알게 한다.
- **다운로드**: `url_private_download` 를 봇 토큰 Authorization 헤더로 받아 `mkdtemp(tmpdir())` 아래에 저장하고, 답이 끝나면 `finally` 에서 지운다. `files:read` scope 가 필요하다. README 설치 안내에는 이미 있으나, 실제 설치된 앱에 적용됐는지는 사용자가 확인한다.
- **전달 대상**: 대화 답변에만 넘긴다(`imagePaths`). 분류기에는 `[사진 N장 첨부]` 한 줄만 싣는다. 사진이 붙은 요청이 워커로 가면 워커는 사진을 쓰지 않는다.
- **글 없이 사진만 보낸 메시지**: 지금은 빈 글이면 "메시지가 비어 있습니다"로 끊는다. 사진이 있으면 통과시킨다.

### 3-3. 읽기 전용 조회

**미리 조회해서 프롬프트에 싣는 것(텍스트)**
- 이대리 실행 원장: 최근 24시간, 이 사용자, 최신순 10건(에이전트·상태·실패 사유·시각).
- 이대리 발송 기록(`slack_delivery`): 최근 24시간, 최신순 10건(종류·상태·미리보기·시각).
- 조회 실패는 답을 막지 않는다. 해당 블록만 빠진다.

**모델이 직접 열어 보게 하는 폴더(`readableRoots`)**
- Hermes 실행 기록: `~/.hermes/cron/output` 한 폴더. job 마다 하위 폴더, 실행마다 `<날짜>.md` 가 있다. 형제 경로(`auth.json`·`config.yaml`·`.env`·`cron/jobs.json`)는 열지 않는다.
  - 경로는 새 env `HERMES_CRON_OUTPUT_DIR` 로 받는다. 비어 있으면 이 조회를 끈다. 새 env 이므로 `.env.example`·`.env`·`app.config.ts`·README 4곳과 `docs/env-catalog.md`(`pnpm docs:sync`)를 함께 갱신한다.
- 이대리 레포 사본: 실행 중인 로컬 레포에서 `git archive HEAD` 로 커밋된 파일만 꺼내 `tmpdir()` 아래 임시 폴더에 푼다.
  - 레포 폴더 자체는 열지 않는다. `.env` 등 gitignore 대상이 있기 때문이다. `git archive` 는 커밋된 파일만 꺼내므로 `.env` 는 들어가지 않고, 안전망으로 PR 리뷰의 비밀 파일 필터(`isSecretFilePath`)를 한 번 더 건다.
  - 답할 때마다 `git rev-parse HEAD` 로 현재 커밋을 보고, 사본을 만든 커밋과 다를 때만 새로 꺼낸다. 네트워크는 쓰지 않는다.
  - 교체 중 진행 중인 답이 옛 사본을 읽을 수 있도록 직전 사본 한 세대를 남기고, 그보다 오래된 것은 지운다. 프로세스 시작 시 죽은 프로세스가 남긴 사본을 정리한다(PR 리뷰 사본의 PID 접두사 방식과 같다).
  - 레포 경로는 프로세스 작업 디렉터리에서 `git rev-parse --show-toplevel` 로 찾는다. git 레포가 아니면 이 조회를 끈다.
- 폴더를 열 때는 지금처럼 읽기 잠금 canary(`assertReadLock`)를 통과해야만 진행한다.

**프롬프트 안내**: 무엇을 어디서 볼 수 있는지 적고, "본 것만 근거로 말하고, 무엇을 봤는지 답에 밝힌다"를 원칙으로 둔다(§3-5).

### 3-4. 폴백: 사진·폴더를 빼고 Claude 로

- 지금은 `imagePaths`·`readableRoots` 가 붙은 요청이 codex 에서 실패하면 폴백 없이 실패한다(`model-router.usecase.ts:160-166`).
- `ModelRouterUsecase.route` 에 "폴백할 때 첨부를 떼고 보낸다" 선택지를 추가한다. 켜져 있으면 Claude 재시도 요청에서 `imagePaths`·`readableRoots` 를 빼고, 프롬프트 끝에 "사진 N장과 기록 폴더가 있었지만 이번 답에서는 볼 수 없었다. 답 첫머리에 그 사실을 밝혀라"를 붙인다.
- 이 선택지는 대화 답변만 켠다. PR 리뷰·video-watch 의 기존 동작은 바꾸지 않는다.
- 미리 조회해 실은 원장·발송 기록은 텍스트라 폴백에서도 그대로 남는다.

### 3-5. 프롬프트 정리

- 사실 블록은 남긴다: 정체, 할 수 있는 일 목록, 자동 동작 목록, 우사기 페르소나, 직전 작업 상태, 말투.
- 금지 문장 묶음은 세 원칙으로 바꾼다.
  1. **본 것만 말한다**: 대화 기록·사진·조회 결과에 있는 것만 사실로 말하고, 무엇을 보고 말하는지 밝힌다.
  2. **못 보면 무엇을 봐야 하는지 말한다**: 근거가 없으면 지어내지 말고, 무엇이 있으면 답할 수 있는지 한 문장으로 말한다.
  3. **결론부터 짧게**: 첫 문장에 답, 필요한 만큼만 덧붙인다.
- "대화 답변은 작업을 실행하지 않는다"는 사실은 유지한다. 조회는 하지만 쓰기는 하지 않으므로 "해 드릴게요" 류 약속 금지는 원칙 2 아래 한 줄로 남긴다.
- **판정 기준** (holdout 26문항 기준, codex 호출을 줄이려는 단계식):
  1. 정리 전·후 각각 `pnpm eval:nl-answer --split holdout --runs 1`.
  2. 두 결과가 갈린 문항만 `--only` 로 정리 전·후 각 3회.
  3. 3회 다수결로 정리 후가 더 나쁘면 회귀로 보고, 그 문항을 지키던 금지 문장을 되살린다. 되살린 문장과 사유를 계획 실행 기록에 남긴다.

### 3-6. 직전 대화를 실어 일정 등록

- 대상: SCHEDULE 워커만.
- 켜지는 조건: 직전 대화(`priorTurns`)에 이대리의 답이 있고, 아래 둘 중 하나가 맞을 때.
  1. 규칙 파서가 제목이나 날짜를 못 채웠다.
  2. 문장에 직전 대화를 가리키는 말("원인", "그거", "방금", "위 내용", "분석한" 등)이 있다. 파서가 다 채웠어도 넘긴다 — 안 넘기면 "내일 원인과 함께 등록해 줘"가 제목 "원인과 함께"로 바로 등록된다.
- 동작: 모델 추출을 부른다. 출력 스키마는 `{ title, dueDate | null, memo }` 이며 `outputSchema` 로 형태를 강제한다.
  - 추출 결과는 코드가 다시 검증한다: 날짜 형식, 제목 길이, memo 길이 상한.
  - 날짜가 없으면 **오늘(KST)** 로 등록하고, 답에 "날짜가 없어 오늘로 등록했다"를 밝힌다.
  - 모델 추출이 실패하면 지금처럼 규칙 파서 결과로 처리한다(되묻기 포함).
- 확인 질문 없이 바로 등록한다. 답에는 제목·날짜·memo 요약을 보여 준다. 일정은 등록 뒤에도 지울 수 있다.
- 기존 가정형 문장 가드(`findHypotheticalMarker`)는 그대로 먼저 적용한다.
- 규칙 파서가 이미 제목·날짜를 다 채운 평서 등록("9월 30일 자동차세")은 지금처럼 모델 없이 처리한다.

## 4. 제약

- CLI 격리 규칙(`buildSafeChildEnv`, stdin 전달, 읽기 잠금 프로필)을 그대로 지킨다. `--sandbox` 와 권한 프로필을 섞지 않는다.
- `process.env` 직접 참조 금지 → `ConfigService`.
- 완료 조건: `pnpm lint:check && pnpm test && pnpm build`, `check:di`, `check:env`, `docs:check`, `check:invariants`, `test:e2e` 전부 green. 새 env 때문에 `pnpm docs:sync` 필요.
- Slack scope: `files:read`(사진), `im:history`(DM 기록), `channels:history`·`groups:history`(채널 스레드)는 README 목록에 있다. 메시지 `metadata` 쓰기·읽기에 추가 scope 가 필요한지는 구현 첫 단계에서 실측한다.

## 5. 정해 둔 것과 남은 것

**사용자가 정한 것**
- 5개 항목과 "이어서 등록"을 한 설계로 진행한다.
- Claude 폴백 때는 사진을 떼고 간다.
- 아침신문과 이대리 답은 구분하고, 자동 발송 글(이대리 자신의 알림 포함)은 참고 자료로 다룬다.
- Redis 대화 기억은 남긴다.
- Hermes 실행 기록 폴더를 조회 범위에 넣는다.
- 이어서 등록은 확인 질문 없이 바로 등록하고, 날짜가 없으면 오늘로 등록한다. 켜지는 조건은 §3-6 의 두 가지다.
- 레포 사본은 로컬 `git archive HEAD` 방식, HEAD 가 바뀔 때만 새로 만든다.
- 기록 범위: 스레드는 전체(30개 상한), DM 최상위는 15개·24시간.
- 사진: 대화 범위 안 합계 4장, 현재 메시지 → 사용자 사진 → 자동 발송 글 사진 순.
- 원장·발송 기록은 매 답변에 싣는다.
- 프롬프트 정리 판정은 전체 1회 + 갈린 문항만 3회.

**내 판단으로 정한 것** — 본문에 *(내 판단)* 으로 표시했다(메시지당 글자 상한 재사용, 사진 문항을 단위 테스트로 대신).

**구현 첫 단계에서 실측할 것**
- Bolt `say` 로 DM 에 붙인 `metadata` 가 `conversations.history` 에서 돌아오는지.
- 읽기 잠금 canary 와 레포 사본 준비가 대화 답변 지연을 얼마나 늘리는지.
- 실제 설치된 Slack 앱에 `files:read` 가 있는지.
