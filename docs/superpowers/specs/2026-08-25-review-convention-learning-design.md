# 리뷰 규약 자동 학습 — 설계

작성 2026-08-25. 대상 브랜치 `feat/review-convention-learning` (base `origin/main` 3fd6960).

---

## 1. 문제

이대리 코드 리뷰봇에는 학습 루프가 있다. 지적을 게시하고, 사람이 기각하면 그 지적을 기억에
적재하고, 다음 리뷰 프롬프트에 "이런 코멘트는 피하세요"로 되먹인다. **이 되먹임이 행동을
바꾸지 못한다.**

### 1-1. 실증 — 같은 지적이 3연속 기각되고도 계속 나왔다

`ARCHITECTURE` 카드 8장을 시간순으로 보면 드러난다.

| 날짜 | PR | 결말 | 적재 |
|---|---|---|---|
| 2026-08-12 | #281·#285 | ACKED | — |
| 2026-08-13 | #288 | REJECTED | `episodic_memory` id 576 |
| 2026-08-20 | #343 | REJECTED | id 901 |
| 2026-08-21 | #354 | REJECTED | id 965 |

기각 사유는 셋 다 같다 — "이 레포는 port/adapter 를 외부 I/O 경계에만 쓰고, DB 접근은
직접 주입이 관례다. 같은 형태가 최소 12곳"(카드 373).

### 1-2. 원인은 검색이 아니라 프롬프트 위계였다

PR #343 리뷰 시점의 실제 쿼리(`제목 + 변경파일`)로 벡터 검색을 재현했다.

```
1. id=630 dist=0.1198 ★주입   스케줄 잡 idempotency 키 지적    ← 무관
2. id=576 dist=0.1241 ★주입   application→infrastructure 지적  ← 관련
3. id=758 dist=0.1356         모의투자 EXPIRED 분기
4. id=350 dist=0.1387         listener 경합 테스트
```

**관련 사례가 실제로 주입됐는데도 같은 지적이 나왔다.** 검색이 못 찾아서가 아니라, 찾아
넣어줘도 모델이 듣지 않는다.

시스템 프롬프트 33행이 카테고리를 `ARCHITECTURE(DDD·Port-Adapter 위반)` 으로 **정의**한다.
되먹임은 프롬프트 맨 끝에 불릿 두 줄로 **덧붙는다**(`review-pull-request.usecase.ts:219`).
덧붙인 예시가 정의를 이기지 못한다.

곁가지로 거리값이 0.1198~0.1491 한 대역에 뭉쳐 있다. 무관한 사례와 정확히 관련된 사례의
차이가 0.004다 — 검색이 순서를 가리지 못한다.

### 1-3. 반대로 규약은 확실히 먹혔다

2026-07-31 에 `SELF_REPO_CONVENTIONS` 로 "마이그레이션 파일 누락은 이 레포에서 오탐이니
지적하지 않는다"를 프롬프트에 **규칙으로** 써넣었다(#194).

```
migration 관련 지적 (이 레포):  2026-07-31  1건
                              그 이후      0건
```

| | 되먹임 (episodic) | 규약 (SELF_REPO_CONVENTIONS) |
|---|---|---|
| 갱신 | 자동 | **수동** |
| 형태 | 프롬프트 끝, 예시 | 규칙, "지적하지 않는다" |
| 효과 | 3연속 재발 | 재발 0건 |
| 마지막 갱신 | 계속 쌓임(18건) | **2026-07-31 이후 없음** |

효과 있는 레버가 수동이고, 자동인 레버가 무효다. 이것이 "자가 학습"의 실제 상태다.

### 1-4. 규약이 이 레포에만 있다

리뷰는 5개 레포에서 돈다. `buildRepoConventions` 는 `jsl107/personal_agents` 일 때만 규약을
붙이고, 나머지 147건은 규약 없이 리뷰된다.

| 레포 | 카드 | 기각 |
|---|---|---|
| JSL107/personal_agents | 288 | 15 |
| DDD-Community/DDD_BE | 63 | 0 |
| schoolbell-e/sbe-api-v5 | 57 | 2 |
| schoolbell-e/sbe-api-v4 | 21 | 0 |
| schoolbell-e/sbe-api-v5-puppeteer | 6 | 1 |

## 2. 목표

기각 이유를 **레포별 규약으로 자동 편입**해, 같은 지적이 반복되지 않게 한다.

성공 기준:

1. `ARCHITECTURE` 반복 지적이 이 레포에서 멈춘다
2. 정탐 채택률(현재 CORRECTNESS 94% · TEST 98%)이 떨어지지 않는다
3. 회사 레포 3곳도 각자의 기각 이력으로 규약을 갖는다

---

## 3. 설계

### 3-1. 핵심 판단 — 차단이 아니라 맥락 제공

효과가 입증된 유일한 방식(규약 주입)을 자동화한다. 지적을 막는 게 아니라 **봇에게 이 레포의
사정을 알려준다.** 진짜 결함을 발견하면 여전히 지적할 수 있다.

사용자가 기각하며 쓴 답변이 이미 규약 문서다. 카드 373 의 기각 이유는 판단과 근거 12곳을
담고 있다. 그 텍스트를 그대로 쓴다 — **새 LLM 호출 0회.**

### 3-2. 데이터 흐름

```
pr_review_finding (status='REJECTED', rejectReason IS NOT NULL)
        │  레포별 · 카테고리별 집계, SECURITY 제외, 90일 이내
        ▼
findRejectionsForConventions()          ← 포트 메서드 1개 추가
        │
        ▼
renderLearnedConventions(rows)          ← 순수 함수
        │
        ▼
리뷰 프롬프트의 규약 자리 (buildRepoConventions 바로 뒤)
```

**DB 스키마 변경 0, 새 테이블 0, 새 모듈 0.** 상태는 이미 `pr_review_finding` 에 전부 있다.
조회 시점에 만들므로 저장할 것이 없고, "90일 이내"라는 조회 조건이 곧 만료다.

배선도 이미 되어 있다 — `CodeReviewerModule` 이 `PrReviewPublishModule` 을 import 하고,
그쪽이 `PR_REVIEW_FINDING_REPOSITORY_PORT` 를 export 한다.

### 3-3. 선별 규칙

| 항목 | 값 | 근거 |
|---|---|---|
| 임계 | 카테고리당 기각 **2건** 이상 | 3이면 `RELIABILITY`(2건)가 빠진다. 차단이 아니므로 낮게 잡아도 피해가 작다 |
| 노출 | 카테고리당 최신 **2건** | 전부 넣으면 `CORRECTNESS` 7건이 프롬프트를 희석한다 |
| 이유 길이 상한 | **400자** 컷 | 카드 373 실측 — 판단과 근거 시작까지 들어간다 |
| 이유 길이 하한 | **40자** | 아래 §3-3-1 |
| 기간 | **90일** | 오래된 규약의 자동 소멸 |
| 제외 | **SECURITY** | 안전핀(§3-4) |
| 제외 | `rejectReason IS NULL` | 이유 없는 기각은 학습 재료가 아니다 |

### 3-3-1. 구현 중 실 데이터가 바꾼 것 두 가지

설계대로 만들어 실 데이터를 통과시켰더니 두 가지가 드러났다.

**① 한 줄 요약형 이유가 좋은 사례를 밀어냈다.** 기각 이유 길이는 두 무리로 깨끗이 갈린다.

| 길이 | 예 | 규약 재료로서 |
|---|---|---|
| 9~14자 | `미반영 근거를 제시함`, `상한 전제를 부정` | 무엇이 왜 틀렸는지가 없다 |
| 260자 이상 | 카드 373 (근거 12곳 나열) | 그대로 규약이 된다 |

첫 시도에서 `미반영 근거를 제시함`(카드 401)이 최신이라는 이유만으로 `ARCHITECTURE` 노출
2칸 중 하나를 차지했고, 근거가 실린 카드 193 이 밀려났다. → **하한 40자**를 두어 한 줄
요약을 뺀다. 이유 없는 기각을 빼는 것과 같은 이유다.

효과: `RELIABILITY` 는 근거 있는 이유가 1건뿐이라 카테고리째 빠지고, `schoolbell-e/sbe-api-v5`
는 기각 2건이 모두 `전제 불성립으로 변경 거부`(14자)라 규약이 서지 않는다. 둘 다 옳은 결과다.

**② 여러 줄 이유가 상한에서 잘리면 항목 경계가 흐려진다.** 기각 이유는 코드블록과 목록이
섞인 산문이라, 400자에서 자르면 열린 코드펜스나 목록 조각이 남는다. → 실을 때 **공백을
한 칸으로 눌러** 불릿 하나가 한 줄이 되게 한다.

### 3-3-2. 실 데이터로 확인한 최종 결과 (2026-08-25)

90일 기각 전건을 실제 함수에 통과시킨 결과다.

| 레포 | 90일 기각 | 규약이 선 카테고리 | 블록 |
|---|---|---|---|
| JSL107/personal_agents | 13건 | `ARCHITECTURE`(2) · `CORRECTNESS`(5) | 1,877자 |
| schoolbell-e/sbe-api-v5 | 2건 | 없음 (둘 다 14자 요약) | 0자 |
| schoolbell-e/sbe-api-v5-puppeteer | 1건 | 없음 (임계 미달) | 0자 |

`ARCHITECTURE` 두 자리에는 의도한 대로 카드 373·193 — 근거를 각각 12곳·4곳 나열한 답변 —
이 들어갔다. 이 기능이 없애려던 반복 지적의 원인이 정확히 그 두 건이다.

### 3-4. 안전핀

- **SECURITY 는 영구 제외.** 바빠서 넘긴 보안 경고를 학습해 침묵하는 사고를 막는다.
  현재 SECURITY 기각은 0건이라 당장 걸리는 것도 없다
- **차단하지 않는다.** 규약은 맥락일 뿐이고 게시 경로는 손대지 않는다. 잘못된 규약이 들어가도
  모델이 판단해 지적할 수 있다
- **90일 만료.** 규약이 코드가 아니라 조회 결과라 오래된 기각은 저절로 빠진다
- **적용 사실을 남긴다.** 어떤 카테고리 규약이 몇 건으로 적용됐는지 로그로 찍는다

### 3-5. 기존 되먹임 제거

`buildNegativeExamples` 와 `recallRejectedComments` 를 **삭제**한다.

- 실효가 없음이 실증됐다(§1-2)
- 새 규약이 같은 자리·같은 목적을 대체한다
- 남겨두면 같은 내용이 프롬프트 두 곳에 실려 희석된다. 충돌하는 지시는 덧붙이는 것보다
  치환해야 한다

`episodic_memory` **적재는 유지**한다. 기록 가치가 있고, 지우는 것은 되돌리기 어렵다.
소비처만 교체된다.

## 4. 범위 밖

- **REVIEW_REPLY_JUDGE 오판** — 카드 57 은 답글이 "타당합니다, 추가했습니다"인데 `REJECTED`
  가 됐다. 수용을 기각으로 읽은 판정 오류이며 별도 과제다. 이번 변경은 그 카드를 규약 후보로
  쓸 수 있으나, 다른 레포(PR #103)라 이 레포 규약에는 들어가지 않는다
- **이유 없는 기각 2건**(카드 226·296) — `rejectReason IS NULL` 필터로 자동 제외된다
- **억제 게이트** — 채택률 기반 차단은 만들지 않는다. 데이터가 여전히 반대 신호를 준다
  (`TEST` 98% · `CORRECTNESS` 94%)
- **검색 축 교정** — episodic 벡터 검색 자체는 손대지 않는다. 소비처가 사라지므로 의미가 없다

## 5. 위험

- **기각 이유가 부정확하면 그 오해가 규약이 된다.** 90일 만료와 "차단 아님"으로 완화하되,
  완전히 막지는 못한다
- **카테고리 묶음이 거칠다.** `CORRECTNESS` 기각 7건은 서로 다른 주제인데 한 카테고리로 묶인다.
  최신 2건만 노출해 희석을 줄이지만, 무관한 사례가 규약에 섞일 수 있다. 의미 단위로 묶으려면
  임베딩이나 LLM 이 필요한데, 거리 분리가 안 된다는 것을 §1-2 에서 실측했다
- **프롬프트 길이.** 최악의 경우 6카테고리 × 2건 × 400자 = 4,800자가 더해진다. 현재 실측은
  1,877자(§3-3-2)

## 6. 검증

- 순수 함수(`renderLearnedConventions`) 단위 테스트 16건 — 임계 미달 제외, SECURITY 제외,
  건수·길이 상한/하한, 한 줄 정규화, 빈 입력
- 조회 계약 테스트 — 90일 경계, `rejectReason IS NULL` 제외
- usecase 테스트 — 규약이 프롬프트에 실제로 실리는지, 기존 되먹임이 사라졌는지
- 게이트 `pnpm lint:check` + `pnpm test` + `pnpm build` 3중 green
- 실 DB 대조 — 90일 기각 전건을 실제 함수에 통과시켜 블록 확인 (§3-3-2 완료)

**미검증**

- **실 부팅에서의 DI** — worktree 에 `DATABASE_URL` 이 없어 앱을 띄우지 못했다. 배선은 정적으로만
  확인했다(`PrReviewPublishModule` 이 포트를 export, `CodeReviewerModule` 이 그 모듈을 import).
  옵셔널 주입이라 배선이 틀려도 부팅은 성공하고 규약만 사라지므로, 미주입 시 warn 로그를 남겨
  두었다 — 재기동 후 첫 리뷰 로그에서 `학습 규약 주입` 또는 `카드 저장소 미주입` 중 무엇이
  찍히는지 확인할 것
- **리뷰 품질 변화** — 규약이 실제로 반복 지적을 멈추는지는 머지 후 스윕으로만 확인된다.
  판정 기준은 §2 성공 기준 셋
