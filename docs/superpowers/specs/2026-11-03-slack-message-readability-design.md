# 이대리 Slack 메시지 개편 설계

작성일 2026-11-03. 대표 승인 2026-11-03.

## 왜 바꾸는가

대표가 실제로 열어 읽는 메시지는 아침 요약 하나뿐이다. 나머지 메시지는 받아도 읽지 않고 넘긴다. 대표가 꼽은 이유는 세 가지다.

- 너무 길다.
- 이해하지 못하는 내용이 많다. 영어 라벨, 내부 식별자, 설명 없이 이어 붙인 PR 번호 같은 것들이다.
- 중요하지 않은 내용이 많이 섞여 있다.

메시지별로 들은 반응은 다음과 같다.

| 묶음 | 대표의 반응 |
|---|---|
| 아침 요약, 아침 계획, 비서실 보고 | 셋이 각자 맡은 일이 뚜렷하지 않고, 쓸모 있는 안내나 정보가 오지 않는다 |
| PO 검토 | 아침 보고와 크게 다르지 않다. 무엇을 하라는 건지 모르겠고, 판정 버튼은 무엇을 판정하라는 건지 모르겠다 |
| 저녁 마감, 업무 회고, 하루 평가 | 무엇을 했고 무엇이 안 끝났는지 와닿지 않는다. 한국말로 풀어 써야 한다 |
| 모의투자, 주식 보고 | 10/28 이후로 오지 않는다 (고장, 이 문서 범위 밖) |
| 승인 카드 | 대부분 읽지 않고 발행을 누른다 |
| PR 리뷰, 장애 알림 | 복사해서 다른 AI에 붙여 넣는 것이 전부다 |

그래서 이번 개편은 글을 다듬는 일에서 끝나지 않는다. 메시지마다 "대표의 어떤 질문 하나에 답하는가"를 다시 정하고, 답이 없는 메시지는 합치거나 없앤다.

## 지금 실제로 나가는 구조

Slack 채널에 나가는 본문은 이미 하루 두 통이다. 2026-10-12와 10-22 결정의 결과다(`docs/superpowers/plans/2026-10-08-daily-message-direction.md`, `2026-10-22-slack-send-reduction.md`).

| 시각 | Slack 본문 | 그 스레드에 달리는 것 |
|---|---|---|
| 08:30 | 아침 한 통 (`morning-briefing`, `formatMorningDigest`) | PM 아침 계획, 13:00 PO 검토(`THREAD_UNDER_GROUP`, `autopilot.orchestrator.ts:90`), 승인 카드, 월요일 주간 판정 카드(`loadWeeklyVerdictCards`) |
| 19:40 | 저녁 한 통 (`evening-retro-publish`, `formatEveningDigest`) | 회고 전문, 블로그·경력 승인 카드, 아침 계획 판정 버튼 |

업무 회고(`work-reviewer`), 하루 평가(`daily-eval`), 비서실(`secretariat`), 공고, 공부, 포트폴리오 발행, 모의투자 추천·체결 같은 보고는 `console` 경로다(`autopilot-delivery-route.ts:16-60`). 이 보고들은 Slack에 게시되지 않는다. 전문은 원장(`slack_delivery`)에 남아 콘솔 앱에서 보이고, 아침·저녁 한 통에 한 줄씩 요약돼 실린다.

따라서 이번 개편은 발송 경로를 합치는 일이 아니다. 다음 세 가지를 바꾸는 일이다.
- 아침·저녁 한 통의 본문 구성
- 그 스레드에 달리는 것
- 콘솔 보고의 문장

워커(`work-reviewer`, `daily-eval`, PM)는 그대로 돈다. 이 워커들의 출력에 기대는 곳이 있기 때문이다.
- `cuj-check.ts:119`는 세 워커의 원장 행을 매일 확인한다.
- `evening-retro-publish`는 업무 회고와 하루 평가 전문을 재료로 쓴다.
- CEO, 주간 요약, PO_EVAL은 PM과 PO_SHADOW의 출력을 읽는다.

## 모든 메시지에 적용하는 글쓰기 규칙

1. 줄표(`U+2014`)를 쓰지 않는다. 제목과 부연은 줄바꿈, 괄호, 쉼표로 나눈다.
2. PR이나 이슈를 번호만으로 부르지 않는다. 무슨 일인지 한국말 한 구절로 쓰고, 번호는 링크로만 붙인다.
3. 내부 식별자를 보여 주지 않는다. `run #11198`, `codex-cli` 같은 모델 이름, `schemaVersion`, enum 값, 환경변수 이름이 여기에 해당한다.
4. 영어 라벨을 쓰지 않는다. `Daily Eval`, `Wins`, `Blockers`, `Work Reviewer`, `Headline` 같은 것들이다.
5. 오류 원문을 붙이지 않는다. 무엇이 멈췄는지와 지금은 괜찮은지만 쓴다.
6. 설명 없는 기호를 쓰지 않는다. 예를 들어 계획 줄 앞의 `⏭ ⚠ 🔁`이 그렇다.

이 규칙은 템플릿 formatter와 LLM 시스템 프롬프트 양쪽에 넣는다. 긴 본문 대부분은 LLM이 쓴 글을 그대로 통과시킨 것이라, formatter만 고쳐서는 줄지 않는다. 기존 금칙어 검사(`src/slack/format/internal-terms.ts`)에 1~5번 규칙을 더해 테스트에서 걸러지게 한다.

## 1. 아침 한 통 (결정됨)

08:30 아침 한 통(`formatMorningDigest`)의 본문을 아래 구성으로 바꾼다.
- 스레드의 PM 아침 계획 전문(3,000자 안팎)은 더 달지 않는다. PM 실행은 계속 돌고, 그 출력이 "오늘 할 일"의 재료가 된다.
- 비서실 보고는 지금처럼 콘솔에만 남긴다.

```
☀️ 11/4(수) 아침

오늘 할 일
• 상벌점 입장 링크가 조건대로 열리는지 확인
• 공지 첨부파일 저장 오류 고치기 (3일째)

어제 장애
• 포트폴리오 사이트 발행 실패, 지금은 복구됨

오늘 일정
• 14:00 팀 회의
• 18:00 이력서 제출 마감
```

**오늘 할 일**
- 한 줄에 하나씩 한국말로 쓴다. PR 제목을 그대로 붙이지 않는다.
- 할 일은 여러 날에 걸쳐 추적한다. 끝나지 않은 일은 다음 날로 넘어가고 "(N일째)"를 붙인다.
- PR 머지처럼 이대리가 끝난 걸 알 수 있는 일은 자동으로 완료 처리한다.
- 아침 메시지에는 버튼을 달지 않는다.

**어제 장애**
- 무엇이 멈췄는지와 지금 상태만 쓴다. 오류 원문은 넣지 않는다.

**오늘 일정**
- 이대리에 등록한 일정(`ScheduleItem`)을 시각순으로 보여 준다. 외부 캘린더는 연결하지 않는다.

**그 밖에 칸**
- 지금 아침 한 통에 한 줄씩 실리던 콘솔 보고(투자, 공부, 공고, 포트폴리오 발행, 승인 대기)는 세 칸 아래 "그 밖에" 칸에 한 줄씩 남긴다.
- 이 줄들이 해당 보고가 Slack에 닿는 유일한 길이기 때문이다. 대표도 "다 와야지"라고 했다.
- 공고 줄은 공고 알림 선점(`claimForNotification`, `morning-briefing.autopilot-task.ts:711-735`)을 함께 맡고 있으므로 지우지 않는다.

**어제 장애 칸의 범위**
- 아직 열려 있는 장애는 "N일째"와 함께 쓴다. 지금 아침 한 통이 쓰는 7일 창과 같다.
- 어제 해결된 장애도 함께 쓴다.

**오늘 일정 칸의 범위**
- 지난 미완 마감은 "지남"으로 계속 보여 준다. 지금 일정 줄(`schedule-briefing.formatter.ts`)과 같다.
- 공휴일 행은 뺀다(`!item.isHoliday`).

**새로 만들어야 하는 것**
- 할 일 추적 저장소가 필요하다. 항목마다 다음을 갖는다.
  - 고정 ID와 처음 나온 날
  - 마지막으로 확인한 날
  - 완료한 날, 무엇을 보고 완료로 판단했는지, 출처 링크
- 같은 일이 다시 나오면 ID를 유지한다.
- 외부 항목과 맞는지 확실하지 않으면 자동 완료하지 않는다.

**먼저 재사용할 것**
- PM에 이미 며칠째 추적이 있다. `computeConsecutiveDaysById`(`src/agent/pm/domain/stale-task.util.ts`)와 `DailyPlan` 이력이다.
- 1단계는 이것으로 "(N일째)"를 낸다. 새 저장소는 자동 완료와 저녁 비율이 필요한 2단계에서 만든다.

**빌더 판단**
- 저장소를 `ScheduleItem`에 얹을지 새 모델로 만들지는 구현 단계에서 정한다. `ScheduleItem`에는 ID, 상태, `completedAt`이 이미 있다. 없는 것은 출처 키와 완료 근거다.
- 이대리가 끝을 알 수 없는 일(회의 준비 등)은 콘솔 앱에서 체크하거나 멘션으로 끝낸다.

## 2. PO 검토를 주간 일 점검으로 (결정됨)

### 지금 PO 봇이 실제로 하는 일

| 항목 | 지금 상태 | 근거 |
|---|---|---|
| 기본 동작 | 아침 계획과 정오 실제 목록을 대조해 "계획과 다른 점"을 최대 3개 짚는다 | `po-shadow-system.prompt.ts:15`, `:33` |
| 추가 재료 | 지난 지적이 어떻게 됐는지 회수한 결과와 제품 목표 사실을 함께 받는다. 다만 활성 제품 목표는 현재 0건이라 목표 기능은 실제로 아무것도 하지 않는다 | `generate-po-shadow.usecase.ts:139-160`, DB `product_goal` 1건(닫힘) |
| 여러 날 흐름 | 지적했던 항목은 7일마다 다시 올라온다. 하지만 한 번도 지적하지 않은 장기 정체는 보이지 않는다 | `plan-reality.diff.ts:105-112`, `:248-267` |
| 결과 확인 | "지난 지적 N건"은 자기 지적이 반영됐는지를 센다. 일의 결과를 세지 않는다 | `po-shadow.formatter.ts:104-134` |
| 결정권 | 사람이 정하고 봇은 권고만 한다 (의도한 설계) | `2026-09-10-po-shadow-product-owner-upgrade-design.md:113-120` |

재료가 아침 계획과 같은 GitHub 담당 목록이다 보니 할 수 있는 말이 "계획과 목록이 다르다"로 좁다. 대표가 원하는 것은 "하던 일에 대한 분석"이다.

### 무엇을 바꾸는가

**보내는 시점**
- 매일 13:00 아침 한 통 스레드에 달던 PO 검토를 멈춘다.
- 대신 월요일 아침 한 통 맨 끝에 "지난주 일 점검" 칸을 붙인다. 대표가 실제로 읽는 통로가 아침 한 통뿐이기 때문이다.
- 분석 기간은 지난 월요일 00:00부터 이번 월요일 00:00까지(KST)다.
- 할 말이 없으면 칸을 그리지 않는다.
- 조회가 실패하면 "없었다"고 단정하지 않고 "확인하지 못함"이라고 쓴다.

**목표 점검 DM은 따로 둔다**
- 월요일 09:15 목표 점검(`goal-checkin`)은 지금처럼 대표 DM으로 보낸다.
- 아침 한 통에 합치지 않는 이유는 목표 답을 DM에서만 받기 때문이다(`router-message.handler.ts:1281`). 아침 한 통은 채널(`AUTOPILOT_TARGET`)로 나간다.
- 목표를 닫는 카드(버튼)도 이 DM에 그대로 둔다.

**목표를 묻는 방식 바꾸기**
- 지금은 "요즘 머릿속에 있는 목표가 있어요?"(`GOAL_QUESTION_TEXT`, `product-goal.formatter.ts:154`)라고만 묻는다. 대표는 "이렇게만 물어보니 떠오르는 게 없다"고 했다.
- 활성 목표가 없으면 빈 질문 대신 **이번 주 목표 후보 2~3개를 이대리가 먼저 제안**한다.
  - 후보 재료는 지난주에 일이 몰린 곳, 오래 걸리는 일, 이번 주 일정(마감)이다.
  - 후보 문장은 LLM이 쓰되 재료에 있는 일만 쓴다.

```
이번 주 목표, 이 중에 있을까요?
1. 상벌점 입장 링크를 이번 주 안에 배포까지
2. 공지 첨부파일 오류 리뷰 끝내고 닫기
3. 금요일 이력서 마감 전에 경력 기록 정리
번호로 답하거나 직접 적어 주세요.
```

- 답은 지금처럼 DM으로 받는다.
- 번호로 답하려면 제안한 후보 원문이 저장돼 있어야 한다. 그래서 `GoalQuestion`에 후보 목록 칸(Json)을 추가한다. 스키마는 추가만 한다.
- 번호 답은 `saveGoalAnswer` 앞에서 저장된 후보 문장으로 바꾼다.
- 직접 적으면 지금처럼 초안을 정리해 보여 준다(`goal-draft.prompt.ts`, `handle-goal-answer.usecase.ts`).
- 질문 표지(`markQuestionAsked`)는 발송이 성공한 뒤에만 남긴다. 지금 동작과 같다.
- 활성 목표가 있으면 후보 제안 대신 지금처럼 진행 상황을 점검한다.

**분석 세 가지** (칸 전체 최대 2항목, 600자 이내)

1. **오래 걸리는 일**
   - 할 일 추적에서 5일 이상 열려 있는 일 가운데 하나를 고른다.
   - 막힌 이유는 근거가 있을 때만 쓴다. 근거가 될 수 있는 것은 리뷰어 무응답, 승인됐지만 머지 안 함, 내 차례, 드래프트다. 이 분류는 코드가 한다.
   - 다음 행동은 LLM이 제안하고 "제안"이라고 표시한다. 근거가 없으면 쓰지 않는다.
2. **일이 몰린 곳**
   - 지난주 머지한 PR을 저장소별로 센다. 코드가 계산한 사실이다.
   - 활성 목표가 있을 때만 목표별 비중을 더한다.
   - 머지 건수는 작업량이나 성과가 아니라 건수라는 점을 문장에서 지킨다.
3. **미뤄도 될 후보**
   - 코드가 오래 정체되고 목표와 이어지지 않은 일을 후보로 뽑는다.
   - LLM은 그중 최대 1개를 골라 이유를 쓰고 "제안"으로 표시한다.
   - 결정은 대표가 한다.

**판정 버튼과 "지난 지적 N건"**
- 판정 버튼(맞았음/이미 알던 것/틀림)은 없앤다.
- "지난 지적 N건" 통계는 메시지에서 뺀다.
- 과거 판정 기록(`AgentRunVerdict`)과 과거 실행 출력은 읽을 수 있게 남긴다.
- 금요일 주간 요약의 "PO 회수 대조" 줄(`buildRecoveryHealthLine`, `weekly-summary.autopilot-task.ts:223-260`)은 지운다. 회수 기능이 없어지면 이 줄은 늘 의미 없는 값을 내기 때문이다. 관련 상수와 테스트도 함께 지운다.

```
지난주 일 점검
• 공지 첨부파일 저장 오류가 8일째 열려 있어요. 리뷰 답변을 기다리는 중이에요.
  제안: 담당자에게 남은 리뷰를 한 번 더 요청해 보세요.
• 지난주에는 상벌점 쪽 변경을 6건 합쳤어요.
  제안: 알림 설정 작업은 다음 주로 미뤄도 될 것 같아요.
```

**유지하는 것**
- `AgentType.PO_SHADOW`, exhaustive 4곳, 재실행 switch, `/po-shadow` 수동 실행은 유지한다. 수동 실행은 같은 주간 분석을 즉시 보여 준다.
- 이름을 바꾸면 과거 원장 값과 4곳이 모두 흔들린다.

**고치는 것**
- 주간 분석은 PM 계획을 선행조건으로 쓰지 않는다.
  - 지금은 18시간 안의 PM 계획이 없으면 `STALE_PLAN`으로 끊긴다(`generate-po-shadow.usecase.ts:66`, `:101-127`, `po-shadow.autopilot-task.ts:40`).
  - 월요일 08:00에는 늘 23.5시간 전 계획뿐이라 매번 끊긴다. 주간 경로에서는 이 조건을 뺀다.
- 주간 실행의 분석 기간(시작, 끝)을 `inputSnapshot`에 저장한다. 재실행(`replay-failed-run.usecase.ts:268-281`)은 그 기간을 다시 쓴다.
  - 재실행 결과의 Slack 포맷(`retry-run.handler.ts:127-135`)도 새 포맷터로 바꾼다.
- PO_EVAL은 PO_SHADOW 최신 실행을 읽는다(`generate-po-evaluation.usecase.ts:135-137`). 새 출력 형태를 읽도록 고치고, 7일 창 밖이면 빈 입력으로 진행하는 지금 동작을 유지한다.
- `RUN_DELIVERY_TARGETS`(`run-delivery.ts:35`)의 `autopilot:noon` 좌표를 정리한다.
- 출력 계약이 바뀌므로 `agent-contract.ts`의 출력 필드를 갱신한다.
- `worker-capability.ts:54`의 "PRD 검토" 광고 문구를 실제 동작에 맞춘다.
- 자연어 분류 eval에 "일 점검해줘"와 하루 평가의 "이번 주 정리해줘"를 가르는 사례를 더한다.

**바꾸는 순서**
- 먼저 새 경로를 만들고 발송을 전환한다.
- 그다음에 정오 대조 코드(`plan-reality.diff.ts`의 계획 대조 부분, 회수 블록, 버튼 배선)를 지운다.

**새로 필요한 데이터**
- 1절의 할 일 추적 저장소가 필요하다. 분석 1의 재료다.
- PR 생성 시각이 필요하다. 지금 PR 요약 타입에는 `createdAt`이 없다(`github.type.ts:98-111`). GitHub 응답에는 이미 들어 있으므로 port, type, adapter까지 전달하면 된다.

**빌더 판단**
- 5일, 14일 같은 경계값은 대표가 바꿀 수 있게 상수 한 곳에 둔다.
- 일수는 달력일로 센다.

## 3. 저녁 한 통 (결정됨)

19:40 저녁 한 통(`formatEveningDigest`)의 본문을 아래 구성으로 바꾼다.
- 업무 회고와 하루 평가는 지금처럼 콘솔 보고로 남는다. 다만 콘솔 보고의 문장에도 공통 글쓰기 규칙을 적용한다.
- 대표가 "와닿지 않는다"고 한 문장은 저녁 스레드의 회고 전문과 콘솔 보고 양쪽에 있다.

```
🌙 11/4(수) 마감

한 일
• 상벌점 입장 링크 확인 끝
• 공지 첨부파일 저장 오류 수정, 리뷰 요청까지 보냄

못 한 일
• 알림 설정 화면 (2일째, 내 차례)
• 학교 관리자 화면 (5일째, 리뷰 답 기다리는 중)

숫자로 보면
• 아침 할 일 4개 중 2개 끝냄 (50%)
• 남을 기다린 일 1개, 리뷰 요청 후 3일째 답 없음
• 밀린 일 2개: 내 차례 1개, 남 기다림 1개

아쉬운 점
• 오전에 리뷰 요청을 보내지 못해서 답이 내일로 밀렸어요.

잘한 점
• 오류 원인을 오전에 찾아서 같은 날 고쳤어요.

내일 추천
• 알림 설정 화면부터 끝내세요. 내 차례로 남은 유일한 일이에요.
```

**한 일 / 못 한 일**
- 아침 한 통의 할 일 목록과 그대로 이어진다. 아침 할 일이 저녁에 "한 일" 또는 "못 한 일"로 갈린다.
- 못 한 일은 다음 날 아침에 "(N일째)"로 다시 나온다.
- 아침 목록 밖에서 끝낸 일(머지한 PR 등)도 "한 일"에 넣는다.

**숫자 세 가지**
- **끝낸 비율**: 아침 할 일 중 오늘 완료된 수를 아침 할 일 수로 나눈다.
- **멈춘 시간**: 남의 응답을 기다리느라 멈춘 일과 그 기간을 쓴다. 예를 들면 리뷰 요청 후 응답 없음, 승인 대기 같은 것이다.
  - 대표가 실제로 손을 놓고 있던 시간은 이대리가 알 수 없어서 재지 않는다.
  - 기간은 GitHub의 리뷰 요청 시각과 첫 응답 시각으로 센다. 지금 신호(`PullRequestEngagementSignals`)에는 시각이 없다. 그래서 GitHub 타임라인을 조회해 port, type, adapter까지 넘긴다.
  - 조회가 실패하거나 잘리면 기간을 쓰지 않는다.
- **밀린 일 개수와 누구 차례인지**: 못 한 일을 "내 차례"와 "남 기다림"으로 나눠 센다.
  - 분류는 `classifyPullRequestEngagement`(`classify-pr-engagement.ts`)의 결과를 enum으로 올려서 쓴다. 자유 문장(`WaitingItem.reason`)을 파싱하지 않는다.
  - "승인됨, 머지만 남음"은 내 차례로 센다.
  - 근거가 없으면 "확인 못 함"으로 따로 센다. 근거 없이 "내 탓"으로 몰지 않는다.
  - 아침 목록이 없거나 비어 있으면 끝낸 비율은 쓰지 않는다.

**말로 쓰는 칸**
- 아쉬운 점, 잘한 점, 내일 추천은 LLM이 쓴다. 각각 최대 1개다.
- 위 숫자와 할 일 목록에 있는 사실만 근거로 쓴다.
- 내일 추천은 다음 날 바로 할 수 있는 행동 하나로 쓴다.

**빠지는 것**
- 영어 제목과 라벨: "Work Reviewer", "Daily Eval", "Wins", "Blockers", "Headline"
- `_model: … · run #N_` 푸터
- "합성 source" 줄
- 저녁 회고의 판정 버튼. 대표가 무엇을 판정하라는 건지 이해하지 못했다.

**저장만 하는 것**
- 이력서용 기록(careerLog)은 메시지에 보이지 않게 하고 저장만 한다. 경력 기능이 읽는 데이터라 저장은 유지한다.

**워커는 합치지 않는다**
- `work-reviewer`, `daily-eval`, `evening-retro-publish`는 그대로 돈다.
- 바꾸는 것은 저녁 한 통의 본문과 각 워커가 쓰는 문장뿐이다.

## 4. 승인 카드 (결정됨)

대표는 승인 카드를 대부분 읽지 않고 누른다. 그렇게 해서 생긴 문제는 "발행된 글의 윤문 품질이 좋지 않다" 정도다.

**카드는 남긴다**
- 블로그, 노션, 포트폴리오 사이트 발행은 밖으로 나가는 일이라 자동 처리로 바꾸지 않는다.

**카드를 다섯 줄 안팎으로 줄인다**

```
📝 블로그 발행할까요?
제목: 메시지를 줄였더니 읽히기 시작했다
어디로: 노션 블로그
첫 문단: 이대리가 보내는 메시지를 하루에 몇 통이나 읽는지 세어 봤다…
[발행] [보류]
```

- 무엇을, 어디로 내보내는지만 쓴다.
- 결과물의 첫 문단은 **본문이 이미 있는 카드에만** 보여 준다(GitHub 공개 발행).
  - 저녁 블로그 후보 카드는 승인한 뒤에 본문을 만든다(`evening-retro-publish.autopilot-task.ts:345`, `evening-blog-publish.applier.ts`). 그래서 제목, 쓸 가치 한 줄, "승인하면 초안을 만들어 노션에 올려요"만 쓴다.
  - 승인 전에 없는 문단을 지어내 보여 주지 않는다.
- 점수, 근거 PR 목록, 초안 개요, 처리 과정 설명은 뺀다.
- 경력 반영 카드(현재 2,100~2,700자)도 같은 틀로 줄인다. 무엇이 어떻게 바뀌는지를 한 줄로 쓰고, 바뀐 전문은 스레드에 둔다. 입력 안내("아래 칸에 적으면")는 남긴다.

**줄이지 않는 것**
- GitHub 공개 발행 카드의 전문 첨부 파일은 남긴다(`blog-github-publish.autopilot-task.ts:145-168`). 공개 저장소에 올라갈 글의 익명화를 확인하는 근거다.
- 카드 원문(`previewText`)은 지금처럼 전문을 저장한다. 콘솔 승인 상세(`ApprovalDetailSheet.swift`)와 선호 학습 신호(`preview-decision.signal-source.ts`)가 읽는다.
- Slack에 보이는 짧은 문장은 따로 만든다.

**범위 밖**
- 발행물의 윤문 품질은 메시지 문제가 아니라 글 생성 품질 문제다. 따로 다룬다.

## 5. PR 리뷰, 장애 알림 (결정됨)

대표는 이 메시지를 받으면 다른 AI에 복사해 붙여 넣고 "고쳐 줘"나 "설명해 봐"를 시킨다. 그래서 두 가지를 바꾼다.
- "설명해 봐"는 메시지가 직접 해 준다.
- "고쳐 줘"는 붙여 넣을 재료를 이대리가 미리 만들어 둔다.

**본문: 설명을 먼저 쓴다**

```
🔴 포트폴리오 사이트 발행이 멈췄어요
무슨 일: 오늘 저녁 발행이 두 번 연속 실패했어요.
영향: 새 글이 사이트에 안 올라가요. 다른 기능은 정상이에요.
짐작되는 원인: 사이트 쪽 로그인이 만료된 것 같아요. (추정)
지금 상태: 내일 아침에 한 번 더 자동으로 시도해요.
```

- 항목은 무슨 일, 영향, 원인, 지금 상태 네 가지만 쓴다.
- 알림 경로에서는 LLM을 부르지 않는다. 모델 쿼터가 장애 원인이면 알림까지 조용히 사라지기 때문이다.
  - "무슨 일"은 task 이름의 한국어 이름표로 쓴다.
  - "원인"은 오류 종류별 고정 문구 사전으로 바꾼다. 예를 들면 로그인 만료, 쿼터 소진, 시간 초과다. 사전에 없으면 "원인 확인 중"이라고 쓴다.
  - "지금 상태"는 다음 실행 시각처럼 코드가 아는 사실만 쓴다.
- 오류 원문, 내부 task 이름(`blog-github-publish` 등), 환경변수 이름은 본문에 쓰지 않는다.

**스레드: "AI에 맡기기" 블록**

```
아래를 Claude Code에 그대로 붙여 넣으면 됩니다.
```

- 그 아래 코드 블록 하나에 다음을 담는다.
  - 저장소 경로, 실패한 기능
  - 오류 원문(지금 `notification.consumer.ts`가 본문에 붙이는 1,500자), 관련 파일 경로
  - 재현 또는 확인 명령, 실행 기록 위치
- 내부 식별자는 여기에만 둔다. 사람이 아니라 AI가 읽는 칸이기 때문이다.

**PR 리뷰도 같은 틀을 쓴다**
- 본문에는 리뷰가 무엇을 지적했는지와 고쳐야 하는지를 쉬운 말로 쓴다.
- 스레드에는 PR 링크, 지적 위치, 지적 원문을 담은 "AI에 맡기기" 블록을 둔다.
- PR 리뷰 스윕은 이미 콘솔 경로이고 이상이 있을 때만 올린다. 바꾸지 않는다.

**범위 밖**
- 버튼 하나로 이대리가 직접 고치게 하는 기능은 이번에 만들지 않는다. 코드를 바꾸는 자동화라 따로 설계한다.

## 6. 나머지 메시지 (결정됨)

아래 메시지는 모두 지금 경로 그대로 둔다. 끄거나 경로를 바꾸지 않는다.
- Slack으로 직접 나가는 것: 운세, 주식 스크리너, 모의투자 장마감·채점, 주간 요약(CEO 주간 회고 포함), 영향 보고
- 콘솔에 남고 아침·저녁 한 통에 한 줄로 실리는 것: 공부 브리프, 채용 공고와 공고 분석, 포트폴리오 발행, 모의투자 추천·체결, 실행 회고, 메모리 정리

대신 "모든 메시지에 적용하는 글쓰기 규칙" 1~6번을 이 메시지들에도 적용한다.
- formatter의 영어 라벨, 줄표, 내부 식별자를 고친다.
- LLM이 본문을 쓰는 메시지는 시스템 프롬프트에 같은 규칙을 넣는다.
- 모의투자의 `LONG_TERM`, `SWING` 같은 계좌 이름은 "장기투자", "단기매매"로 바꾼다. 차트 범례가 이미 그렇게 쓰고 있다.
- 금칙어 테스트는 이 메시지들의 formatter에도 건다.

## 구현 전에 정해 둔 것

아래는 설계 판단이다. 대표가 바꿀 수 있다.

1. **할 일이 들어오는 입구와 "같은 일" 판정**
   - 입구는 두 가지다.
     - 아침 계획(PM)이 쓰는 GitHub 담당 이슈·PR
     - 대표가 멘션으로 직접 추가한 할 일
   - 같은 일인지는 출처 키로 판정한다. GitHub 항목은 PR·이슈 URL, 직접 추가한 일은 저장소가 발급한 ID다.
   - LLM이 한국어로 고쳐 쓰는 것은 화면 문구뿐이고 키에는 쓰지 않는다.
   - PR이 다시 열리면 같은 항목을 다시 연다.
   - GitHub 조회가 실패한 날은 아무것도 완료로 처리하지 않는다. 조회 실패를 "0건"으로 확정하지 않는다(`work-reviewer.autopilot-task.ts:70-83`과 같은 원칙).
   - 콘솔에서 체크하는 기능은 이번 범위 밖이다. 완료는 자동 판정과 멘션("@이대리 그거 끝났어")으로만 한다.
2. **끝낸 비율의 분모**
   - 아침 발송 때 그날 보여 준 할 일 목록을 날짜별로 따로 저장한다.
   - 저녁 비율은 이 기록을 분모로 쓴다.
3. **월요일 주간 칸이 만들어지는 시각**
   - 주간 분석은 월요일 08:00에 먼저 돌린다. 08:30 아침 한 통은 그 결과만 읽는다.
   - 결과가 없거나 실패했으면 칸에 "지난주 점검을 만들지 못했어요" 한 줄만 쓴다. 다시 돌리지 않고 다음 주로 넘긴다.
   - 아침 한 통은 늦추지 않는다.
   - 할 말이 없을 때(조회는 성공했고 항목이 0개)는 칸을 그리지 않는다.
   - 배포 뒤 첫 몇 주는 추적 기록이 짧다. 5일을 채운 항목이 없으면 "오래 걸리는 일"을 건너뛴다.
4. **PR이 아닌 할 일의 "누구 차례"**
   - 근거가 없으므로 "확인 못 함"으로 센다.
   - 숫자 세 줄은 합계를 맞추지 않아도 된다.
5. **"AI에 맡기기" 블록과 장애 본문의 오류 원문**
   - 본문과 스레드 모두 기존 `redactPii`(`src/common/util/pii-redaction.util.ts`)를 거친다.
   - URL 속 자격증명(`user:pass@`)과 `password=` 형태도 가린다. 이 둘을 위한 패턴은 이번에 더한다.
   - 확신이 없는 부분은 원문 대신 "로컬 로그 위치"만 안내한다.
   - 원문에 있는 백틱 세 개는 코드 블록이 깨지지 않게 이스케이프한다.
6. **금칙어 테스트 범위**
   - 이미 `internal-terms.jest-setup.ts`가 모든 `*.formatter.ts`와 `*.autopilot-task.ts`의 출력을 검사한다. 여기에 줄표와 "글자 없는 `#번호`" 규칙을 더한다.
   - 새로 검사를 걸 곳은 둘이다. `notification.consumer.ts`의 알림 문구와 `src/slack/handler/**`의 안내 문구다.
   - 코드 블록과 URL은 검사에서 뺀다. 지금 검사기와 같다. "AI에 맡기기" 블록은 코드 블록이라 내부 식별자를 담을 수 있다.
   - 번호 규칙은 "글자 없이 `#번호`만 있는 링크나 문장"을 막는다. "공지 첨부파일 저장 오류(#4746)"처럼 이름 뒤에 붙은 번호는 허용한다.
   - LLM이 쓴 문장은 테스트로 잡을 수 없다. 프롬프트 규칙과 첫 실발송 확인으로 검증한다.
7. **줄표를 걷어 낼 때 함께 고칠 것**
   - 줄표 문자열로 서로 맞물린 생산자와 소비자가 있다. 예를 들어 `portfolio-publish`가 `헤더 — 사유`로 쓰고, `morning-briefing.autopilot-task.ts:232`, `:250`이 줄표로 잘라 읽는다.
   - 이런 곳은 같은 PR에서 구분자를 상수로 빼서 양쪽이 같이 바뀌게 한다.
   - 사람에게 보이는 문자열만 바꾼다. 코드 주석은 건드리지 않는다.
8. **전환 방식**
   - task id와 묶음(group) 이름은 바꾸지 않는다. 그래야 기존의 같은 날 중복 발송 방지 장치(그룹·날짜 guard, `autopilot.orchestrator.ts`)가 그대로 동작한다.
   - 새 메시지와 옛 메시지를 함께 보내는 기간은 두지 않는다. 사용자가 한 명이라 중복 발송이 더 나쁘다.
   - 스키마는 추가만 한다. 되돌릴 때는 코드만 되돌리고 테이블과 칸은 남긴다(`db:push` 가드가 DROP을 막는다).
9. **스케줄과 환경변수**
   - 월요일 08:00 주간 분석은 `po-shadow` task의 cron을 월요일 08:00으로 바꿔 만든다. 묶음은 `noon`에서 뺀다.
   - 기존 `AUTOPILOT_PO_SHADOW_SCHEDULE` override가 `.env`에 남아 있으면 매일 돌 수 있다. 구현 때 `.env`를 확인하고 README와 `.env.example` 안내를 고친다.
   - 아침 묶음의 첫 task id(`secretariat`)는 그대로 둔다. 그래야 `AUTOPILOT_SECRETARIAT_*` override가 계속 먹는다(`autopilot-schedule.ts:42-59`).
   - cron 기본값이 바뀌면 `pnpm docs:sync` 후 `docs/env-catalog.md`를 스테이징한다.
   - LLM 호출은 기존 `AgentType`(PM, PO_SHADOW, 저녁 회고) 안에서만 한다. 새 `AgentType`은 만들지 않는다.
10. **판정 버튼** (아래 「판정 버튼 제거」에 따른다)
    - 이미 게시된 옛 버튼은 배포 후에도 눌릴 수 있다. 처리기는 남겨 두고, 눌리면 저장만 한다.
11. **콘솔 앱**

1. **판정 버튼을 모두 없앤다.**

## 바꾸는 순서

1. **1단계: 문장과 구성**
   - 공통 글쓰기 규칙과 금칙어 테스트를 적용한다.
   - 아침·저녁 한 통의 새 구성을 만든다. "(N일째)"는 PM 이력으로 낸다.
   - 승인 카드, 장애 알림, PR 리뷰, 콘솔 보고의 문장을 고친다.
   - 프롬프트에 규칙을 넣는다.
   - 새 저장소는 만들지 않는다.
2. **2단계: 할 일 추적**
   - 할 일 저장소와 날짜별 아침 목록을 만든다.
   - 자동 완료를 붙인다.
   - 저녁 숫자 세 가지를 낸다. 리뷰 요청 시각 조회와 차례 enum이 여기에 들어간다.
3. **3단계: 주간 일 점검**
   - PO 재설계, 목표 후보 제안(`GoalQuestion` 칸 추가)을 한다.
   - 정오 PO와 판정 버튼을 걷어 낸다.
   - 금요일 주간 요약의 회수 줄을 지운다.

## 검증 기준

- 게이트를 모두 통과해야 한다.
  - `pnpm lint:check && pnpm test && pnpm build`
  - `pnpm check:di`
  - `pnpm check:env && pnpm docs:check && pnpm check:invariants && pnpm test:e2e`
- cron 기본값이나 에이전트 계약이 바뀌면 `pnpm docs:sync`를 돌린다.
- formatter 테스트로 다음을 고정한다.
  - 줄표가 없다.
  - 번호만 있는 PR 표기가 없다.
  - 내부 식별자가 없다.
  - 600자 이하다(주간 칸).
- 문구를 고정하던 기존 spec 중 바꾼 목록을 PR 본문에 적는다.
- 첫 실제 발송 한 통을 대표가 읽고 확인한다.
- 2주 뒤 원장(`slack_delivery`)의 반응 수와 스레드 답글 수로 아침·저녁 한 통이 실제로 읽히는지 다시 본다.
