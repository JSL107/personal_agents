# 목표 대화 — 머릿속 목표를 꺼내고, 매주 점검하고, 매일 아이디어로 잇는다

작성일: 2026-10-21
대상: `src/agent/po-shadow/` (목표 도메인·디스패처·PO 보고), `src/autopilot/` (월요일 점검 태스크), `src/preview-gate/` (목표 카드), `prisma/schema.prisma` (`ProductGoal`)
상태: 설계 — 구현 전 확인 대기

## 1. 왜 다시 설계하나

PO Shadow 단계 3(#773, 2026-10-08)이 `ProductGoal` 을 들여왔지만 **13일 동안 한 번도 쓰이지 않았다.**

| 측정 (2026-10-21, 로컬 DB) | 값 |
|---|---|
| `product_goal` 행 | 0 |
| `preview_action` 중 `PRODUCT_GOAL` 카드 | 0 (생성 이력 자체가 없음) |
| 10-08 이후 라우터를 거친 대화 | 75건 |
| 그중 "목표"가 들어간 대화 | 0건 |
| 같은 기간 PO Shadow 실행 | 매일 (30일 30회) |

등록을 시도했다가 실패한 것이 아니라 **시도한 적이 없다.** 코드에서 확인한 원인은 셋이다.

1. **존재를 알 길이 없다.** 활성 목표가 0개면 PO 보고는 단계 3 이전과 똑같이 나가도록 의도돼 있다
   (`generate-po-shadow.usecase.ts:139-140`). 사용법은 분류기 프롬프트(`worker-capability.ts:56-58`)와 PR 본문에만 있다.
2. **등록 문장이 까다롭다.** `DECLARE_PATTERN`(`product-goal.ts:53`)에 맞는 "분기/제품 목표는 …" 형식에 "달성 기준은"과
   숫자·완료어(`COMPLETION_MARKER`)가 있어야 하고, 하나라도 빠지면 카드 없이 거절된다. 수정 경로는 없다(닫고 재선언).
3. **등록해도 연결이 약하다.** 목표와 작업은 PR·이슈 **제목의 키워드 부분 문자열**로만 잇는다(`isLinkedToGoal`).
   한국어 키워드는 영어 PR 제목에 잡히지 않고, 짧은 키워드는 과하게 잡힌다.

사용자 인터뷰(2026-10-21)에서 확인한 조건:

- 목표의 크기를 하나로 정할 수 없다 — 분기 방향과 이번 달 할 일이 섞인다.
- 목표는 주로 **머릿속**에 있다. 적어 둔 곳이 없다.
- 이대리가 **먼저 말을 거는 것은 언제나 환영**한다.
- 목표가 있으면 듣고 싶은 것: **얼마나 진행됐나 · 달성에 무엇이 부족한가 · 잊은 목표 리마인드 · 목표 기반 아이디어.**
- 주간 점검은 **한 주의 시작(월요일 아침)**, 매일 PO 보고는 **목표 기반 아이디어**를 올린다.

## 2. 목표와 성공 기준

**목표**: 머릿속 목표가 이대리에 들어오고, 그 목표를 기준으로 매주 진척·부족분·리마인드를, 매일 아이디어를 받는다.

**성공 기준 (도입 후 4주 안에 판정)**

- 활성 목표가 1개 이상 등록된다.
- 월요일 점검 4회 중 사용자 반응(버튼·답장·👍/👎)이 2회 이상 있다.
- 매일 아이디어에 대한 👍 가 1건 이상 나온다.

**중단 신호** — 월요일 점검 4회 연속 무반응이거나, 등록된 목표가 4주 안에 0개로 돌아가면 기능 전체를 다시 판정한다
(유지·축소·삭제). 같은 기능이 두 번 "0회 사용"으로 남지 않게 하려는 장치다.

## 3. 범위 밖

- 목표 계층(상위·하위 목표), OKR 구조 — 크기가 섞여도 평면 목록으로 받는다.
- 목표와 작업의 영속 연결 테이블 — 연결은 점검 시점에 AI가 판정하고 결과만 실행 원장에 남긴다(§5-2).
- 노션 등 외부 도구에서 목표 가져오기 — 목표가 머릿속에 있다는 응답에 따라 제외.
- 레포·라벨 기반 연결 — 사용자 요청으로 보류.

## 4. 사용자 흐름

### 4-1. 꺼내기 — 이대리가 묻고, AI가 정리한다

**언제 묻나**

- 월요일 아침 점검 때 활성 목표가 0개면, 점검 대신 질문을 보낸다.
  > 🧭 요즘 머릿속에 있는 목표가 있어요? 크기 상관없이 대충 말해 주세요. 제가 정리해서 보여 드릴게요.
- 분기 첫 월요일에는 목표가 있어도 "이번 분기에 새로 생긴 목표가 있나요?"를 덧붙인다.

**답하면** — 스레드 답장(또는 멘션·DM)을 AI가 목표 초안으로 정리해 확인 카드로 보낸다. 한 답에서 여러 목표가 나오면 각각 카드.

| 칸 | 필수 | 설명 |
|---|---|---|
| 제목 | ✅ | 한 줄 |
| 왜 | — | 이 목표가 중요한 이유. 아이디어 생성의 재료 |
| 끝났다고 볼 기준 | ✅ | 흐릿하면 AI가 한 번 되묻는다: "끝난 건 어떻게 알 수 있을까요?" |
| 기한 | — | 없어도 된다 |

- 승인 ✅ → 등록. "기준은 ~로 바꿔" 같은 답장 → 고친 카드를 다시 보낸다(수정 경로).
- 지금의 정규식 검사(`findGoalDeclarationProblem`)는 **거절 사유에서 되묻기 재료로** 바뀐다. 까다로움을 검사에서 대화로 옮긴다.
- 기존 "분기 목표는 …" 문장 선언과 "목표 보여줘"·"목표 닫아줘"는 그대로 둔다(빠른 경로).

### 4-2. 월요일 목표 점검 — 진척 · 부족분 · 리마인드

매주 월요일 09:00 KST(아침 브리핑 08:30 다음), 활성 목표마다:

> 🧭 **모의투자 추천 엔진 완성** — 지난주 관련 작업 3건 (#870, #872, #875)
> - 진척: 추천은 매일 돌고, 채점(3-B)은 아직 시작 전
> - 부족한 것: 기준 "추천 적중률 측정"에 필요한 채점 로직이 없음
>
> ⏰ **블로그 주 1회** — 3주째 관련 작업 없음. 아직 유효한가요? [유지] [닫기]

- **연결**: 지난 7일의 머지 PR·열린 이슈·PM 계획 항목을 목표 목록과 함께 모델에 주고, 항목별로 어느 목표 일인지(없으면 없음) 판정한다.
  판정 결과는 그 실행의 `inputSnapshot.goalLinks` 에 남긴다. 키워드는 더 이상 필수가 아니다(있으면 힌트로만 쓴다).
- **잊은 목표**: 연속 N주(초기값 2) 연결된 작업이 없으면 리마인드 줄로 바꾸고 [유지]/[닫기] 버튼을 단다. 직전 점검들의 `goalLinks` 로 센다.
- **기한**: 기한 7일 이내·초과는 기존 `GOAL_DEADLINE_RISK_DAYS` 규칙을 그대로 쓴다.

## 5. 구현 설계

### 5-1. 데이터 변경 (`ProductGoal`)

| 변경 | 이유 |
|---|---|
| `why String? @db.Text` 추가 | 아이디어 생성 재료 |
| `keywords` 빈 배열 허용 (`MISSING_KEYWORDS` 거절 제거) | 연결을 AI 판정으로 옮김 |
| `source String` 추가 (`DECLARED` / `INTERVIEW`) | 어느 경로로 들어왔는지 — 성공 기준 판정용 |
| `lastRemindedAt DateTime?` 추가 | 리마인드 중복 방지 |

`pnpm db:push` 대상. 열 추가·제약 완화뿐이라 파괴적 변경 없음(`db-push-guard` 통과 예상).

### 5-2. 구성 요소와 재사용

| 역할 | 위치 | 재사용 |
|---|---|---|
| 목표 초안 생성 (답 → 카드) | `po-shadow` 디스패처에 인터뷰 경로 추가 | `PreviewGate` `PRODUCT_GOAL` 카드·`ProductGoalApplier`·`update-preview-payload`(수정) |
| 월요일 점검 | 새 autopilot 태스크 `goal-checkin` (월 09:00) | `collectProductGoals`·`buildProductGoalFacts`·PO 컨텍스트 수집 |
| 리마인드 버튼 | 점검 메시지의 [유지]/[닫기] | 기존 CLOSE 카드 경로 |
| 매일 아이디어 | `generate-po-shadow.usecase.ts` 프롬프트·포매터 섹션 | `[활성 제품 목표]` 주입부(`:595,626-630`), `SlackReactionSignal` |
| 아이디어 → 일정 | 👍 아이디어를 IDEA_TRIAGE 로 전달 | `JudgeIdeaUsecase` |
| 먼저 말 걸기 빈도 제한 | 점검·질문 발송 | `subconscious` 의 `PROMOTION_BUDGET` 패턴 참고 |

**AgentType 결정** — 월요일 점검을 새 `AgentType` 으로 만들면 AGENTS.md §4 체크리스트(enum exhaustive 4곳·재실행 switch·ResponseCode)를 모두 밟는다.
초기안은 **`PO_SHADOW` 의 실행 모드(`mode: 'GOAL_CHECKIN'`)로 두고** 실행 원장에서 `triggerType` 으로 구분한다.
점검이 독립 비서로 자랄 근거가 생기면 그때 분리한다.

### 5-3. 출력 형태는 코드로 검증한다

연결 판정(`goalLinks`)과 아이디어 목록은 모델 출력을 그대로 쓰지 않는다. `outputSchema` 로 형태를 받고, 코드가 다시 거른다.

- 판정된 `goalId` 가 활성 목표 목록에 있는지, 작업 항목이 입력 목록에 있는지 확인한다. 없으면 버리고 사유를 남긴다.
- 아이디어는 근거로 든 항목이 입력에 실제로 있어야 통과한다. 근거 없는 아이디어는 버린다.

## 6. 단계

| 단계 | 내용 | 완료 판정 |
|---|---|---|
| 1. 꺼내기 | 인터뷰 질문 · 답 → 초안 카드 · 수정 루프 · 키워드 선택화 · 스키마 변경 | 실제 Slack 에서 답 한 번으로 목표 1개 등록 |
| 2. 월요일 점검 | `goal-checkin` 태스크 · AI 연결 판정 · 리마인드 버튼 · 목표 0개면 질문 | 다음 월요일 실제 발송 확인 |
| 3. 매일 아이디어 | PO 보고 섹션 · 반복 방지 · 👍→IDEA_TRIAGE | 1주간 섹션 발송·반응 수집 |
| 4. 판정 | §2 성공 기준·중단 신호로 4주 뒤 평가 | 유지·축소·삭제 중 하나로 결론 |

단계마다 PR 하나. 각 PR 은 `pnpm lint:check && pnpm test && pnpm build` 와 DI 검사를 통과해야 한다.

## 7. 위험

- **알림 피로** — 월요일 1회 + 매일 아이디어 섹션이 더해진다. 아이디어는 근거 없으면 생략, 하루 2개 상한으로 막는다.
- **AI 연결 판정 오류** — 엉뚱한 작업을 목표에 붙이면 진척이 부풀려진다. 점검 메시지에 연결된 PR 번호를 그대로 보여 줘 사람이 눈으로 확인하게 한다.
- **쿼터** — 월 4회 점검 + 매일 PO 프롬프트 증가분. 2026-10 실측상 쿼터 소진 0건이라 여유가 있다.
- **흐릿한 목표** — 되묻기로 막지만, 그래도 흐릿하면 등록은 허용하고 점검에서 "기준이 흐려 진척을 판정할 수 없음"을 그대로 보고한다.

## 8. 아직 정하지 않은 것

- 잊은 목표 판정 주수(초기 2주)와 아이디어 상한(초기 2개)의 조정 — 단계 4 평가 때 재검토.
- 활성 목표 상한 `MAX_ACTIVE_PRODUCT_GOALS = 3` 유지 여부 — 크기가 섞인 목표를 받으면 3개는 빠듯할 수 있다.
