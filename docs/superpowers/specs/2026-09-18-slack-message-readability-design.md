# Slack 메시지 가독성 개편 — 설계

작성 2026-09-18. 대화로 합의한 내용을 굳힌 문서.
구현 착수 전 상태이며, 미결 항목은 §7에 분리해 둔다.

---

## 1. 문제

> "슬랙에 오는 메시지를 안 읽게 돼."

증상은 세 가지로 진술됐다.

1. 내용이 너무 많고 길어서 이해하기 어렵다.
2. 자율 실행이라 앞선 맥락이 빠져 무슨 말인지 모를 때가 있다.
3. 진짜 핵심은 빠진 채 매일 돌아간다고 느껴진다.

핵심 증상은 "안 읽게 된다"다. 한 번 "안 읽어도 된다"가 학습되면 이후 전부 건너뛰게 되므로,
개별 메시지의 품질보다 **읽을지 말지 3초 안에 판단 가능한가**가 설계 기준이 된다.

### 6번 보강 — 기각이 아니라 방치였다 (2026-09-18 정정)

자율 제안 72건 중 61건 DISMISSED / 11건 DISPATCHED. 제안 종류는 72건 중 65건이
`CODE_REVIEWER` 한 가지.

**DISMISSED 를 "사용자가 기각" 으로 읽은 것은 오판이었다.** `expirePendingOlderThan` 이 만료
카드를 DISMISSED 로 닫고 `dismissSweptPending` 도 스윕이 대신 처리한 카드를 DISMISSED 로 닫으므로,
이 상태값에는 세 부류가 섞여 있다. 응답까지 걸린 시간으로 분해한 실측:

| 구간 | 건수 |
|---|---|
| 10분 내 (사람이 누른 것) | **0** |
| 2시간 내 | 2 |
| 25시간 내 (만료 의심) | 22 |
| 25시간 초과 (만료·스윕) | 37 |

사람이 기각 버튼을 누른 흔적이 사실상 없다. 61건은 거절된 것이 아니라 **보이지 않은 채
소멸**했다. 따라서 중복 억제의 기대 효과는 **소음 감소로 한정**되고, 채택률 개선 효과는 없다 —
17회가 1회로 줄어도 그 1회를 보지 않으면 결과는 같다.

제안 문구 자체는 부적절하지 않았다. 실행분과 소멸분을 대조하면 **같은 대상에 대한 거의 동일한
문구**였다.

- 실행 (2026-09-15) — "PR #2808의 권한·웹훅 재통합 변경을 코드 리뷰할까요?"
- 기각 (2026-09-15) — "PR #2808의 권한 처리와 웹훅 연동을 중심으로 코드 리뷰할까요?"

`change_key` 는 `github:pr:<owner>/<repo>#<번호>` 로 **대상 단위까지 동일**하다. 그런데 같은 키로
새 제안이 계속 생성된다. 원인은 저장소 인터페이스에 있다 —
`subconscious-proposal.repository.port.ts:37` 의 `hasPending(ownerUserId, changeKey, createdAfter)`
은 **PENDING 상태만** 본다. 카드가 만료·기각·실행으로 PENDING 을 벗어나면 같은 키가 다시
통과한다. 주석은 "만료된 PENDING 은 죽은 카드이므로 중복 판정에서 빼야 한다(안 그러면 그
대상의 제안이 영구히 막힌다)" 로 좁힌 이유를 밝히고 있다 — 영구 차단을 피하려던 선택이 17회
반복을 만들었다.

대비되는 수치: `preview_action` 의 승인율은 BLOG_GITHUB_PUBLISH 23/23, EVENING_CAREER_REFLECT
33/38, EVENING_BLOG_PUBLISH 34/40 로 85~100%다. 같은 시스템이 띄우는 카드인데 한쪽은 거의 다
눌리고 한쪽은 아무도 보지 않는다. 승인 카드 발송(`slack.service.ts:285` `postPreviewMessage`)은
멘션을 붙이지 않으므로, **조용한 카드가 잘 눌리고 시끄러운 보고가 안 읽히는** 역전이 일어나
있다. 무엇이 이 차이를 만드는지는 미확인 — §7-4.

### 2026-09-18 착수 중 정정 — 오독 두 건

구현에 들어가 코드를 읽고 나서 앞선 진단 두 건이 틀린 것으로 드러났다. 둘 다 결론을 바꾼다.

1. **"긴 메시지" 의 근거로 든 자수는 Slack 메시지가 아니었다.** `output` JSON 전체 크기를 메시지
   길이로 읽었다. 실제 회고 본문은 210~388자로 이미 짧다. 따라서 3-1(전문 생성 걷어내기)과
   3-2(제목·중요도 모델 출력)의 전제가 약해졌다 — **2단계에서 보류**한다.
2. **스레드 분리는 cron 경로에 이미 있다.** 없는 것은 슬래시 경로인데, 그쪽은 ephemeral 응답이라
   Slack 이 스레드를 허용하지 않는다. 즉 고칠 수 있는 대상이 아니다.

실물로 확인된 과밀은 사용자가 직접 붙여 준 채택률 줄 하나였다(카테고리 7개 · 숫자 15개를 한 줄).
그래서 2단계의 실제 작업은 그 줄로 좁혔다(3-3).

남은 의심: "전반적으로 다 길다" 는 진술과 실측(회고 388자)이 어긋난다. 어느 메시지가 실제로
긴지 아직 특정되지 않았다 — §7-5.

## 3. 합의한 방향

### 3-1. 안 읽을 전문은 만들지 않는다

당초 "핵심은 메인, 전문은 스레드" 로 잡았으나, 전문을 스레드로 옮겨도 읽지 않는다는 진술에
따라 **전문 생성 자체를 걷어내는 쪽**으로 바꿨다.

근거: EVENING_RETRO 의 `prNotes[].note` 는 PR 본문을 재서술한 사본이고, 원본은 GitHub 에 있다.
`ref` 가 `owner/repo#번호` 형태이므로 링크로 만들 수 있다. 사본을 길게 만드는 대신 링크를 걸면
세부가 필요할 때 원본이 열리고, 재서술본보다 정확하다. 생성 시간과 토큰도 함께 줄어든다
(EVENING_RETRO 중위 73초).

목표 형태:

```
어제 운영 장애 2건 수습 — DDD 프로젝트 목록 전체 500
삭제된 기수를 참조하던 데이터가 원인 (#94 복구 · #97 재발 차단)

그 외 6건 — 배너 API · 크롤 로깅 · 인증 폴백 · 리뷰 스윕 · 기각 기록 · 채점표
(#1117 #99 #590 #591 #595 #594)
```

`#번호` 는 전부 PR 링크. 스레드 없음.

### 3-2. 제목과 중요도는 모델이 함께 낸다

현재 `prNotes` 의 필드는 `ref` 와 `note` 둘뿐이다. 무엇이 운영 장애이고 무엇이 로깅 추가인지,
각 항목의 제목이 무엇인지가 데이터에 없다. 따라서 formatter 수정만으로는 위 형태가 나오지
않는다.

`note` 의 `—`(대시) 앞을 제목으로 잘라 쓰는 방안을 검토했고, 모델을 건드리지 않는 장점이
있었다. 그러나 3-1 에서 전문 생성을 걷어내기로 하면서 **모델 지시를 어차피 바꿔야** 하므로
제목·중요도도 모델 출력에 포함하는 쪽으로 정했다.

주의: 모델이 중요도를 과대평가하는 경향이 있다(전부 최상위로 매김). 기준을 프롬프트에 박고,
실제 분포를 실측해 검증할 것.

### 3-3. 변화만 앞세운다

매일 같은 숫자가 오면 읽지 않게 되므로, **달라진 것만** 본문에 올리고 나머지는 한 마디로
묶는다. 실례 — 다음 메시지가 실제로 발송된 형태다.

```
📊 채택률(최근 14일 · JSL107/personal_agents) TEST 94%(69) ↓5%p · CORRECTNESS 93%(55) → ·
RELIABILITY 100%(21) ↑4%p · READABILITY 100%(16) · SECURITY 표본 7 · ARCHITECTURE 표본 1 ·
STYLE 표본 1
```

한 줄에 카테고리 7개·숫자 15개가 들어 있고, 대부분 볼 필요가 없다(SECURITY·ARCHITECTURE·
STYLE 은 표본이 7·1·1 이라 비율이 의미를 갖지 못한다). 바꿀 형태:

```
📊 채택률 이상 없음 (TEST만 ↓5%p, 69건 중 94%)
```

전부 정상이면 `📊 채택률 이상 없음` 한 줄. **통계는 이상할 때만 보낸다** — 아예 없애지 않는
이유는 조회 수단을 따로 만들어야 하고, 이상 감지라는 안전망은 값이 싸기 때문이다.
"무엇을 이상으로 볼지" 기준은 §7 미결.

### 3-4. 멘션은 기본 없음, 필요한 것만 표시

`autopilot.orchestrator.ts:53` 이 채널 발송마다 멘션을 붙여 통계 보고도 승인 카드와 같은
알림을 울린다. 알림 피로가 "안 읽게 된다" 의 또 다른 경로다.

- **멘션 필요** — ✅ 눌러야 진행되는 승인 카드, cron 실패 알람, 인증 만료 경고. 놓치면 일이 멈춘다.
- **멘션 없음(기본값)** — 스윕 완료 보고, 채택률 통계, 정상 종료 요약. 나중에 봐도 무해하다.

기본값을 조용한 쪽에 두는 것이 핵심이다. 그래야 새로 추가되는 메시지가 자동으로 조용해진다.

### 3-5. 맥락 한 줄을 자율 메시지에 붙인다

`context-summary.formatter.ts` 가 만드는 "직전 실행 #N" 류를 자율 실행 메시지에도 붙인다.
재료는 이미 있다 — `agent_run.parent_id`(self FK)와 직전 실행 조회.

### 3-6. 반복 제안을 막는다

같은 `change_key` 로 **이미 제안한 적이 있으면 상태와 무관하게** 다시 묻지 않는다. 기각 이력을
조건으로 삼지 않는 이유는 §2 정정에 있다 — 사람이 누른 기각이 0건이므로 "기각했으니 다시 묻지
않는다" 는 근거가 성립하지 않는다.

재리뷰가 필요한 경우는 슬래시 명령(`/review-pr`)이 이미 담당한다. 자동 재제안을 허용하는 쪽은
미결(§7-2)이 정리된 뒤 완화 조건으로 다룬다. 완전 차단으로 시작하는 편이 되돌리기 쉽다.

**기대 효과는 소음 감소로 한정한다.** 17회가 1회로 줄어도 그 1회를 보지 않으면 실행 수는
늘지 않는다.

## 4. 범위 — 판결(2026-09-18)에 따른 단계 분리

심사 결과는 `고치고 만든다` 였고, 바꾼 것은 **첫 대상**이다. 당초 EVENING_RETRO 포맷을 1단계로
잡았으나 그 경로는 30일 30건이다. 안 읽는 습관은 자주 오는 쪽에서 학습되므로(모의투자 1,406건 ·
자율 제안 625건 · 코드 리뷰 443건), 모델을 건드리지 않고 당일 체감되는 두 가지를 먼저 넣는다.

### 1단계 (이번 범위) — 모델 무관, 코드 안에서 끝남

- **멘션 기본 끄기** (3-4) — `autopilot.orchestrator.ts` 의 `withOwnerMention` 호출부 축소.
  실패 알림은 멘션 유지, 일반 보고는 조용히.
- **자율 제안 중복 억제** (3-6) — `hasPending` 이 PENDING 만 보는 것을 같은 `change_key` 전체
  이력으로 넓힌다.

10분 테스트 실측(2026-09-18): 최근 7일 자율 실행 984건 중 울려야 했던 것은 실패 73건 +
승인 카드 14건 = **87건(8.8%)**. 나머지 91%는 알림이 불필요했다. 984는 실행 수이므로 발송 수의
상한이며, 정확한 발송 수는 미계측.

### 2단계 승격 조건

1단계 반영 후 3일 관찰에서 **자율 제안 카드가 주 10건 이하**로, **멘션 발송이 절반 이하**로
줄면 2단계로 올린다. 줄었는데도 여전히 읽히지 않으면 문제는 알림이 아니라 내용이므로, 포맷을
더 다듬는 대신 §7-1(매일 무엇을 알고 싶은가)로 돌아간다.

### 2단계 — 사용자 요청으로 관찰 없이 착수(2026-09-18)

승격 조건을 기다리지 말고 지금 정리하라는 요청에 따라 진행했다. 다만 위 정정으로 항목이 바뀌었다.

**완료**

- PR 리뷰 스윕 채택률 줄에 3-3 적용 — 5%p 하락 또는 80% 미만만 수치로, 나머지는 개수로 묶음.
  표본 미달은 표시하지 않음. 실제 회차를 spec 회귀로 고정

**보류 (전제가 약해져서)**

- `toSlackText` 분리 — 슬래시 경로는 ephemeral 이라 스레드 불가, cron 은 이미 분리됨
- 3-1 전문 생성 걷어내기 · 3-2 제목·중요도 모델 출력 — 회고 본문이 이미 388자로 짧다.
  무엇이 실제로 긴지(§7-5) 특정한 뒤에 다시 판단

**미착수**

- 맥락 한 줄(3-5). 사용자가 말한 "앞선 내용 누락" 은 회고 본문의 `#93` 처럼 **참조가 설명 없이
  나오는** 형태였다. "직전 실행 #N" 을 붙이는 것으로는 풀리지 않는다 — 참조를 링크로 만드는
  쪽이 맞고, 그건 §7-1 이 정리된 뒤에 설계한다

**제외**

- formatter 29개 전면 재작성. 공통 지점 개선의 효과를 먼저 측정한다. `slack-handler.helper.ts`
  주석에 따르면 그 한 지점을 25곳 이상이 지난다
- 실사용이 없는 경로 손질 — `preview_action` 전수에서 PM_WRITE_BACK 1건(취소), DOCS_AUDIT_PR

## 7. 미결 — 착수 전 확인 필요

1. **매일 오는 메시지에서 실제로 알고 싶은 것.** 현재 회고는 "한 일 나열" 이다. 알고 싶은 것이
   "지금 막혀 있는 것" 이나 "내가 결정해야 할 것" 이라면 포맷을 고쳐도 계속 읽지 않게 된다.
   질문을 던졌으나 답을 받지 못했다. 답이 없으면 나열을 유지한 채 압축만 적용한다.
2. **PR 수정 후 재리뷰를 원하는 경우가 있는지.** 없다면 중복을 완전히 막는다. 있다면 "크게
   바뀐 것" 의 기준이 필요하다. 실제로 PR #52 는 09-09~09-15 사이 계속 수정되던 중 두 번은
   실행됐다.
3. **통계에서 "이상" 의 기준.** 예: 직전 대비 5%p 이상 하락, 표본 20건 미만은 비율 미표시 등.
   숫자를 정해야 3-3 이 구현 가능하다.
5. **어느 메시지가 실제로 긴가.** "전반적으로 다 길다" 는 진술과 실측(회고 388자)이 어긋난다.
   `agent_run.output` 은 메시지가 아니므로 이 축으로는 잴 수 없다. formatter 를 통과한 최종
   문자열을 남기거나(발송 로그), 실제 화면을 몇 건 받아서 특정해야 한다. 이것을 모르면 3-1·3-2 가
   엉뚱한 곳을 고친다.
4. **승인 카드는 눌리고 자율 제안은 보이지 않는 이유.** 전자는 85~100%, 후자는 사람이 누른
   흔적이 0건이다. 둘 다 같은 워크스페이스로 가는데 결과가 갈린다. 발송 채널(DM 대 채널),
   도착 시각의 규칙성, 카드 형태 중 무엇이 원인인지 미확인. 이것을 모르면 2단계에서 포맷을
   고쳐도 같은 결과가 날 수 있다.

## 8. §7-5 계측 — 방식 결정 (2026-09-18)

### 8-1. 이미 보낸 메시지를 읽는 길은 막혔다

Slack 에 남아 있는 과거 메시지를 읽으면 코드 변경 없이 30일치를 잴 수 있으므로 그쪽을 먼저
확인했고, 두 경로 모두 닫혀 있었다.

- 붙어 있는 Slack 커넥터는 회사 워크스페이스다. 이대리는 다른 워크스페이스에서 돌고, 회사 쪽
  `DM with idaeri`(`D0B04HXSTEC`)는 비어 있다.
- 봇 토큰으로 `conversations.history` 를 직접 부르는 경로는 `.env` 접근 차단에 막힌다.

따라서 **앞으로 나가는 것을 재는 방식**만 남는다.

### 8-2. 발송 직전 길이 기록

계측 지점은 세 곳이고, 한 메시지가 두 번 기록되지 않도록 갈라 둔다.

| 지점 | 덮는 것 | `origin` |
|---|---|---|
| `toReadableSlackArgs` (`message-blocks.builder.ts`) | 모든 텍스트 발송 | 기본 `reply` |
| `SlackService.postMessage` | 이대리가 먼저 밀어내는 것 | `push` / `push-thread` |
| `postPreviewMessage` · `postProposalMessage` | 승인 카드 · 자율 제안 카드 | `card` |

카드 2종은 blocks 로만 나가 공통 렌더를 지나지 않으므로 각자 붙인다. 기록은
`logs/slack-send.jsonl` 에 한 줄씩 쌓인다(gitignore 대상).

```json
{"at":"...","origin":"push","chars":3184,"parts":4,"blocks":6,"head":"🌙 어제 운영 장애 2건 수습 —"}
```

`parts` 는 **구분선으로 나뉜 조각 수**다. cron 요약은 `autopilot.orchestrator.ts` 의 `mainText`
에서 여러 task 요약을 `────────` 로 이어 붙여 한 메시지로 보내므로, 이 값이 있어야
"3,184자가 하나인지 넷을 붙인 것인지" 가 갈린다. 처방이 거기서 갈린다 — 각 요약을 줄일 일이냐,
붙이는 것을 그만둘 일이냐.

**조각 수는 task 수가 아니다.** `weekly-summary.autopilot-task.ts:167` 은 한 task 의 요약
안에서 worklog·건강 줄과 CEO 요약을 같은 구분선으로 잇는다 — 단독 발송인데도 조각이 2다.
읽을 때 "붙여 보낸 덩어리가 몇 개인가" 로 읽어야 맞고, "몇 개 task 가 합쳐졌나" 로 읽으면 틀린다.
세는 기준은 **줄 전체가 구분선인 경우만**이다. 부분일치로 세면 본문에 같은 문자가 섞이거나
모델이 더 긴 가로줄을 그렸을 때 조각 수가 부풀어, 판단 축 자체가 흔들린다.

현재 병합 묶음은 `evening` 4개(work-reviewer · daily-eval · evening-retro-publish ·
blog-github-publish), `morning` 2개, `noon` 1개이고 나머지 31개 task 는 단독 발송이다.
회고 본문이 388자여도 저녁 메시지는 그 네 개의 합으로 도착한다 — §2 정정이 남긴 어긋남의
유력한 설명이지만, 나머지 세 요약의 실제 길이는 아직 모른다. 계측이 확정하거나 기각한다.

### 8-3. 안 세는 것 (알려진 구멍)

- **`chat.update` 재렌더** — 승인 카드 상태 갱신(`slack-preview-card.updater.ts`),
  `closeProposalCard`, 커리어 카드 갱신. 새 알림이 아니라 기존 카드를 덮는 것이라 "읽을지 말지"
  판단 대상이 아니다.
- **발송 실패분** — 기록 시점이 "발송 직전" 이라 실패해도 한 줄 남는다. 길이 분포에는 무해하고,
  성공 후로 옮기면 pull 경로(`respond`/`say`)와 시점이 어긋나 같은 축으로 비교할 수 없다.
- **테스트 실행분** — `NODE_ENV=test` 에서는 기록하지 않는다. 막지 않으면 spec 5,472건의
  문자열이 분포에 섞인다.

### 8-4. 수집 절차

1. main 머지 후 **서버 재시작** — 도는 프로세스는 `dist/src/main` 이라 재시작 전에는 옛 코드다.
   두 번째 인스턴스를 띄우면 cron 이 이중 발화하므로 금지.
2. 재시작 직후 `wc -l logs/slack-send.jsonl` 로 기록이 실제로 쌓이는지 확인. 쓰기가 막히면
   경고를 한 번만 남기고 조용히 건너뛰므로, 이 확인을 건너뛰면 하루 뒤 빈 파일을 보게 된다.
3. 24시간 수집. 자주 도는 것(pr-review-sweep `*/3`, preview-sweeper `*/10`)은 몇 시간이면
   표본이 쌓이고, 저녁 다이제스트는 하루에 한 번이라 다음 날 아침에 전체 분포가 나온다.
4. 분포 확인 — `origin` 별 길이 순위와 `parts` 분포를 본다.

```bash
jq -s 'group_by(.origin)[] | {origin: .[0].origin, n: length,
  중위: (sort_by(.chars)[length/2|floor].chars), 최대: (max_by(.chars).chars)}' logs/slack-send.jsonl
```

5. 그 결과로 §4 「보류」 두 항목(3-1 전문 생성 걷어내기 · 3-2 제목·중요도 모델 출력)을 재판단한다.
   실제로 긴 메시지가 있으면 그 경로부터, 없으면 두 항목을 접는다.

계측은 §5 가 요구하는 전후 비교(길이 목표를 숫자로 고정하고 전후를 잰다)에 그대로 쓰이므로
답이 나온 뒤에도 남긴다.
