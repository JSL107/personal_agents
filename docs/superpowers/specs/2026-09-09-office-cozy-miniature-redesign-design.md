# 이대리 오피스 대규모 리디자인 설계

**작성일:** 2026-09-09  
**대상:** `clients/idaeri-console`, `clients/office-web`  
**아트 디렉션:** 포근한 스티커형 미니어처 오피스

## 1. 배경과 문제

현재 오피스는 `cozy` · `chibi` 를 표방하지만 실제 화면은 세 가지 시각 규칙이 충돌한다.

- 3.5등신에 가까운 무표정 캐릭터와 현실적인 사무 가구가 섞여 있다.
- 캐릭터는 정면, 가구와 방은 탑다운에 가까운 시점을 쓴다.
- 이름표·상태창·책상·의자가 캐릭터와 겹쳐, 인물이 가구에 끼인 듯 보인다.
- 차가운 회색 바닥, 강한 검은 외곽선, 규칙적인 책상 배치가 생활 공간보다 감시실을 연상시킨다.
- macOS 대시보드의 개인 방과 전체 오피스가 같은 에셋을 쓰지만 구도와 비율이 달라 한 세계로 보이지 않는다.

이번 리디자인은 기존 도트 에셋을 다듬는 작업이 아니다. 오피스의 감정적 인상과 렌더링 언어를 교체한다.

## 2. 목표

첫 화면에서 “업무를 감시하는 사무실”이 아니라 **귀여운 AI 동료들이 함께 생활하는 작은 스튜디오**로 느껴져야 한다.

완료 기준은 다음과 같다.

1. 캐릭터가 2.2~2.5등신의 둥근 실루엣과 명확한 표정을 갖는다.
2. 캐릭터·가구·소품은 모두 같은 3/4 시점을 쓴다.
3. 이름표나 상태 UI가 얼굴과 몸을 가리지 않는다.
4. 상태는 색상뿐 아니라 표정·소품·작은 동작으로도 구분된다.
5. 부서는 거대한 방이 아니라 2~4명이 모여 있는 작은 작업 섬으로 읽힌다.
6. macOS 대시보드와 오피스, 웹 오피스가 같은 시각 토큰과 의미 체계를 쓴다.
7. 기존 실시간 상태, 지시, 승인, 클릭, 출퇴근, 이동, 세션 연동은 회귀하지 않는다.

## 3. 비목표

- 백엔드 API나 `ConsoleStore` 데이터 계약을 바꾸지 않는다.
- 화면에 새로운 업무 기능을 추가하지 않는다.
- 사실적인 3D, 고해상도 도트, 일반적인 관리자 대시보드 화풍을 목표로 하지 않는다.
- 30명 모두를 개별 원화로 제작하지 않는다. 재사용 가능한 모듈형 캐릭터 규칙을 쓴다.

## 4. 아트 디렉션

### 4.1 형태

- 스타일은 **부드러운 2D 스티커 일러스트**를 기본으로 한다.
- 외곽선은 순수 검정이 아니라 짙은 따뜻한 갈색을 쓰고 두께를 줄인다.
- 양자화된 도트 경계는 폐기하고 부드러운 곡선과 낮은 강도의 종이 질감을 사용한다.
- 캐릭터와 가구에 약한 입체감은 주되, 클레이 장난감처럼 광택이 강한 3D로 가지 않는다.

### 4.2 색

| 역할 | 방향 |
|---|---|
| 기본 배경 | 웜 아이보리 |
| 주요 면 | 크림, 밝은 원목 |
| 포인트 | 살구, 버터 옐로, 세이지 민트, 더스티 라벤더, 소프트 스카이 블루 |
| 글자·외곽선 | 짙은 웜 브라운 |
| 위험·실패 | 저채도 코랄 |

부서색은 방 전체를 채우지 않고 러그, 리본, 배지, 작은 소품에만 쓴다. 상태색은 작은 칩과 필수 피드백에만 쓴다.

### 4.3 캐릭터 시스템

캐릭터는 완성 이미지 30장이 아니라 다음 파트를 조합하는 규칙으로 만든다.

- 얼굴형 3종
- 머리 실루엣 8종
- 상의 6종과 부서 색상
- 안경·헤드셋·모자·리본 등 액세서리
- 평온, 집중, 기쁨, 곤란, 긴장, 피곤 표정
- 타이핑, 대화, 독서, 서류 운반, 물 주기, 커피, 휴식 행동

`agentType`에서 각 파트 선택을 결정적으로 파생해, 실행할 때마다 모습이 바뀌지 않게 한다.

### 4.4 상태 표현

| 상태 | 표정·행동 | 보조 표시 |
|---|---|---|
| `waiting` | 평온한 표정, 독서·차 마시기·화분 돌보기 | 중립 칩 |
| `inProgress` | 집중 표정, 타이핑·화이트보드 | 작은 황금색 활성점 |
| `awaitingApproval` | 서류를 들고 대기 | 라벤더 승인 칩 |
| `awaitingIntegration` | 손을 멈추고 연결을 기다림 | 소프트 블루 연결 아이콘 |
| `completed` | 웃는 표정, 작은 체크 제스처 | 민트 체크 |
| `failed` | 곤란스러운 표정, 손에서 바로 떨어진 소품 | 저채도 코랄 경고 |

모션은 2~4px 범위의 작은 숨쉬기, 고개 끌덕임, 팔 움직임을 기본으로 한다. 오래 반복해도 피로하지 않아야 하며 시스템의 모션 축소 설정을 존중한다.

## 5. 화면 구조

### 5.1 오피스 탭

- 크림색 캔버스 위에 4~6개의 둥근 작업 섬을 배치한다.
- 작업 섬은 벽으로 닫힌 방이 아니라 러그·책상·화분·조명으로 영역이 자연스럽게 구분된 장면이다.
- 대표 영역은 상단 밴드가 아니라 중앙의 작은 라운지 또는 커뮤니티 테이블로 표현한다.
- 직원을 누르면 장면을 가리지 않는 오른쪽 inspector가 열린다.
- 기본 이름표는 없애고 hover·선택·주요 상태에서만 작은 크림색 pill로 표시한다.
- 승인·실패·연동 대기는 상단 요약 칩과 해당 캐릭터의 작은 배지로 이중 표시한다.

### 5.2 대시보드 카드

- `AgentRoomView` 대신 선택한 캐릭터의 상반신과 작은 업무 장면를 보여주는 `AgentPortraitView`를 둔다.
- 캐릭터가 카드의 시각적 중심이되되, 텍스트는 절대 얼굴이나 몸을 가리지 않는다.
- 상단에 이름·부서·상태, 하단에 현재 작업·명령·주요 행동을 둔다.
- 부서별 버튼색은 제거하고, 모든 주요 행동은 하나의 따뜻한 오렌지 계열을 쓴다.

### 5.3 탐색과 정보 위계

- 상단바: 제품명, 연결 상태, 진행·승인·실패 요약
- 중앙: 살아 있는 오피스 장면
- 오른쪽 inspector: 선택한 직원의 역할, 현재 상태, 진행 중인 일, 지시 행동
- 하단 보조 탐색: 오피스, 승인, 세션, 설정

## 6. 구현 경계

### 6.1 유지할 계약

다음 흐름은 변경하지 않는다.

```text
ConsoleStore / SSE snapshot
  -> OfficeView
  -> OfficeScene.sync
  -> OfficeFloorPlan
  -> character / furniture renderer
```

- `agentType` 기반 캐릭터 식별
- `OfficeFloorPlan` 의 좌석·부서 소속·이동 가능성
- `agentTypeAt` 클릭 판정
- `onAgentClick`, `onPresidentClick`
- 승인 큐와 상태 적용
- 지시·승인·거절 시트
- SSE, 출퇴근, 걷기, 세션 표현
- `--render`, `--render-dashboard` 회귀 진입점

### 6.2 macOS

- `AgentRoomView.swift`를 `AgentPortraitView`로 교체한다.
- `SpriteLoader.swift`의 도트 리컬러·`nearest` 전제를 제거하고 모듈형 일러스트 렌더러로 분리한다.
- `CharacterNode`의 pose·state·hover·selection API는 유지하되 텍스처 하나가 아닌 파트 조합 노드로 그린다.
- `OfficeScene` 의 floor·furniture·zone label 렌더만 새 시각 언어로 교체한다.

### 6.3 웹

- `office.js`에 macOS와 동일한 캐릭터 파트·팔레트·상태 의미 규칙을 둠다.
- `live.js`의 SSE·큐·출퇴근·이동 상태 머신은 유지한다.
- `index.html`의 `image-rendering: pixelated`를 제거한다.
- 양 플랫폼은 에셋 파일 이름이 아니라 `character`, `desk`, `plant`, `status`, `department` 같은 의미 토큰을 공유한다.

## 7. 데이터 흐름

1. `ConsoleStore`가 기존처럼 스냅샷과 SSE 이벤트를 수신한다.
2. `agentType`에서 캐릭터의 얼굴·머리·복장·액세서리를 결정적으로 파생한다.
3. `state`에서 표정·행동·보조 배지를 선택한다.
4. `department`에서 작업 섬의 러그·소품·리본 색을 선택한다.
5. `OfficeFloorPlan`의 좌표를 작업 섬 내 장면 좌표로 변환해 배치한다.
6. 클릭·hover·상태 변경은 기존 callback과 상태 경계를 통해 UI로 되돌아간다.

## 8. 오류·폴백

- 특정 캐릭터 파트를 만들지 못해도 기본 얼굴·머리·복장 조합으로 렌더한다.
- 부서 매핑이 없으면 중립 크림·세이지 토큰을 쓴다.
- 장식 소품이 누락돼도 캐릭터, 상태, 클릭 영역은 유지한다.
- macOS와 웹 중 한쪽에서 고급 표현을 쓸 수 없으면 동작을 제거하지 않고 정적 표현으로 낮춘다.
- 이미지 생성 결과는 바로 실행 에셋으로 쓰지 않고 스타일 프레임과 참조로만 사용한다. 실행 에셋은 모듈형 규칙으로 제작한다.

## 9. 구현 단계

1. **시각 기반:** 팔레트·타이포·모서리·그림자·캐릭터 파트 토큰을 정의한다.
2. **대시보드 수직 슬라이스:** `AgentPortraitView`와 카드 하나를 완성해 스타일을 증명한다.
3. **macOS 오피스:** 캐릭터 노드, 작업 섬, 가구, inspector를 교체한다.
4. **상태·모션:** 표정·행동·배지·축소 모션을 연결한다.
5. **웹 동기화:** Canvas 렌더러를 같은 의미 토큰과 장면 규칙으로 교체한다.
6. **전체 회귀:** 카드·오피스·상태·클릭·승인·세션·웹 화면을 검증한다.

## 10. 테스트와 시각 검증

### 10.1 자동화

- `agentType` 조합이 항상 같은 캐릭터 파트를 선택하는지 테스트한다.
- 모든 상태가 표정·행동·배지 토큰을 갖는지 테스트한다.
- 캐릭터 클릭 영역과 좌석·작업 섬 소속을 테스트한다.
- 승인 큐, 대표 클릭, 지시 시트, 세션 표현 테스트를 유지한다.
- macOS `swift build` 및 `swift run ConsoleCoreTests`를 통과한다.
- 루트 저장소에서 `pnpm lint:check`, `pnpm test`, `pnpm build`를 통과한다.
- 웹의 `pnpm check:canvas`, `pnpm check`를 통과한다.

### 10.2 시각 회귀

다음 화면을 라이트·다크 모드와 주요 창 크기에서 캡처한다.

- 대시보드 전체 및 대표 카드
- 전체 오피스
- 부서별 작업 섬
- 대기, 진행, 승인, 완료, 실패 상태
- inspector 열림
- 출퇴근·걷기·승인 집결 장면
- macOS와 웹의 동일 스냅샷 비교

시각 판정 기준:

- 얼굴과 몸이 UI에 가려지지 않는다.
- 검은 외곽선과 차가운 회색 면이 화면을 지배하지 않는다.
- 직원이 복제된 인형보다 개별 동료로 보인다.
- 작업 섬이 사무실 도면보다 생활 장면으로 읽힌다.
- 귀여움이 핵심 기능인 상태·승인·지시를 방해하지 않는다.

## 11. 접근성과 성능

- 상태는 색상만으로 표현하지 않고 표정, 아이콘, 문구를 함께 쓴다.
- VoiceOver 라벨에 직원 이름·역할·상태·현재 작업을 유지한다.
- 모든 클릭 대상은 기존 hit-test 하한보다 작아지지 않는다.
- 모션 축소 환경에서 반복 애니메이션을 멈춘다.
- 캐릭터 파트와 장식은 캐싱하고, 프레임마다 이미지를 재생성하지 않는다.

## 12. 중단 조건

다음 중 하나면 단계를 완료한다.

- 스타일 프레임과 대표 카드가 목표 인상을 만족한 뒤 다음 단계로 넘어간다.
- macOS 전체 오피스가 기능 회귀 없이 새 시각 언어를 쓴 뒤 웹으로 넘어간다.
- 웹까지 동기화하고 자동화·시각 회귀 검증을 모두 통과하면 리디자인을 완료한다.
