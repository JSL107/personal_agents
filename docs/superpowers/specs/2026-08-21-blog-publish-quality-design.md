# 자동 발행 블로그 글 품질 — 설계

/ 2026-08-21 / 대상: 오늘의 공부 딥다이브 → 블로그 발행 라인

## 왜 이 문서가 필요했나

첫 자동 발행 글(2026-08-19, HTTP 캐시)을 보고 네 가지 문제를 진단했다. 깊이가 없다,
AI 티가 남는다, 개인 경험 절이 비었다, 말투가 안 닿는다.

그 진단을 그대로 고치기 전에 실물을 대조했더니 **진단의 무대가 달랐다**. 딥다이브 확장
라인(`ExpandStudyBriefUsecase`)은 2026-08-20 11:31에 머지됐고 cron은 11:00이라, 그날까지
자동 회차가 한 번도 없었다. 진단 근거였던 HTTP 캐시 글은 이 라인이 아니라 다른 초안
공급원에서 나온 글이다.

실제 딥다이브 초안을 발행 라인에 통과시켜(모델 3회 실호출, 커밋 없음) 다시 재보니 결과가
이렇게 갈렸다.

| 진단 | 딥다이브 실물 | 판정 |
|---|---|---|
| 깊이를 더하는 단계가 없다 | 초안 6,636자 → 발행본 6,684자 | 재현 안 됨 |
| 문장 중간 볼드·나열식 불릿 | 볼드 0개, 불릿 0개 | 재현 안 됨 |
| 개인 경험 절이 비었다 | 6개 절 전부 존재 | 재현 안 됨 |
| 말투가 안 닿는다 | 22/22문단 윤문 적용, 구어 어미 6/142문장 | 재현됨 |

대신 진단에 없던 문제가 드러났다.

## 문제 1 — 익명화가 글의 구체성을 지운다

개인 경험 절은 있는데 읽으면 아무 내용이 없다.

> 실행 감사 계층은 먼저 audit spine 역할을 맡습니다. 요청 라우팅 계층은 자연어 멘션을
> 어느 작업 분배 계층에 보낼지 정합니다.

발행본 계수: `협업 메신저` 15회, `코드 호스팅 플랫폼` 9회, `○○ 계층` 19곳. `Slack`·`GitHub`·
`NestJS` 는 0회. 같은 초안의 윤문 전 원문에는 `Slack 명령을 받으면 GitHub PR diff를 읽습니다`
처럼 이름이 그대로 살아 있었다. 지운 것은 익명화 단계다.

두 단계가 정반대 지시를 받고 있었다.

- 확장 프롬프트: "위 모듈 목록에서 고른 **실제 이름**을 쓴다"
- 익명화 프롬프트: "클래스·함수명은 해당 데이터 또는 책임의 **일반 설명으로 대체**한다"

익명화 규칙은 회사 PR 회고를 위해 쓰였다. 딥다이브 글은 공개 문서와 글쓴이 본인의 공개
저장소를 재료로 쓰는데, 익명화기에는 둘을 가를 근거가 없다.

### 결정: 초안 출처로 익명화 계약을 나눈다

Notion 초안의 `출처유형` 속성(`오늘의 공부` / `PR`)으로 시스템 프롬프트를 고른다. 이 값은
발행 순서를 정하느라 이미 읽고 있어 조회가 늘지 않는다.

공개 프로젝트용 프롬프트에서는 내부 식별자 치환 지시를 **덧붙여 완화하지 않고 제거**했다.
상반된 지시를 아래에 붙이기만 하면 모델이 위 지시를 그대로 지킨다(이 레포가 이미 겪어
`humanize-system.prompt.ts` 가 같은 이유로 `replace` 를 쓴다).

모르는 출처유형은 **엄격한 회사용으로 떨어진다.** 새 출처가 생겼을 때 조용히 느슨한 쪽을
타는 것보다, 지나치게 가리고 사람이 알아채는 편이 안전하다.

안전장치는 그대로다. 파이프라인 끝의 금지어 검사(`BLOG_MASK_FORBIDDEN_TERMS`)가 제목·요약·
slug·경로·본문을 다시 훑는다. 이 변경은 1차 방어선을 출처에 맞게 조정하는 것이지 방어선을
없애는 것이 아니다.

## 문제 2 — 분류가 프론트매터에 없다

블로그 저장소가 태그를 버리고 분류로 바꿨고 값은 `backend`/`web`/`infra`/`note` 넷으로
고정돼 있다. 발행 라인은 이 값을 넣지 않아 새 글이 "미분류"로 올라온다.

### 결정: 편집 단계가 고르고, 파서는 관대하게 받는다

편집 단계는 이미 제목·slug·요약을 한 JSON으로 내놓는 유일한 자리다. 필드 하나를 더하므로
모델 호출은 늘지 않는다.

값이 없거나 넷 밖이면 비우고 프론트매터에서 `category` 줄을 생략한다. slug 과 달리 예외로
끊지 않는다 — slug 은 URL 이라 틀리면 링크가 영구히 깨지지만, 분류는 빠져도 화면에
"미분류"로 보일 뿐이다. 값 하나로 발행 전체를 막지 않는다.

## 문제 3 — 기술 글에 코드 예시가 없다

6,684자 발행본에 코드펜스가 0개였다. 확장 프롬프트가 "코드나 설정 예시는 출처에 실제로
있는 것만 옮긴다"고 **허용**했을 뿐 요구하지 않았기 때문이다.

### 결정: 허용을 요구로 바꾸되 출처 제약은 유지

최소 두 곳에 코드·설정·요청 예시를 넣고, 언어를 표시한 코드블록에 담는다. 출처에 없으면
지어내지 말고 출처가 규정한 형식·필드 이름을 인용하게 한다.

## 문제 4 — 문체 지표가 4%를 0%로 표시한다

발행 카드에 `구어 0%` 로 찍혀 "말투가 전혀 안 먹었다"로 읽혔다. 실제로는 142문장 중 6개
(4%)였다. 비율을 소수 1자리로 반올림해 0~5%가 전부 0이 되고 있었다.

### 결정: 비율을 0~100 정수 퍼센트로 저장한다

`shortSentenceRatio` → `shortSentencePercent`, `colloquialEndingRatio` →
`colloquialEndingPercent`. 이름에 단위를 넣어 호출부가 다시 100을 곱하지 않게 한다.

## 문제 5 — 말투 프로파일이 장문에서 안 지켜진다

윤문은 22/22 문단에 닿았는데도 구어 종결어미가 5% 안팎이었다(프로파일 목표 10~20%).
같은 초안 문단 전체(95문장)를 실제 모델로 반복 윤문해 조건을 대조했다.

| 조건 | 구어 어미 | 최장 문장 | 총 글자수 |
|---|---|---|---|
| 원문(윤문 전) | 0% | 156자 | 4,749자 |
| A 현행 | 5% / 5% / 5% / 3% | 98~102자 | 4,939~5,069자 |
| B preference 주입 제외 | 5~10% | 58자 | 유지 |
| C 기존 간결 규칙 추가 | 13% / 0% | 69자 | **996자 (92%)** |
| D 장문 끊기 규칙 신설 | 5% / 3% | 97~98자 | 유지 |
| E 문단별 강제 | **16% / 23%** | 98~102자 | 유지 |

읽은 것:

- **B 기각.** `doNot` 을 문체 블록에서 빼도 구어는 늘지 않았다. 처음 세운 가설이 틀렸다.
- **C 기각.** 두 회차 모두 총량을 깎았다. 블로그 본문은 분량이 곧 내용이라 쓸 수 없다.
- **D 기각.** "한 문장 60자 이내" 를 넣어도 A와 차이가 없었다.
- **E 채택.** "열 문장에 한두 번" 이라는 전역 비율은 모델이 글 전체를 세야 해서 장문에서
  지켜지지 않는다. 입력이 문단별 JSON 값이므로 "각 값마다 최소 한 문장" 으로 바꾸면 세지
  않고도 지킬 수 있다. 두 회차 모두 A의 3~7배가 나왔고 총량은 유지됐다.

  다만 두 번째 회차 23% 는 재현 대상(10~20%)의 상단을 넘는다. 상한 지시("한 값에서 세 번을
  넘기지는 마라")를 더 조이지 않은 이유는 그 변경이 미검증이 되기 때문이다. 이제 카드 지표가
  정수 퍼센트로 정확히 보이므로(문제 4), 실사용에서 과하면 그때 조인다.

작은 표본(5문단)에서는 같은 조건이 13%와 0%로 갈렸다. 문단 전체로 표본을 키우자 반복
재현성이 생겼다(A가 세 회차에서 5%, 5%, 3%). **조건 차이를 5문단 표본으로 판정했다면
C를 채택하고 분량을 깎았을 것이다.**

## 검증

- `pnpm lint:check` 0 error (경고 57개는 main 과 동일), `pnpm test` 3,788개 통과, `pnpm build` 통과.
- 새 가드는 일부러 깨뜨려 확인했다 — 공개용 프롬프트에 치환 지시를 되살리면 실패하고,
  `category` 출력을 지우면 실패하고, 익명화 분기를 고정값으로 바꾸면 배선 테스트가 실패한다.
- `scripts/verify-blog-publish.ts --dump <경로>` 로 발행본 전문을 받아 전후를 대조한다.
  앞 500자만으로는 고유명사 보존·코드블록·분류처럼 본문 전체에 흩어진 것을 볼 수 없다.

## 범위 밖

- **깊이를 더하는 단계 신설**: 실물에서 재현되지 않았다(6,636자 → 6,684자). 익명화를 고치면
  체감이 달라질 수 있어, 고친 글 한 편을 본 뒤 다시 판단한다.
- **글감 재설계**: "내가 부딪힌 문제에서 출발" 은 저녁 회고 라인이 이미 하는 일이다. 두
  공급원의 관계를 정하는 문제라 별도 결정이 필요하다.
- **preference 주입 정리**: 문체와 무관한 `doNot` 이 "사용자 문체 선호" 라는 이름으로 윤문
  프롬프트에 붙는다. 말투에 영향이 없다는 것이 실측으로 확인돼 이번에는 건드리지 않는다.
  다만 이름과 내용이 어긋난 상태는 남아 있다.
- **AI 티 검사 범위 확대**: 딥다이브 글에서는 볼드·불릿이 0개라 재현되지 않았다. 회고 라인
  글에는 실재하므로 그쪽을 대상으로 별도 판단한다.
