# 모의투자 백테스트 설계 — 규칙을 바꿨을 때 좋아졌는지 숫자로 답한다

작성일: 2026-08-16
선행: 3단계 #288(추천·시가 체결), #292(추천 채점·그림자 성적·코스피 초과수익) 머지 완료, 운영 중

---

## 1. 무엇을 만드는가

**과거 주가를 놓고 "그때 이 규칙대로 샀으면 어떻게 됐을지"를 계산해 표로 뱉는 명령어 하나**를 만든다.

성공 기준은 다음 문장에 숫자로 답할 수 있게 되는 것이다.

> "거래대금 하한을 5억에서 10억으로 올리면 같은 기간 승률이 58%에서 63%로 오르고 최대손실이 -11%에서 -8%로 줄어든다."

지금은 이 질문에 **앞으로 3개월 굴려보는 것 말고는** 답할 방법이 없다. 그마저도 그 사이 장이 달랐으면 비교가 성립하지 않는다.

---

## 2. 왜 지금인가

두 가지가 겹쳤다.

**첫째, 검증 수단 없이 규칙만 쌓이고 있다.** `SCREENER_RULE_VERSION`은 이미 2다. 규칙을 한 번 바꿨지만 그것이 개선이었는지 판정한 기록이 없다. 앞으로 손절·익절·부분 익절을 넣자는 얘기가 나올 텐데, 판정 수단 없이 넣으면 좋아졌는지 나빠졌는지 모른 채 복잡도만 는다.

**둘째, 2026-08-16 검증에서 실제 결함이 나왔다.** 매수 수량은 D일 **종가**로 확정되는데 체결은 D+1 **시가**라, 그 사이 갭 상승분이 그대로 초과 편입된다. 체결 단계의 가드가 현금 잔액뿐이라 비중은 아무도 보지 않는다.

| 검증 항목 | 결과 |
|---|---|
| 스크리너 필터·랭킹, 비중 산정, 중복·후보밖 제거 | 통과 |
| 시가 체결, 현금 부족 시 수량 축소, 보유 초과 클램프, 미보유 매도 만료 | 통과 |
| 실현손익 = 매도수령액 − 매수원가 (소수점 일치) | 통과 |
| 원장 불변식 (시드 − 체결내역 = 현금, 체결수량 = 보유수량) | 통과 |
| **체결가 기준 20% 비중 상한** | **위반 — 갭 +92%에서 38.4% 편입** |

상한가(+30%) 갭이면 20%가 26%가 된다. 파산은 안 나지만 리스크 규칙이 조용히 깨진다. **이 부류의 결함은 종가 체결로 근사하는 백테스트로는 구조적으로 영원히 못 잡는다.** 체결 기준을 시가로 잡는 이유가 여기 있다.

## 3. 지금 서 있는 땅

| 항목 | 값 |
|---|---|
| 유니버스 | KRX 상장 보통주 (`Ticker.krxMarket != null`) |
| 일봉 저장 | `DailyPrice` — 종가·수정종가·거래량. **시가·고가·저가 없음** |
| 시가 조달 | 토스 `/candles`가 `openPrice`를 준다. `DailyBar.open`으로 파싱까지 되어 있으나 **저장하지 않고 체결 때 실시간 조회로만 쓰고 버린다** |
| 과거 깊이 | 최초 200봉 수집 후 매일 5봉 증분 (`DEFAULT_INITIAL_DAYS=200`, `DEFAULT_INCREMENTAL_DAYS=5`) → **약 10개월** |
| 채점기 | `matchRecommendationCycles` + `aggregateRecommendationScores` — 승률·평균/중앙값 수익률·최대손실·평균보유일·이상탐지 6종 |
| 벤치마크 | `calculateBenchmarkPerformance` — 코스피 대비 초과수익. `BenchmarkDailyClose` 적재 중 |
| 그림자 성적 | `calculateShadowPerformance` — 장투 60일·스윙 5일 기계적 보유 시뮬레이션 (종가 기준) |
| 휴장일 처리 | **공휴일 달력 없음.** "봉이 없으면 휴장" 데이터 기반 판정으로 전 모듈 통일 |

**채점 계층은 이미 다 있다.** 백테스트가 새로 만들 것은 "과거를 재생하는 부분"뿐이고, 성적 산출은 기존 함수에 그대로 먹인다.

## 4. 전체 구조

```
DailyPrice (거래일만 존재)
      ↓
[신규] 재생 루프 — 날짜를 하루씩 넘기며
      ↓
calculateIndicators → screenStocks          ← 기존 그대로
      ↓
[신규] 결정론적 선택 — 점수 상위 N종
      ↓
constrainPaperRecommendation                ← 기존 그대로
      ↓
RecordPaperTradeUsecase.executePendingOrder ← 기존 그대로 (인메모리 대역 위에서)
      ↓
verifyPaperInvariants                       ← 기존 그대로 (재생 종료 시 장부 검산)
      ↓
matchRecommendationCycles → aggregateRecommendationScores → calculateBenchmarkPerformance
      ↓                                     ← 기존 그대로
성적표 출력
```

재생이 끝나면 불변식을 반드시 통과해야 한다. 시뮬레이션 장부가 어긋난 채로 나온 성적은 규칙의 성적이 아니라 버그의 성적이다. 위반이 하나라도 있으면 성적을 출력하지 않고 실패로 끝낸다.

신규 코드는 **재생 루프**, **결정론적 선택**, **인메모리 대역**, **CLI 껍데기** 넷뿐이다.

## 5. 결정 사항과 근거

### 5.1 LLM은 백테스트에서 제외한다

과거 각 시점의 codex 호출을 **"스크리너 점수 상위 N종 기계적 매수"** 로 대체한다.

같은 규칙을 두 번 돌렸을 때 결과가 달라지면 A/B 비교의 기준선이 흔들려 백테스트의 존재 이유가 사라진다. 1년치 × 2전략 = 약 500회 호출이라는 쿼터·시간 비용도 있지만, 결정적 이유는 재현성이다.

"LLM이 기계보다 잘 고르는가"는 이 백테스트의 질문이 아니다. 그 질문은 이미 `calculateShadowPerformance`가 운영 중에 forward로 재고 있다. 역할을 겹치지 않게 분리한다.

부수 효과로 **기계 기준선이 생긴다.** 지금까지는 그림자 성적이 "고정 보유기간"만 대조군이었는데, 앞으로는 "같은 규칙으로 기계가 골랐을 때"라는 대조군이 추가된다.

**매도도 함께 사라지므로 청산 규칙을 정해야 한다.** 실전의 매도는 LLM이 판단하는데 그 자리가 비었다. 백테스트는 **보유 `--hold` 일수가 지나면 전량 청산**한다. 기본값은 그림자 성적과 같은 값(장투 60일, 스윙 5일)을 쓴다 — 같은 기준이어야 두 숫자를 나란히 놓을 수 있다. 이 값 자체가 튜닝 대상이다.

### 5.2 체결은 시가로 한다 — `DailyPrice.open` 컬럼을 추가한다

§2에서 밝힌 대로 갭 관련 결함은 시가 체결에서만 드러난다. 백테스트 수치를 실전 성적과 직접 비교하려면 진입 기준도 같아야 한다.

비용은 스키마 1컬럼과 전 종목 200봉 재수집 1회다. 토스가 이미 `openPrice`를 주고 있어 새 API 연동은 없다.

### 5.3 실전 체결 usecase를 그대로 통과시킨다

`fillPendingOrderAtomically`만 인메모리로 대역하고 `RecordPaperTradeUsecase.executePendingOrder`는 실제 코드를 부른다.

체결 로직을 새로 쓰면 현금 부족 시 이진탐색 축소, 보유 초과 클램프, 만료 판정이 백테스트에는 없게 되어 "실전과 같은 것을 재는가"가 깨진다. 대역은 2026-08-16 검증에서 이미 만들어 동작을 확인했고 30줄이었다.

DB에 실제 계좌를 만들어 재생하는 방식은 버린다. 백테스트 계좌·주문·체결이 운영 테이블에 쌓이고, 재실행하면 `PaperTrade.fingerprint` 유니크 제약에 막혀 파라미터 스윕이 불가능해진다.

### 5.4 채점기를 재사용한다

시뮬레이션 결과를 `RecommendationOrderInput` / `RecommendationTradeInput` 형태로 뱉어 기존 채점기에 먹인다. 백테스트 +4.1%와 실제 계좌 +2.8%가 **같은 자로 잰 숫자**가 되어 직접 비교할 수 있다. 성적 계산을 새로 짜면 두 숫자의 정의가 갈라져 비교가 무의미해진다.

## 6. 선행 작업 — `DailyPrice.open`

```prisma
model DailyPrice {
  // ...
  open           Decimal?  @db.Decimal(18, 4)   // 신규. 기존 행 보존 위해 nullable
}
```

1. 스키마에 nullable `open` 추가 → `pnpm db:push` → `pnpm prisma:generate`
2. `toWriteRows`가 `bar.open`을 함께 싣도록 수정 (`CollectUniversePricesUsecase`)
3. 전 종목 200봉 재수집 1회 — `--days=200` 강제. 야간 실행
4. 백테스트는 `open`이 `null`인 거래일을 **건너뛰지 않고 실패로 보고**한다. 조용히 빠지면 표본이 줄어든 줄 모른 채 성적만 좋아 보인다

`open`을 nullable로 두는 이유는 기존 행을 지우지 않기 위함이다. 재수집이 끝나면 사실상 전 행이 채워지지만, 스키마에서 필수로 못 박으면 재수집 실패 종목에서 쓰기 자체가 막힌다.

## 7. 두 축 — 추천은 평일, 체결은 거래일

실전 크론이 그렇게 돈다. 백테스트도 같아야 한다.

| 축 | 실전 | 백테스트 |
|---|---|---|
| 추천 생성 | 평일 19:30 (`30 19 * * 1-5`) — **공휴일에도 돈다** | 구간 내 모든 평일 |
| 체결 | 평일 09~15시 10분마다 — 봉이 있는 날만 성사 | `DailyPrice`에 행이 있는 날 |

휴장일 처리에 달력이 필요 없는 이유가 여기 있다. `DailyPrice`에는 휴장일 행이 애초에 없으므로 **존재하는 거래일만 순회하면 실제 휴장이 자동 반영된다.** 실전이 "봉이 없으면 휴장"으로 판정하는 것과 같은 원리다.

두 축을 분리해야만 재현되는 현상이 있다. 연휴 동안 추천이 매일 쌓였다가 개장일 아침에 한꺼번에 체결되는 경우다. 하루 3종목이 아니라 6~9종목이 한 번에 들어올 수 있다. 같은 종목 중복은 `pendingBuyTickerIds`와 예약현금 차감이 막지만 다른 종목은 막지 않는다. **이는 정상 동작으로 확인된 사항이며**(2026-08-16 판단), 백테스트는 이것을 막는 것이 아니라 **성적에 미치는 영향을 측정**한다.

백테스트를 거래일만으로 단순화하면 이 현상이 사라져 실전과 다른 것을 재게 된다.

## 8. 산출 지표와 출력

기존 채점기가 주는 것에 백테스트 고유 지표 세 개를 더한다.

| 구분 | 지표 | 출처 |
|---|---|---|
| 추천 품질 | 승률, 평균·중앙값 수익률, 최대손실, 평균보유일 | `aggregateRecommendationScores` |
| 시장 대비 | 코스피 초과수익 | `calculateBenchmarkPerformance` |
| 계좌 | 최종 평가액, 수익률 | `calculateAccountValuation` |
| **신규** | **목표비중 초과 편입 건수와 최댓값** | §2 결함 상시 감시 |
| **신규** | **만료 사유별 건수** (현금부족 / 시장구분없음 / 시가없음) | 규칙이 주문을 얼마나 버리는지 |
| **신규** | **한 거래일 동시 체결 횟수** — `--max-positions`를 넘겨 체결된 날의 수와 그날 최대 종목수 | §7 두 축 분리의 관측 대상 |

```

규칙 turnover>=5e8, max=3종, weight=20%, hold=60일
─────────────────────────────────────────────
추천 34건 · 체결 31건 · 만료 3건(현금부족 2, 시장구분없음 1)
승률 58.1%  평균수익률 +2.4%  중앙값 +1.1%  최대손실 -11.3%
평균보유 21일 · 코스피 대비 초과수익 +3.7%p
최종 평가액 10,412,880원 (+4.1%)
⚠ 목표비중 20% 초과 편입 4건 (최대 26.3%)
⚠ 연휴 후 동시 체결 2회 (최대 6종목)
```

## 10. CLI

```bash
pnpm backtest --strategy=LONG_TERM --from=2026-01-02 --to=2026-08-14 \
              --turnover-min=5e8 --max-positions=3 --weight=20 --hold=60
```

| 인자 | 기본값 | 의미 |
|---|---|---|
| `--strategy` | 필수 | `LONG_TERM` \| `SWING` |
| `--from` / `--to` | 필수 | 재생 구간 (KST 날짜) |
| `--seed` | `10000000` | 시드 자본 |
| `--turnover-min` | `5e8` | 거래대금 하한 |
| `--max-positions` | `3` | 동시 최대 종목수 |
| `--weight` | `20` | 종목당 목표 비중(%) |
| `--hold` | 장투 60 / 스윙 5 | 보유 거래일수 — 이 일수가 지나면 전량 청산 |

Slack 슬래시로 만들지 않는다. 3초 ack 제약과 맞지 않고, 결과가 여러 줄 표이며, 사람이 규칙을 만질 때 돌리는 물건이라 대화 채널에 놓을 이유가 없다.

`--hold`가 필요한 이유는 §5.1에서 LLM을 뺐기 때문이다. 매도 판단자가 사라졌으므로 청산 규칙을 기계적으로 정해야 한다. 이 값 자체가 튜닝 대상이다.

| 재생 루프 | 합성 일봉 3~5종목으로 고정 시나리오. 갭 상승·연휴·현금 소진을 각각 포함 |
| 인메모리 대역 | 2026-08-16 검증 하네스를 회귀 테스트로 승격 — 실전 usecase 통과 여부 |
| 전체 | 같은 인자로 두 번 돌려 **바이트 단위 동일 출력** 확인. 결정론이 깨지면 백테스트 전체가 무의미해지므로 이 테스트가 가장 중요하다 |

§2의 20% 초과 결함은 재생 루프 테스트에 **실패하는 케이스로 먼저 넣는다.** 백테스트가 그 결함을 검출하는지부터 확인하고, 그다음 결함 자체를 고친다.

## 12. 한계 — 이 백테스트가 답하지 못하는 것

정직하게 못 박아 둔다. 여기 적힌 것을 근거로 실전 판단을 내리면 안 된다.

| 한계 | 내용 |
|---|---|
| **과거 깊이 10개월** | 200봉이 전부다. 하락장 표본이 없으면 성적이 낙관적으로 나온다. 구간을 바꿔가며 여러 번 돌려 안정성을 봐야 한다 |
| **생존 편향** | 유니버스는 **현재** 상장 종목이다. 그 기간에 상장폐지된 종목이 표본에서 빠져 성적이 과대평가된다. 백테스트가 실전보다 잘 나오는 가장 큰 이유가 이것일 가능성이 높다 |
| **슬리피지 없음** | 시가에 원하는 수량이 전부 체결된다고 가정한다. 거래대금 하한 5억이 이를 어느 정도 방어하지만 완전하지 않다 |
| **거래정지·상하한가 미반영** | 시가 데이터가 있으면 체결된 것으로 본다 |
| **LLM 부재** | 실전은 codex가 고르고 판다. 백테스트 성적은 **"규칙만 남기고 기계가 굴렸을 때"의 기준선**이지 실전 예측치가 아니다. codex가 이보다 잘할 수도 못할 수도 있고, 그 판정은 운영 중 그림자 성적이 맡는다 |

수수료·거래세는 `calculateTradeCost`를 그대로 쓰므로 날짜별 세율 변경(2025-12-29 개정)까지 정확히 반영된다.

## 13. 범위 밖

- 손절·익절·부분 익절·리밸런싱 규칙 — 백테스트로 검증한 뒤 별도로 다룬다
- 미국 주식·신규 전략 계좌
- 파라미터 자동 최적화(그리드 서치) — 먼저 수동으로 몇 번 돌려보고 필요하면 그때
- §2의 20% 초과 결함 **수정** — 이 설계는 검출까지만 담당한다
