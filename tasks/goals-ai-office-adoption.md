- **왜**: dispatcher 19종에 회사 현황·지연 귀속 착지점이 없다(2026-09-04 `router.module.ts` 실측).

- **전제**: 없음. 데이터 소스(agent_run 원장 · PreviewGate 카드 · 쿼터 에러)는 전부 기존 것.

  `ResponseCode` 포함) + intent classifier 착지 예문 + `docs:check` + 실호출 검증 1건(Slack 실응답).
- **결과**: `DELAY_REPORT` 워커 신설 — #467 머지 (main `2311fc69`).

### [x] B. BLOCK_REASON 상용구 사전 — 이유 + 해결 행동 (#470 머지 완료)

- **무엇**: 실패·스킵·미연동 카드의 공통 포맷 사전. ①안 되는 진짜 이유 ②지어내지 않는다는 선언
  ③풀리면 무엇을 하는지. 쿼터 소진 · 연동 미설정 · 선행 산출물 부재 3부류부터.
- **전제**: A(#467)가 "이유 + 해결 행동" 문구를 이미 쓰고 있다 — 사전으로 뽑을 때 그 문구를
  출발점으로 삼고, A 의 미연동 판정이 message 문자열 매칭에 의존하는 한계도 함께 본다
  (`src/agent/delay-report/domain/attribute-delay.ts` 주석).
- **완료 조건**: 사전 1곳 정의 + A 워커와 기존 실패 카드 최소 1경로에 적용 + 3중 green.
- **결과**: `BLOCK_REASON` 사전 신설 — #470 머지 (main `d5587b44`).
  사전은 `src/common/domain/block-reason.ts` 한 곳 — 부류 3종(QUOTA · INTEGRATION · PREREQUISITE)마다
  ②"지어내지 않는다" 선언 + ③해결 행동을 들고, ①이유는 호출부 문구를 그대로 쓴다.
  적용 2곳: (1) A 워커 — `attribute-delay.ts` 가 자체 신호 상수·상용구를 버리고 사전을 쓰고,
  `delay-report.formatter.ts` 의 조치 문구도 사전에서 가져온다. (2) 슬래시·버튼 실패 카드 공통 길목
  `slack-handler.helper.ts` 의 `toUserFacingErrorMessage`(호출 25곳 이상) — 알아본 부류에만 빠진 조각을
  채우고, 모르는 실패는 원문 그대로 둔다.
  덤: 사전이 PREREQUISITE 를 알아보면서 A 워커도 선행 산출물 부재를 별도 원인으로 귀속하게 됐다.
  같은 안내가 한 줄에 두 번 나오지 않도록 `statesRecoveryAlready` 로 ③ 중복을 막는다.
  게이트: `lint:check` · `test`(513 suite / 5,242) · `build` · `docs:check` 전부 green.
  실 렌더 문자열은 빌드 산출물로 4부류(미연동 · 쿼터 · 선행 부재 · 미분류)를 뽑아 눈으로 대조했다.
  **Slack 실멘션 왕복은 미검증** — A 와 같은 이유로 운영 백엔드(포트 3099) 재시작이 필요하다.
  한계: 판정이 여전히 message 문자열 매칭이다(원장·DomainException 에 errorCode 가 안 남는다).
  근거 파일·라인은 사전 상단 주석에 실측으로 적어 뒀고, 문구가 바뀌면 조용히 깨진다.
  자체 리뷰에서 3건을 잡아 고쳤다 — 쿼터 안내 중복 문장, 한 번만 쓰는 래퍼 함수, 조사 오류(`Notion가`).
  봇 리뷰 3건은 전부 정탐으로 판정해 반영했다. 핵심은 **선행 부재 판정이 절반도 못 알아보던 것** —
  연속 문자열 `먼저 실행` 으로만 찾아 레포 실제 문구 11건 중 2건만 잡혔다(`먼저 \`/today\` 로 …`,
  `새로운 \`/today\` 실행 후 …` 가 통째로 빠짐). "무엇이 없다" + "대표가 실행할 것이 있다" 두 조각
  판정으로 바꿔 11건 적중·오탐 0. 나머지 둘은 `statesRecoveryAlready` 를 부류별 신호로 좁힌 것
  (미연동 문구의 "잠시 후 다시 시도" 는 키를 넣으라는 말이 아니다)과 formatter PREREQUISITE 스펙 추가.

### [x] C. 브리핑 4분할 — 성과 / 대표 결정사항 / 위험 / 다음 (#472 머지 완료)

- **무엇**: worklog(`DailyReview`)·저녁 브리핑에 decisions / risks 필드 분리. 빈 값은 생략이 아니라
  "오늘 결재 안건 없음"처럼 명시적 부정으로 채운다.
- **전제**: 착수 시 `src/agent/work-reviewer/domain/work-reviewer.type.ts` 현 스키마와 대조 먼저.
  스키마 변경이므로 A·B 와 같은 회차에 섞지 않는다.
- **완료 조건**: 필드 분리 + 산출물 실측 1건(빈 필드 없이 명시 문구 확인) + 3중 green.
- **결과**: `DailyReview` 에 `decisions` · `risks` 두 배열 필드 신설 — #472 머지.
  전제였던 스키마 대조 결과 두 필드는 없었고, 기존 `nextActions` 는 "내가 이어서 할 일" 이라
  "대표가 정해줘야 움직일 수 있는 것" 을 담을 자리가 아니었다.
  렌더 경로가 `formatDailyReview` 하나로 모여 있어 `/worklog` 슬래시와 저녁 브리핑(autopilot
  `work-reviewer` task)이 한 번의 포매터 수정으로 같이 덮였다 — 저녁 브리핑용 별도 스키마는 없다.
  **명시적 부정은 데이터가 아니라 렌더 단계에 뒀다.** 모델이 빈 배열을 내면 포매터가
  `결재 안건 없음` / `식별된 위험 없음`(`work-reviewer.type.ts` 의 두 상수)으로 바꿔 찍는다.
  배열 안에 "없음" 문자열을 채우게 하면 원장에 가짜 안건이 쌓인다.
  적용 7곳: 타입 · shape 가드 · codex output schema(required) · 시스템 프롬프트(작성 기준 + 출력 JSON) ·
  Slack 포매터 · PM 이 어제 회고를 읽는 `previous-worklog-formatter` · 윤문 어댑터(두 필드도 윤문 대상).
  **빈 값은 세 상태로 갈린다** — 값 있음 / `[]`(검토했고 안건 없음) / `undefined`(그 축을 아예 안 봄).
  세 번째는 이 필드 도입 이전에 원장에 적재된 회고를 다시 읽을 때만 나오며, 그때는 "없음" 이라고
  적지 않고 섹션 자체를 내지 않는다. 형태 가드도 둘로 갈랐다 — 모델 응답은 두 필드 필수
  (`isDailyReviewShape`), 원장 재조회는 누락 허용하되 채우지 않음(`isStoredDailyReviewShape`).
  처음에는 누락을 빈 배열로 채웠는데, **그러면 "안 봤다" 가 "없다" 로 둔갑해 이 목표가 세운 명제를
  스스로 깨는 것**이라 봇 리뷰 지적을 받고 고쳤다.
  **봇 리뷰 4건(codex 3 · 이대리 1)은 전부 정탐으로 판정해 반영했다.** ①위 누락/빈 배열 뭉갬
  (codex·이대리가 같은 결함의 legacy 면과 파서 면을 각각 지적) ②`buildWorkText` 가 `plan.blocker` 를
  버려 PM 이 이미 지목한 차단 요소가 회고 입력에 안 실리던 것 — daily·weekly 두 호출부가 코드를
  복제하고 있어 공용 `formatPlanLines` 로 모아 한 번에 고쳤다 ③`risks` 를 "오늘 관찰된" 으로 못 박아
  같은 usecase 를 7일치로 쓰는 주간 요약에서 중간 위험이 빠지던 것 — 입력의 `[기간]` 기준으로 바꿨다.
  ③ 을 고치다 프롬프트 template literal 안의 백틱이 문자열을 끊고 있던 버그도 함께 잡았다.
  게이트: `lint:check` · `test`(513 suite / 5,262 + 콘솔 5 suite / 40) · `build` · `docs:check` 전부 green.
  실측은 빌드 산출물로 렌더해 눈으로 대조 — ①결정·위험 있음 ②둘 다 빈 경우(섹션이 사라지지 않고
  명시 문구로 채워짐) ③미검토(섹션 자체가 안 나옴) ④PM 프롬프트 섹션의 같은 세 갈래 ⑤blocker 가 회고
  입력에 실리는지.
  **Slack 실멘션 왕복은 미검증** — A·B 와 같은 이유로 운영 백엔드(포트 3099) 재시작이 필요하다.
  **실 모델이 두 필드를 실제로 채우는지도 미검증** — 프롬프트·output schema 로 요구만 해 뒀고
  codex 실호출로 확인하지 않았다.
  **범위 밖(의도적)**: Notion `append-worklog` 의 KPT 기록은 안 건드렸다. KEEP-PROBLEM-TRY 는 대표의
  개인 회고 템플릿이라 "대표 결정사항" 이 들어갈 칸이 없고, 요청받지 않은 템플릿 변경이라 뺐다.
  `agent-contract` 의 `deliverableFields` 에도 안 넣었다 — 두 필드는 비는 것이 정상이라 계약에 넣으면
  정상 산출물이 계약 위반으로 잡힌다.
