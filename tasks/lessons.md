# Lessons

## 2026-08-13 — 장중 일봉 부재를 비거래 증거로 단정함

체결 provider 호출이 성공해 전일 봉만 반환됐다는 사실만으로 거래정지·상장폐지를 단정했다. 장중에는 provider가 아직 당일 봉을 만들지 않은 경우도 응답이 같으므로, 첫 회차에서 정상 주문 전체를 만료시킬 수 있었다.

- **적용:** 장중의 당일 봉 부재는 `PENDING` 재시도 대상으로 둔다. 장 마감 후에만 비거래 가능성을 종결 판단한다.
- **계측:** HTTP/timeout 같은 조회 실패와 성공 응답의 당일 봉 부재를 다른 counter로 기록한다.
- **증거 수준:** 같은 응답을 만드는 원인이 둘 이상이면 강한 상태 전이를 하지 않는다. 시간 창·추가 신호로 모호성이 해소될 때까지 보류한다.

## 2026-08-12 — 디렉터리 존재와 저장소 소유권·commit 범위는 별도 검증 대상임

- `.git`이 있다는 사실은 설정한 remote의 clone이라는 뜻이 아니다. 개인 환경처럼 민감한 데이터를 push하기 전에는 설정 repository와 현재 `origin`을 정규화해 비교하고, 불일치 시 자동 삭제·재clone 대신 경로와 양쪽 값을 담아 중단한다.
- 생성 전용 저장소라도 working tree 전체가 생성기 소유라고 가정하지 않는다. 변경 감지와 staging 양쪽에 같은 managed pathspec을 사용해야 미추적 메모·임시 secret이 commit 경계에 들어오지 않는다.
- 삭제를 반영하려면 `git add -A`를 유지하되 경로를 제한한다. 선택적 디렉터리는 처음부터 없을 수 있으므로 scoped status가 있을 때만 개별 stage하면 미존재 pathspec 오류와 tracked deletion을 함께 처리할 수 있다.

## 2026-08-12 — 경로·commit SHA·exit 0만으로는 동기화 정본을 증명하지 못함

- `sourceHome`은 장치 식별자가 아니다. 동일 사용자명의 여러 Mac은 같은 홈 경로를 쓰므로 장치 판별은 hostname처럼 별도 장치 속성으로 하고, 구 데이터에 식별자가 없으면 안전한 쪽인 승인 요청으로 보낸다.
- HEAD SHA가 같아도 working tree 파일은 달라질 수 있다. commit을 승인 단위로 삼는 실행은 side effect 직전에 SHA와 clean tree를 함께 검증해야 한다.
- overwrite 성격의 snapshot push는 경쟁 실패 뒤 로컬 분기를 보존할 이유가 없다. 원격 기본 브랜치를 동적으로 찾아 정본으로 reset하고 전체 export를 제한 횟수만 재시도해 영구 교착을 막는다.
- 부분 성공 warning이 있으면 성공 메시지만 바꾸지 말고 완료 이력도 남기지 않는다. 재승인 경로가 닫히면 경고 노출은 복구 수단이 아니다.
- 자격 증명 검사는 사람이 stdout을 볼 것이라는 가정에 맡기지 않는다. 구조적 manifest 필드로 adapter의 commit 경계에 전달하고, child process env도 필요한 기본값과 명시된 secret만 allowlist한다.

## 2026-08-12 — 기간 이름·기준일·계층 경계·DB 읽기 상한을 테스트에서 놓침

- 기간이 이름에 들어간 지표는 최소 표본 수를 같은 숫자로 강제한다. 짧은 표본으로 계산 가능한 수학적 값과 비교 가능한 도메인 지표는 다르다.
- 횡단면 순위는 모든 후보의 기준일이 같아야 한다. 결과의 `asOf`만 최댓값으로 표시하지 말고, 다른 최신일 후보를 제외하고 제외 건수를 관측 가능하게 만든다.
- 외부 상태 코드에 따른 정책은 adapter가 domain error로 정규화한 뒤 application이 그 계약만 소비하게 한다. application에서 infrastructure error를 import하지 않는다.
- 애플리케이션의 배열 절단은 DB 전송량을 제한하지 않는다. 장기 누적 테이블은 query 자체에 안전한 시간 하한을 두고, 정확한 개수 절단은 기존 애플리케이션 로직으로 보완한다.

## 2026-08-12 — 시계열 지표 이름은 저장 컬럼의 관측 한계를 드러내야 한다

- 일봉에 종가만 저장하면서 `high200`이라고 부르면 독자는 장중 고가를 포함한다고 오해한다. 입력 한계로 이름을 유지해야 한다면 타입과 계산부 가까이에 “최고 종가”이며 장중 고점은 반영할 수 없다는 계약을 남긴다.
- 외부 API 오류가 상태 코드를 가진 전용 오류로 이미 전달된다면 메시지 문자열을 파싱하지 않는다. 오류 타입을 최소 공개하고 호출자가 `instanceof`와 status로 명시적 복구 정책을 적용한다.
- 재시도 성공은 요청 하나가 성공했다는 뜻이 아니라 종목 처리가 최종 성공했다는 뜻으로 집계한다. 중간 재시도 뒤 후속 저장·재수집이 실패하면 회복 건수에 넣지 않는다.


## 2026-08-12 — 도메인 반환 타입은 빈 입력 정책까지 함께 닫아야 한다

- 계산 결과의 필수값(`close: number`)을 정의하면서 빈 입력은 “모든 값 null”이라고 쓰면 타입과 동작이 충돌한다. 빈 입력이 정상 상태라면 필드를 전부 nullable로 퍼뜨리기보다 계산 결과 자체를 `null`로 반환해 하류 분기를 한 곳에 둔다.
- 설계 예시 타입도 레포 의존 방향을 따라야 한다. Infrastructure의 실제 값이 `Prisma.Decimal`이어도 Domain은 기존 구조 타입 `DecimalValue`로 받는다.
- 순위합을 0~100으로 바꾼다는 문장만으로는 구현 계약이 아니다. 동률 순위, null 정렬, 단일 후보 분모 0, 반올림 자리, 최종 tie-break까지 정의해야 재현 가능한 점수가 된다.
## 2026-08-12 — 승인 payload를 검증만 하고 실행 경계에 전달하지 않아 승인 의미가 깨짐

- Preview payload에 `snapshotSha`를 담았지만 applier가 존재 여부만 확인하고 무인자 `applySnapshot()`을 호출해, 승인 대기 중 HEAD가 바뀌면 승인한 snapshot과 실제 적용 snapshot이 달라질 수 있었다.
- 승인·결제·배포처럼 외부 부작용을 허가하는 식별자는 UI/audit payload에 존재하는 것만으로 충분하지 않다. 실행 port의 인자로 끝까지 전달하고 side effect 직전에 현재 대상과 다시 비교해야 한다.
- `exit 0`도 완전 성공과 같지 않다. 하위 script가 warning을 stdout/stderr로 보고하며 부분 성공을 허용하면, adapter가 구조화해 최종 사용자 메시지까지 전달해야 한다. 출력 문자열을 저장만 하고 presentation layer에서 버리면 실패가 성공으로 위장된다.
- 설계가 위험한 무인자 계약을 고정했더라도 limitation 기록으로 끝내지 않는다. 승인 불변식이 깨지는 실제 경로를 확인하면 구현 완료와 분리해 명시적으로 계약 변경 승인을 요청하거나 후속 blocker로 올린다.


## 2026-08-12 — 최신 봉 존재 여부는 초기 적재 완료 조건이 아니다

- `_max(tradeDate)`가 존재한다는 사실은 일봉이 한 건 이상 있다는 뜻일 뿐, 기준 이력 200봉이 채워졌다는 뜻이 아니다. 다른 기능이 같은 저장소에 몇 봉을 먼저 넣을 수 있는 공유 시세 계층에서는 존재 여부로 최초/증분을 나누면 부분 이력이 영구히 복구되지 않는다.
- 최초 적재 완료 여부는 요구한 기준 봉 수로 판단하고, `0봉`·`부분 이력`·`완료 이력`을 분리한다. 부분 이력은 과거 조정가가 바뀔 수 있으므로 전체 구간 upsert가 필요하다.
- 외부 목록으로 대량 상태를 뒤집는 작업은 응답 자체의 절대 하한만으로 부족하다. 첫 실행을 위한 절대 하한과 직전 정상 상태 대비 상대 하한을 함께 둔다.


## 2026-08-12 — 합성 fixture와 필드 존재만으로 실데이터 경계를 고정하지 못함

- `market='KR'`과 `tossSymbol != null`은 국내 조회 가능 종목일 뿐 KRX 보통주 유니버스라는 충분조건이 아니다. 도메인 분류가 완료됐음을 나타내는 `krxMarket != null`까지 조회 경계에 넣는다.
- 외부 목록은 행 구조가 정상이어도 동일 키 행이 중복될 수 있다. 파서 테스트는 합성 행뿐 아니라 보존된 실응답 fixture로 고유 키 불변식을 검증한다.
- scheduled task의 정기 sync를 요일에 제한하면 최초 가동·장애 복구가 다음 요일까지 조용히 지연된다. 저비용 authoritative sync는 매 실행 먼저 수행하고, 0건 성공이 정상인지 별도 검토한다.
- audit DTO에 실패 원인이 있다는 사실은 사용자 가시성과 다르다. `summaryText`/`detailText`/CLI까지 최종 출력선을 테스트하고, 표본 제한은 전체 건수와 절단 사실을 함께 표시한다.

## 2026-08-12 — 성공한 Autopilot 수집을 skip으로 반환해 전달을 지움

- 데이터 수집 task가 원장에는 성공을 남겨도 `{ skip: true }`를 반환하면 Autopilot 오케스트레이터가 사용자 전달 결과를 제거한다.
- env gate로 의도적으로 비활성화한 경우만 `skip: true`로 반환한다. 실제 실행은 수집·갱신·차단·실패 건수를 담은 `summaryText`와 `skip: false`를 반환한다.
- 원장 audit 검증만으로 끝내지 말고, task의 최종 `AutopilotTaskResult`가 사용자에게 전달 가능한지도 회귀 spec으로 고정한다.

## 2026-08-11 — 부분 가격 누락을 표시 문제로만 다루면 가짜 자산 곡선이 영구 적재됨

- 보유 종목 일부의 가격이 아예 없을 때 해당 행만 결과에서 빼고 formatter에 경고를 붙여도, 부분 합계 스냅샷이 적재되면 총평가액 급락이 사후 재계산 없이 영구 고정된다.
- `stale`(가격은 있으나 날짜가 오래됨)과 `unpriced`(가격 자체 없음)는 같은 결손이 아니다. 일부 stale은 근거 가격으로 평가 가능하지만 unpriced는 하나라도 있으면 계좌 총액을 완성할 수 없으므로 스냅샷을 적재하지 않는다.
- 사용자-visible 경고뿐 아니라 영속화 경계까지 추적한다. 잘못된 숫자를 저장한 뒤 표시만 정직하게 만드는 것은 데이터 무결성 수정이 아니다.

## 2026-08-11 — 즉석 다수결 규칙이 전부 stale 분기를 소거함

- `tradeDate`를 관측된 `priceDate`의 다수값으로 정하고 `priceDate != tradeDate`를 stale로 삼으면, 다수 그룹은 정의상 non-stale이라 전부 stale 차단이 도달 불가능해진다.
- 휴장 판정처럼 “모든 입력이 기준일과 다른가”가 필요한 흐름은 기준일을 입력 집합에서 유도하지 않는다. 외부 실행 기준일(`executedAt`의 KST 날짜)을 고정하고 각 입력을 그 기준과 비교한다.
- 새로운 집계 규칙을 추가하기 전에 기존 차단 분기의 도달 가능성을 논리적으로 확인하고, 정본 spec과 어긋나면 구현 전에 중단한다.

## 2026-08-10 — task 진입 수를 성공 산출물로 오인해 skip+실패 재시도를 막음

- `executedTaskCount`는 `skip`도 세므로 전달 가능한 결과가 하나도 없는 `skip + throw`를 부분 성공처럼 만들었다. 재시도 판단은 실행 횟수가 아니라 외부에 전달할 실제 산출물(`summaryText` 또는 preview)과 실패 존재 여부로 표현한다.
- cron 파서를 둘러싼 정책 함수는 현재 기본값 모양만 가정하지 않는다. BullMQ가 허용하는 5필드·6필드 입력을 모두 정규화한 뒤 같은 의미 필드에 정책을 적용하고, 지원하지 않는 필드 수만 보수적으로 거부한다.
- 리뷰 회귀 테스트는 지적된 조합을 그대로 만들고 수정 전 RED를 실제 확인한다. 인접한 all-skip·partial success·preview-only 경계도 함께 고정한다.

## 2026-08-05 — 같은 값으로 수정된 총원은 리베이스 충돌이 나지 않는다

- 두 브랜치가 같은 집계 문구를 같은 중간값으로 바꾸면 3-way merge는 충돌 없이 낡은 값을 보존한다. 리베이스 뒤에는 충돌 유무와 별개로 정본 registry에서 수치를 다시 계산한다.
- 총원 변경은 확인된 파일 목록만 고치지 않는다. 제품 하위 전체의 현재·과거 숫자를 전수 검색하고, 현재 상태 문구만 갱신하며 역사적 결함 기록은 보존한다.
- 부서 인원 증가 뒤에는 전체 배정 단언뿐 아니라 해당 부서의 실제 좌석 수, 방 경계, 벽·문, 통행 불변식을 함께 확인하고 요약에 좌석 여유를 남긴다. 후보 좌표 개수를 용량으로 쓰지 말고 desk-seat 교차 충돌까지 시뮬레이션한 안전 수용량을 기록한다.

## 2026-08-05 — 영속화 후 발송 실패의 멱등 경계

- 저장을 마친 뒤 발송하는 전체 파이프라인에서 발송 실패가 발생해도 완료 guard를 해제하지 않는다. 재시도가 파이프라인 처음부터 시작하면 조사·판정·저장이 중복된다.
- 멱등 회귀 spec은 배열형 반환 mock이 아니라 key 상태를 보존하는 fake로 `acquireOnce`/`isDone`/`release` 의미를 재현한다.
- 요약과 상세처럼 중요도가 다른 다단 발송은 오류 경계를 분리한다. 정본이 DB에 있으면 상세 발송 실패는 warn으로 남기고 이미 성공한 요약을 무효화하지 않는다.

## 2026-08-05 — 회귀 렌더가 안 그리는 요소는 영구 사각지대가 된다

콘솔 오피스의 세션 캐릭터 열 명이 대표실 앞줄에 붙어 서서 이름표가 한 줄 글자 뭉치로
뭉개져 있었는데, 화면 회귀용 오프스크린 렌더(`--render`)가 `syncSessions` 를 호출하지 않아
**세션이 한 명도 그려지지 않았다**. 에이전트·가구·조명만 나오는 그림을 보며 "화면 확인함" 으로
넘어가는 동안, 실제 앱에만 존재하는 이 결함은 점검을 통째로 빠져나갔다.

  보고된다**. 빈 자리는 "문제 없음" 과 구분되지 않는다.
- 화면에 사람/카드/배지를 새로 세우는 경로를 추가할 때는 회귀 렌더에도 같은 sync 를 연결한다.
  안 하면 그 요소는 사람이 실앱을 볼 때까지 아무도 안 본다.
- 라벨 자리를 정할 때 **스프라이트 폭이 아니라 라벨 폭**을 기준으로 간격을 잡는다. 한 칸 간격은
  사람은 구분되지만 머리 위 이름표는 서로 이어 붙는다.
- 바닥·가구 위에 뜨는 글자는 외곽선(`strokeWidth` 음수) 없이는 무늬에 묻힌다. 같은 씬 안에
  외곽선을 쓰는 라벨과 안 쓰는 라벨이 섞여 있으면 후자만 읽히지 않는다.

**적용**: 시각 결함을 고치기 전에 회귀 렌더가 그 요소를 **실제로 그리는지** 먼저 확인한다.
안 그리면 그것부터 연결하고, 고치기 전/후를 같은 방법으로 굽어 대조한다.

## 2026-08-03 — "대표 하나만" 검사한 테스트 두 건 + 접근성 정보 유실 (#208, 이대리 리뷰 3건 정탐)

이대리 자동 리뷰가 3건을 달았고 **전부 정탐**이었다. 두 건이 같은 패턴이다.

**패턴 — 반복 구조를 대표 하나로만 검사했다.** 칸막이 벽은 여섯 열을 세우는데 테스트는 `floor[y][0]` 한 열만 봤고, 휴식 자리는 셋인데 도달성은 `loungeTiles.first` 하나만 봤다. 둘 다 "루프로 만들었으니 하나가 맞으면 나머지도 맞겠지"라는 암묵적 가정이었다. 실제로 깨뜨려보니 오른쪽 세로 벽을 안 세우면 x=9·19·29 세 건이 실패하는데 **기존 검사로는 300건 통과**했다. 루프 범위나 오프셋이 어긋나는 회귀가 정확히 이 틈으로 지나간다.

- **적용**: N개를 만드는 코드는 **N개를 검사한다**. `zones.flatMap`처럼 데이터에서 대상 목록을 유도해 순회하면 대상이 늘어도 테스트가 따라간다. "대표 하나"는 스모크일 뿐 회귀 방지가 아니다.
- **곁들여 배운 것**: 실패 방향이 두 갈래인 불변식은 양쪽을 다 검사해야 한다. 문이 **없으면** 도달성 테스트가 잡지만, 문이 **여러 칸으로 늘어나** 벽이 무의미해지는 쪽은 어떤 테스트도 잡지 못했다. 기존 테스트가 한 방향을 막아준다고 다른 방향이 막히는 게 아니다.
- **새 테스트는 깨뜨려서 확인한다**: 이번엔 일부러 벽을 빼고 문을 넓혀 각각 3건 실패를 확인한 뒤 복구했다. 통과하는 테스트는 아무것도 증명하지 않는다.
- **그 절차가 실제로 값을 했다(#210)**: 비서실 필터의 회귀 테스트를 쓰고 깨뜨려봤더니 **필터를 제거해도 통과**했다. 원인 둘 — (1) `failedRuns` 를 비워둬서 필터가 걸러낼 입력 자체가 없었고, (2) 보고할 항목이 하나도 없어 digest 가 통째로 skip 되어 검증할 문자열이 빈칸이었다. 즉 **테스트가 "실패 조건"을 만들지 못하면 초록불은 아무 의미가 없다.** 회귀 테스트를 쓸 때는 검증 대상 로직이 실제로 실행되는 입력인지, 그리고 그 출력이 조기 반환(skip·early return)으로 사라지지 않는지 함께 확인한다.

**접근성 — 화면에 보이는데 스크린리더에는 없었다.** 대시보드 카드를 한글 직책으로 바꾸며 영문 식별명을 캡션 `Text`로 남기고 "정보 손실 0"이라고 PR에 썼다. 그런데 `accessibilityElement(children: .combine)`은 자식 라벨을 명시 `accessibilityLabel`로 **대체**하므로, 그 캡션이 VoiceOver에 읽히지 않았다. 시각 UI만 보고 손실 없음을 판정한 것이다.

- **적용**: "정보를 다른 곳에 남겼으니 손실 없다"는 주장은 **모든 출력 경로**에서 확인해야 한다. SwiftUI에서 `accessibilityElement(children: .combine)` + 명시 `accessibilityLabel`을 쓰면 자식 라벨은 전부 사라진다 — 화면에 추가한 정보는 라벨 문자열에도 직접 넣어야 한다.

## 2026-08-03 — 파이프가 exit code 를 삼켜 "3중 green"이 거짓이 될 수 있었다 (#200)

PR #200 검증에서 `pnpm test 2>&1 | tail -12; echo "test_exit=$?"` 로 3중 green 을 확인했다. 여기서 `$?` 는 **`tail` 의 종료 코드**다 — jest 가 실패해도 `tail` 이 성공하므로 항상 `0` 이 나온다. 게다가 `tail -12` 는 이 레포 `pnpm test` 의 2단계(jest 2회 실행) 중 **두 번째 단계 요약만** 보여줘, 288 suites 가 도는 1단계 결과가 화면에서 잘려나갔다. 즉 "40 tests passed" 만 보고 2,152개를 확인했다고 착각할 수 있는 구조였다. 실제로는 통과였지만, 실패해도 똑같이 초록으로 보였을 것이다.

- **왜 놓치기 쉬운가**: `set -o pipefail` 이 없는 기본 셸에서 파이프라인의 종료 코드는 마지막 명령의 것이다. 출력을 줄이려고 `| tail`·`| grep`·`| head` 를 붙이는 순간 검증 명령의 성패가 사라진다. 출력 축약과 종료 코드 확인은 **양립하지 않는다**.
- **적용**: 게이트 명령(`lint:check`/`test`/`build`)은 **파일로 리다이렉트하고 exit code 를 따로 받는다** — `pnpm test > /tmp/test.log 2>&1; echo "exit=$?"` 후 로그를 grep 한다. 파이프가 꼭 필요하면 `set -o pipefail` 이나 `${PIPESTATUS[0]}`. 그리고 테스트 통과를 보고할 때는 **총 테스트 수를 함께 확인**한다 — 이 레포는 2단계라 한쪽 요약만 보면 규모가 10분의 1로 보인다([[project_test_script_two_phase]]).

## 2026-08-03 — 시간 상수를 하나만 바꿔 다른 시간 상수가 효과를 삼켰다 (#200)

## 2026-07-23 — 계획서 코드의 async 락/테스트 레이스 결함 (실행 중 발견)

PreviewGate 카드 수명 PR(#157) 구현 중, 계획서에 "완전한 코드"로 적어둔 두 곳이 실행하니 깨졌다. 계획서 코드도 실행 전엔 미검증 가설이다.

- **in-memory 락 획득 시점**: `if (applying.has(id)) throw; ... const p = await assertReadyToResolve(...); applying.add(id)` 처럼 락을 async 검증 **뒤에** 잡으면, 첫 클릭이 `await` 에서 suspend 된 사이 두 번째 클릭도 `has()` 체크를 통과해 둘 다 진행한다(레이스). → 락은 검증 **전에 동기적으로** `add` 해야 한다. 대신 실패-복구 카드 갱신(APPLY_FAILED)이 검증 단계 실패에까지 걸리지 않도록 try/catch 를 이중으로: 바깥은 락 finally, 안쪽은 apply 단계 전용.
- **테스트 deferred gate 취약성**: `apply.mockImplementation(() => new Promise(r => { releaseApply = () => r(...) }))` 는 `releaseApply` 가 mock 호출 시점에야 설정된다. 첫 호출이 아직 apply 에 도달 안 한 상태에서 테스트가 `releaseApply()` 를 부르면 no-op 이 되고 첫 호출이 영원히 매달려 timeout. → gate Promise 와 `releaseApply` 를 **미리 고정**(`const gate = new Promise(r => { releaseApply = r }); apply.mockReturnValue(gate.then(...))`)하고, `setImmediate` 로 첫 호출의 락 획득을 보장한 뒤 두 번째를 던진다.

**적용**: 동시성/락/타이밍이 얽힌 계획서 코드는 TDD 로 먼저 RED 를 실증하고, 통과할 때까지 계획을 신뢰하지 않는다. 락은 "체크와 획득 사이에 await 가 없어야" 원자적이다.

- **적용:** 모델 prompt의 동작을 뒤집을 때는 반대 지시를 append하지 않는다. 기존 충돌 규칙을 조건부 제거·치환한다.
- **테스트:** 새 지시의 존재뿐 아니라 충돌하는 기존 지시의 부재를 함께 검증한다. 비활성 경로는 기준 prompt와 전체 문자열 exact equality로 고정한다.
- **실측:** prompt unit green은 모델 행동의 충분조건이 아니다. 실제 모델 실측 실패가 나오면 문구 강도보다 먼저 모순·반복·배치 구조를 점검한다.

# 2026-08-10 — 대체 알림 경로의 운영 전제를 확인하지 않고 "사용자 통지 유지"로 판정

C1에서 전멸 그룹의 digest 발송을 제거하고 `AutopilotConsumer`의 `publishCronFailure`를 대체 통지로 간주했다. 그러나 실제 경로는 `NotificationPublisher`가 optional이고, `NotificationConsumer`가 `CRON_FAILURE_ALERT_OWNER_SLACK_USER_ID` 미설정 시 즉시 return하며, `.env.example`도 해당 키를 기본 미설정으로 둔다. 코드 경로가 존재한다는 사실만 확인하고 기본 배포에서 끝까지 발송되는지 확인하지 않아 silent failure 회귀를 만들었다.

- **적용**: 기존 사용자-visible fallback을 제거할 때 대체 경로의 DI optional 여부, env 기본값, feature gate, dedupe, enqueue 실패, 최종 send target까지 전부 추적한다. 어느 하나라도 조건부면 기존 fallback과 동등하다고 판정하지 않는다.
- **적용**: "사용자가 계속 통지받는다"는 결론은 happy-path 호출 연결이 아니라 **기본 설정에서 최종 side effect가 발생하는지**로 증명한다. 설정값을 확인할 수 없으면 미설정을 안전 기준으로 삼는다.
- **적용**: retry를 살리기 위해 idempotency guard를 건너뛰는 실패 알림은 retry마다 중복될 수 있다. 이 tradeoff를 코드 주석과 테스트에 명시하고, silent loss와 중복 알림 중 어느 쪽을 선택했는지 운영 근거를 남긴다.

# 2026-08-12 — 외부 조정 시세를 불변 데이터로 가정한 설계 충돌

유니버스 최초·증분 수집 설계에서 `createMany({ skipDuplicates: true })`를 모든 일봉 저장에 쓰려 했지만, 실제 `DailyPrice` 스키마와 기존 감시는 분할·배당으로 과거 조정가가 소급 변경되는 계약이라 upsert를 사용하고 있었다. 설계 문장만 따르면 저장된 조정 계열이 영구히 낡는 결함이었다.

- **적용**: 외부 시계열의 중복 저장 정책을 정할 때 API의 raw/adjusted 의미, schema 주석, 기존 writer의 update 동작을 함께 대조한다. “확정 후 불변”은 공급자가 소급 보정하지 않는다는 근거가 있을 때만 인정한다.
- **적용**: 최초 적재와 증분 갱신의 쓰기 정책을 분리한다. 최초 빈 구간은 `createMany(skipDuplicates)`, 증분 겹침은 upsert하고 저장값 대조로 소급 재작성 신호를 감지한다.
- **적용**: 기존 task의 “구조를 따른다”는 요구는 반환값만 보지 말고 AgentRun, enum, registry, docs까지 연쇄 범위를 추적한다. 재사용 가능한 기존 agent/trigger 조합이 있으면 새 타입을 만들기 전에 확인한다.

# 2026-08-13 — cron 선후관계를 배열 위치만으로 해석함

모의투자 추천 계약의 "16:00, universe-sweep 다음"을 playbook 배열 순서로만 해석할 여지가 있었지만, 실제 `universe-sweep` 기본 시각은 18:30이고 실측 종료는 18:39였다. 16:00 추천은 당일 종가 저장 전 실행돼 판단일과 체결일 사이를 불필요하게 이틀로 벌린다.

- **적용:** "A 다음 실행"이라는 schedule 요구는 배열 위치가 아니라 실제 시작·완료 시각과 timezone을 함께 대조한다.
- **지연 작업:** 선행 batch가 수 분 걸리면 cron 시작 시각만 비교하지 않고 실측 또는 보수적 종료 여유를 둔다.
- **검증:** playbook spec은 배열 인접성뿐 아니라 선행 완료 후 후행 시각이라는 시간 관계도 고정한다.

# 2026-08-13 — 계획 문서의 "남은 것" 표를 실제 잔여로 믿음

"기획 중 남은 일"을 묻는 요청에 `docs/superpowers/plans/` 의 로드맵과 "남은 것" 표를 근거로
잔여 목록을 만들었다. 그 표들은 **작성 시점 스냅샷이고 사후 갱신하지 않는 것이 레포 규칙**인데
(CLAUDE.md §7), 그 사실을 계산에 넣지 않았다. 코드·PR과 대조해 보니 네 항목이 이미 끝나 있었다.

| 문서가 말한 잔여 | 실제 |
|---|---|
| 자율 워커 3종 실행 원장 편입 | #263 으로 머지 완료 |
| README 콘솔 앱 누락 | #286 으로 처리 완료 |
| `scripts/` lint 편입 | `package.json` 에 이미 `{src,test,scripts}` |
| `DOCS_AUDIT_*`·`CONTRADICTION_JUDGE` 발화 확인 | 관측 수단(주간 하트비트)은 이미 있음. **발화 자체는 여전히 미확인** |

마지막 줄에서는 두 번 헛짚었다. 첫째로 문서가 요구한 것은 "원장 편입" 이 아니라 **"발화 확인"**
이었는데 항목 이름부터 바꿔 읽었다. 둘째로 원장 편입이 불필요하다는 근거는 맞았다 — 두 task 는
게이트가 꺼져 있어도, 점검 결과가 0건이어도 요약 1줄을 반드시 내보낸다("꺼둬서 안 했다"와
"죽어서 안 돌았다"를 가르려고). 주석에 "LLM 을 안 쓰는 구간은 agent_run 에도 없다"고 명시하고
하트비트로 대체한 **의도된 설계**이므로, 원장 편입을 했다면 중복 구현이었다.

그러나 거기서 "그러므로 이 항목은 끝났다"로 넘어간 것이 착오다. **하트비트는 발화를 관측할
수단이지 발화했다는 증거가 아니다.** 게이트가 꺼져 있으면 "건너뜀" 하트비트만 나가고
(`docs-sync-audit.autopilot-task.spec.ts` 의 `DOCS_AUDIT_ENABLED='false'` 케이스), 그때 LLM
워커는 한 번도 돌지 않는다. 실제 주간 발화는 Slack·큐·실행 로그에서 따로 확인해야 하고,
그 확인은 아직 하지 않았다.

worktree 도 같은 착시였다. 16개가 미완 작업처럼 보였지만 전부 머지된 브랜치의 잔해였다 —
**squash 머지라 `origin/main..<branch>` 에 원본 커밋이 그대로 남는다.** 커밋 수는 미머지의
근거가 되지 못한다.

- **적용:** 계획 문서는 "그때 무엇을 하려 했나"의 기록이지 "지금 무엇이 남았나"의 답이 아니다.
  잔여를 판정할 때는 문서를 출발점으로만 쓰고, **항목마다 코드 grep·PR 상태·실행 기록으로
  현재 상태를 다시 만든다.**
- **적용:** 브랜치의 머지 여부는 커밋 수가 아니라 **PR 상태(`gh pr list --state all`)** 로 본다.
  squash 머지 레포에서 `rev-list --count` 는 항상 0 이 아니다. 다만 **머지 확인은 worktree 를
  지워도 된다는 뜻이 아니다** — PR 이 `merged` 여도 그 뒤에 얹은 커밋이나 미커밋·untracked
  파일이 남아 있을 수 있다. 삭제 전에 현재 tip 이 PR head SHA 와 같은지, `git status --short`
  가 비어 있는지까지 본다([[feedback_worktree_cleanup_stash]]).
- **적용:** "원장에 기록이 없다"를 결함으로 단정하기 전에 **그 자리에 다른 관측 수단이 있는지**
  본다. 같은 문제를 다른 방식으로 이미 푼 코드가 있으면 편입이 아니라 중복이다. 반대로 **관측
  수단이 있다는 사실을 실행했다는 증거로 쓰지 않는다** — 계기판이 달렸다는 것과 엔진이 돌았다는
  것은 다른 명제다.
- **비용:** 이 대조를 먼저 하지 않았다면 이미 머지된 기능을 다시 구현하고, 해결된 관측 문제에
  중복 코드를 얹고, 살아 있는 작업이 든 worktree 를 지울 뻔했다.
